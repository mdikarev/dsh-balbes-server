# Несколько ботов: разные владельцы и доступ

- Status: draft

## Intent

Один процесс обслуживает несколько bot-подключений, и каждое даёт доступ своему
владельцу: бот становится единицей настройки и разграничения, а не единственной
точкой входа. Сегодня Telegram-канал жёстко single-owner: один token-ref в
`$DSH_HOME/.credentials.yaml`, settings-namespace `balbes-telegram`
(`enabled`, `allowedUserId`), один `$DSH_HOME/telegram-state.json` и ровно
один разрешённый user ID, а OVERVIEW держит «только один владелец, один user ID
и личный чат» вне scope. Эта инициатива описывает будущий облик, в котором
подключений много и доступ между ними разграничен. С инициативой p5 (сессии из
Telegram) она делит понятие сессии воркспейса, но не сливается с ней: p5 — про
создание и возврат к сессиям, p6 — про владельцев и границы доступа.

## In scope

- Несколько bot-подключений в одном процессе: у каждого свой token, allowlist
  (хотя бы один разрешённый user ID), `enabled` и собственное
  persistent-состояние (update offset, активный воркспейс, session mapping).
- Бот как единица доступа: задачи и сессии привязываются к боту, сессии разных
  ботов не смешиваются ни в реестре сессий воркспейса, ни в состоянии.
- Разграничение доступа: у каждого бота — свой набор доступных воркспейсов
  (дом и/или проекты), а не полная вселенная сервера.
- Управление из админки: страница «Telegram» становится списком подключений
  (добавить, удалить, включить; token, user ID, доступные воркспейсы, статус);
  существующий единственный бот мигрирует в первое подключение.
- Хранение: секреты по подключению в `$DSH_HOME/.credentials.yaml`, настройки —
  коллекцией в settings-namespace, нечувствительное состояние — по подключению.
- Совместимость с принятыми механизмами: `AgentTaskService`, командная
  поверхность, карточка прогресса и сериализация задач сохраняются, но получают
  явную привязку к боту.
- Модель угроз меняется осознанно: при нескольких владельцах «нет per-agent
  allow-фильтра и read-guard» перестаёт быть допустимым — границы доступа
  описываются для бота, а не принимаются на веру.

## Out of scope

- Мультиюзерность админки (аккаунты, роли, RBAC в веб-UI): админка остаётся
  single-owner.
- Другие платформы-каналы (A2A и прочие) — отдельные инициативы.
- Групповые и публичные чаты, несколько пользователей внутри одного бота.
- Отдельный процесс или контейнер на бота.
- Федерация: общий доступ ботов к сессиям и воркспейсам друг друга.
- Биллинг, квоты и лимиты ресурсов на владельца.
- Потоковая доставка ответа модели (streaming) — отдельный этап.

## Absorbs into

- ARCHITECTURE.md — модель «несколько ботов = несколько владельцев», хранение
  настроек/секретов/состояния по подключению, правило разграничения доступа и
  место approval.
- GLOSSARY.md — термины «bot-подключение», «владелец бота», «доступные
  воркспейсы бота».
- API_CONTRACTS.md — множественность и параметризация поверхности `telegram.*`.
- ADMIN_UI.md — страница «Telegram» как список подключений.
- OVERVIEW.md — снятие «один владелец, один user ID, один бот» из scope и
  out-of-scope.

## Open questions

- Разграничение доступа: набор разрешённых воркспейсов на бота, отдельный дом на
  владельца или отдельный writable-root?
- Может ли один воркспейс обслуживаться несколькими ботами, и как тогда делятся
  сессии и записи `workspace-sessions.json`?
- Как быть с «нет per-agent allow-фильтра и read-guard»: scope на бота,
  per-bot sandbox-политика, отдельный approval или сочетание?
- Кто отвечает на approval для неинтерактивного канала: владелец бота, общий
  админ или операция отклоняется fail-closed?
- Идентичность подключения: устойчивый slug/id бота (когда `botUsername` может
  меняться) и миграция текущего единственного бота.
- Общий или per-bot выбор дефолтной модели и воркспейса по умолчанию?
- Сериализация задач и очередь (сейчас FIFO до 3 на воркспейс): общая на процесс
  или на бота?
- Может ли один Telegram user ID быть разрешён нескольким ботам, и что это
  значит для атрибуции сессий?
