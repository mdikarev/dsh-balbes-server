# Создание воркспейсов из GitHub

- Status: draft

## Intent

Проект-воркспейс появляется на сервере не только как пустой каталог с именем:
владелец может завести его из существующего git-репозитория, и первым
источником становится GitHub. Это прямое продолжение p0: там создание проекта
ограничено «пустой каталог + имя», а импорт/клонирование из GitHub/GitLab и
git-креденшелы явно вынесены в отдельную будущую настройку (p0, Out of scope).
Здесь направление доводится до будущего облика: репозиторий — ещё один источник
воркспейса, клонирование — обычная операция сервера, а результат — такой же
проект в `$DSH_HOME/projects/<имя>/`, как и созданный вручную из админки.
GitHub выбран первым провайдером; другие git-хостинги описываются как расширение
той же модели, а не как отдельное понятие. Инициатива не меняет живую canon и не
является задачей на исполнение.

## In scope

- Создание проекта-воркспейса из git-репозитория как альтернатива созданию
  пустого каталога: источник — URL репозитория, базовый провайдер — GitHub.
- Результат клонирования — обычный проект: каталог `$DSH_HOME/projects/<имя>/`
  и запись в реестре `projects.json` в доме; после создания это такой же
  управляемый владельцем воркспейс (правила проекта — файлы внутри), как и
  созданный «с нуля».
- Репозиторий как источник, а не как второй тип воркспейса: понятие «воркспейс»
  и разделение дом/проект сохраняются, git — лишь способ наполнения проекта.
- Выбор репозитория и ветки при создании; поведение по умолчанию — ветка
  по умолчанию репозитория.
- Публичные репозитории как базовый сценарий; приватные — через git-креденшелы,
  хранимые на сервере, а не в воркспейсе.
- Имя проекта: выводится из имени репозитория; коллизии с существующими
  проектами и с зарезервированным домом разрешаются явно, а не перезаписью.
- Длительность и сбой: клонирование — операция с видимым статусом и ошибкой в
  админке; неуспех не оставляет полузаписанный проект в реестре.
- GitHub — первый провайдер; расширение на другие git-хостинги опирается на ту
  же модель (git-URL и креденшелы), без отдельного понятия «хостинг».
- Совместимость с dsh-рамкой: git-операция — внешний процесс/инструмент под
  серверной песочницей и политикой approval, а не обход dsh-ядра.
- Владелец всегда главнее: после создания файлы проекта — обычные файлы,
  доступные для ручного редактирования.

## Out of scope

- GitLab и прочие хостинги в первой версии: GitHub первым, остальные —
  расширение той же модели, а не отдельная инициатива.
- Хостинг собственного git-сервера, зеркал и федерации репозиториев.
- Синхронизация после создания (pull/fetch, отслеживание upstream) —
  самостоятельный шаг, а не часть первого создания.
- Коммиты, push, ветки, PR и работа агента с историей git — отдельные
  направления.
- Интеграция с API GitHub как продуктом: issues, PR, reviews, вебхуки, CI.
- GitHub как способ входа в админку (OAuth) и любые аккаунты/роли в веб-UI:
  админка остаётся single-owner.
- Git-команды в чате и Telegram — канальные инициативы, не эта.
- Несколько рабочих копий одного репозитория и управление ими как группой.
- Мультиарендность: общий кэш репозиториев и разграничение доступа между
  владельцами.

## Absorbs into

- ARCHITECTURE.md — модель «воркспейс из git-репозитория»: место git-операции,
  хранение git-креденшелов, связь с песочницей и approval.
- GLOSSARY.md — термины «создание воркспейса из репозитория», «git-источник»,
  «git-креденшелы».
- API_CONTRACTS.md — ручка создания проекта из репозитория и её ошибки/статус.
- ADMIN_UI.md — форма «создать проект из GitHub» и отображение статуса/ошибки
  клонирования.
- OVERVIEW.md — создание из GitHub как альтернатива «пустой каталог + имя» в
  scope создания воркспейса.
- p0-agent-workspaces.md — снятие git-пункта из Out of scope после реализации.

## Open questions

- Приватные репозитории: HTTPS + token в `$DSH_HOME/.credentials.yaml` против
  SSH-ключей; область действия, ротация и отзыв креденшелов.
- Коллизия имени: отказ, автосуффикс или выбор владельца; как связать проект с
  исходным репозиторием в реестре.
- Глубина выбора источника: только ветка по умолчанию, произвольная ветка, тег
  или коммит; поддержка подкаталога для monorepo.
- Submodules и Git LFS: поддержка, отказ или явное предупреждение.
- Транзакционность: как гарантируется уборка частичного каталога и отсутствие
  записи в реестре при ошибке сети или аутентификации.
- Ограничения ресурсов: таймаут, лимит размера и защита от «тяжёлых»
  репозиториев, влияющих на диск и другие задачи.
- Прогресс длительной операции: где живёт статус, кто его видит и что при
  рестарте сервера во время клонирования.
- Расширение на другие хостинги: достаточно ли произвольного git-URL, и что
  считается «поддержанным» провайдером.
