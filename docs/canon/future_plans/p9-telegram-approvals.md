# Апрувы из Telegram: канал запрашивает, владелец даёт

- Status: absorbed
- Design: docs/superpowers/specs/2026-09-24-telegram-approvals-design.md
- Plan: docs/superpowers/plans/2026-09-24-telegram-approvals.md

## Intent

Telegram-канал сегодня неинтерактивен для approval: гейтованная операция штатного
пути инструментов (tool pipeline, sandbox-эскалация bash) при политике `ask`
уходит в waterfall `approval/request`, но у канала нет своего answerer'а,
поэтому запрос резолвится `unavailable` и задача падает fail-closed. Живой canon
фиксирует это как границу канала: «границы — sandbox-политика процесса и approval;
гейтованная операция без интерактивного отвечающего отклоняется (fail-closed), а не
зависает» (ARCHITECTURE, GLOSSARY, OVERVIEW). Эта инициатива переводит канал к
облику, в котором сервер (канал) сам присылает владельцу запрос на подтверждение, а
владелец даёт одноразовое решение прямо в чате. Это расширение канала, а не
изменение dsh-ядра: answerer композируется на штатный шов `ctx.approval`
(waterfall `approval/request`, пакет `@deepseek-ai/dsh-user-approval`), рядом с
уже существующим веб-answerer'ом (`dsh-client-ui-approval`).

## In scope

- Telegram-answerer на штатном шве `ctx.approval` (`approval/request`):
  канал принимает запросы своих агентов (agent-scoped dispatch) и возвращает один
  из штатных исходов — `allowed-once` / `rejected` / `cancelled` /
  `unavailable`, не изобретая собственную семантику решения.
- Доставка запроса владельцу: сообщение в личный чат с идентификацией инструмента,
  причины (`reason`), метки воркспейса и эха задачи; грант одноразовый и действует
  только на этот конкретный запрос.
- Ответ владельца: только inline-кнопки («разрешить один раз» / «отклонить»);
  текстовых команд `/approve` и эвристики по тексту нет. Нажатие закрывает запрос
  ровно один раз, повторный и поздний ответ игнорируются, запрос привязан к своему
  сообщению (`messageId`).
- Тайм-аут и отмена: тайм-аут — жёсткая константа 5 минут; `/stop` и abort
  сигнала инструмента отзывают запрос (сообщение-запрос правится в «отменено»).
  Без ответа исход — отказ, а не зависание: fail-closed сохраняется, но теперь
  решается владельцем, а не отсутствием answerer'а.
- Несколько параллельных запросов: у каждого свой короткий id и своя pending-запись;
  незакрытый запрос одного агента не блокирует другие. Мягкий потолок — 32,
  лишний запрос сразу `unavailable`.
- Совместимость с очередью и живой карточкой: запрос не ломает сериализацию задач
  воркспейса и живой прогресс; карточка и меню-карточка показывают строку
  «⏳ ждёт подтверждения: <tool>», пока запрос висит.
- Политика: остаётся штатной, per-session (`ask` / `never`); канал не понижает и
  не повышает её молча. При `never` запросы до Telegram не доходят.
- Аудит: штатные `approval/asked` / `approval/decided` в сессии агента; решение
  владельца — источник истины, а не эвристика по тексту.
- Разграничение доступа: один бот и один владелец (single-owner); отвечать может
  только разрешённый владелец (private chat + allowed user ID). Мультиботовость,
  группы и несколько пользователей — вне границ.
- Хранение состояния: pending — только in-memory, durable-хранилища нет; после
  рестарта нажатие по неизвестному id отвечает «Устарело» и ничего не меняет.

## Out of scope

- Изменение или обход dsh-ядра и `@deepseek-ai/dsh-user-approval`: только
  композиция answerer'а на штатном шве.
- Новые виды гейтов сверх штатного approval (например, собственная политика
  «подтверждать каждую shell-команду»).
- Постоянные и сессионные гранты («разрешить всегда»): только one-shot, как в
  dsh; расширение политики — отдельная инициатива.
- Веб-UI approval — он уже существует (`dsh-client-ui-approval`) и не меняется.
- Мультиюзерность админки, групповые чаты и несколько пользователей внутри бота.
- Другие каналы (A2A и прочие) и потоковая доставка ответа модели.

## Open questions

На момент `implementing` открытых вопросов нет: их закрыл утверждённый дизайн
`docs/superpowers/specs/2026-09-24-telegram-approvals-design.md`.

- Форма ответа: только inline-кнопки («✅ Разрешить один раз» / «⛔ Отклонить»);
  текстового `/approve` и эвристики по тексту нет. Запрос привязан к своему
  `messageId`.
- Тайм-аут: жёсткая константа 5 минут, без настройки и админского тумблера.
- Что видит владелец: имя инструмента, `reason`, метка воркспейса и эхо задачи
  (обрезанное); аргументов инструмента в запросе шва нет by construction.
- Параллельность: несколько pending одновременно, у каждого свой id; незакрытый
  запрос одного не блокирует другие; мягкий потолок 32 → лишний `unavailable`.
- `/stop` и abort: отзывают запрос, сообщение-запрос правится в «отменено»,
  исход `cancelled`.
- Хранение: только in-memory; после рестарта неизвестный id отвечает «Устарело».
- Боты и владельцы: один бот, один владелец (single-owner).
- Настройка: отдельной нет — approval всегда включён, когда включён канал.
