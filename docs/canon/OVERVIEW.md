# Overview

## Purpose

`dsh-balbes-server` — серверная дистрибуция DeepSeek Harness на фундаменте dsh:
собственная сборка движка dsh (без форка) для работы на VPS в single-user
режиме, без штатной веб-морды dsh и со своей админкой. Цель — разворачиваемый
агентский сервер, который обрастает админкой (сделано), долговременной памятью
и самообучением (аддитивные компоненты над dsh, следующие этапы).

## Problem & context

dsh — это лоадер профилей: профиль = список бандлов (`dsh.profile.bundles`) +
свой слой патчей (`cordis.patch.yml`). Любая функция dsh — Cordis-компонент,
который можно отключить, переопределить или добавить патчем; даже штатная
веб-морда (`dsh-web-app` + `dsh-client-ui-*`) и MCP-клиент — бандлы, а не ядро.
Поэтому «свой сервер» не требует форка: он собирается из готовых бандлов dsh
поверх `dsh-base` через собственный профиль, без правки установленных
`@deepseek-ai/*`.

Долгосрочный вектор — самообучаемый агент с долговременной памятью (внешний
референс направления — продукт Hermes Agent). Выполнены Этап 1 (разворачиваемое
ядро dsh-base на сервере) и Этап 2 (сервер-демон с авторизацией и админкой-
срезом «логин + одна кнопка тестового промпта»). Поверх этапа 2 — воркспейсы
на сервере (дом агента + проекты с реестром-индексом и страницей админки) и
Telegram-канал для владельца с выбором воркспейса, persistent dsh-сессиями,
задачами агента и чтением файлов.
Память, самообучение, git и детальный UX админки — будущие этапы.

## Primary users / agents

- Один владелец сервера (single-user): устанавливает профиль `balbes` на VPS
  одной командой; работает с сервером через админку в браузере (вход по
  логину/паролю, тестовый промпт) и через API (`curl` с JWT).
- Агенты-разработчики, работающие в этом репозитории: следуют canon
  (`docs/canon/`), рамкам CONTRIBUTING и правилам AGENTS.md.

## Scope

### In scope

- Профиль dsh `balbes` = `@deepseek-ai/dsh-base` + `dsh-balbes-host`
  (собственный host-бандл); headless удалён из профиля; штатная веб-морда dsh
  не включается.
- Сервер-демон: один процесс dsh под systemd (`dsh-balbes`), автозапуск,
  переживает reboot; HTTP на `0.0.0.0:${BALBES_PORT:-8080}`.
- Собственный host: плагины `startup`/`server`/`auth`/`static`/`api`
  (пакет `dsh-balbes-host`): роутинг `/api/*` (только POST — правило R-API-1),
  JWT-авторизация, раздача SPA.
- Воркспейсы на сервере: пакет-плагин `dsh-balbes-workspaces`
  (`packages/plugins/`), дом агента `$DSH_HOME/agent/` (автосоздание при
  первом старте, зарезервирован) и проекты `$DSH_HOME/projects/<имя>/`
  (строгий slug); при первом старте в доме создаются стартовые файлы
  `AGENTS.md`, `self.md` и каталог `skills/` (только отсутствующие, без
  перезаписи); каталог — источник правды, реестр-индекс
  `$DSH_HOME/projects.json` (600); API
  `/api/workspaces/list|create|delete|tree|events` (bearer; `tree` —
  scoped-чтение каталогов воркспейса по одному каталогу, `events` — push-
  события внешних изменений для живого дерева; контракты — в API_CONTRACTS);
  страница
  админки «Проекты»: панель списка воркспейсов (дом закреплён, «⋮»-действия,
  создание «+»), дерево каталогов выбранного воркспейса, пустая правая зона
  под будущее содержимое.
- Telegram-канал владельца: пакет-плагин с long polling, только личный чат и
  один разрешённый Telegram user ID; настройка token, user ID и enabled через
  админку; выбор воркспейса inline-списком; persistent dsh-сессия на workspace;
  задачи с `cwd` выбранного корня; ленивое дерево и просмотр ограниченных
  текстовых файлов; состояние polling и session mapping сохраняются в
  `$DSH_HOME` и переживают рестарт (сессия возобновляется). Поверхность
  инструментов задачи ограничена файлами выбранного воркспейса, поиском в
  интернете и планированием: без shell, skill, subagent и загрузки
  произвольных URL.
- Раздел «Модели»: страница админки и API
  `/api/models/list|save|delete|default` (bearer) — подключения
  провайдеров: DeepSeek официальный (закреплён, только ключ), пресеты
  каталога движка dsh (провайдер из каталога: официальный URL по
  умолчанию, опциональный override «свой URL») и «Свой URL»/custom
  (displayName/baseURL/ключ/модели); глобальная дефолтная модель для
  `/api/prompt`. Значения ключей — refs в `$DSH_HOME/.credentials.yaml`;
  API ключи не возвращает никогда (контракты — в API_CONTRACTS).
- Админка `dsh-balbes-admin` (React + Vite): вход по логину/паролю, кнопка
  «Отправить тестовый промпт» → ответ модели над кнопкой.
- Учётные данные админки: `$DSH_HOME/admin-auth.json` (600, пароль только
  scrypt-хэш), генерация один раз при установке; сброс ротирует `jwtSecret`.
- Одно-командная установка/обновление на VPS с Ubuntu (`scripts/install.sh`,
  `curl | bash`): окружение, сборка workspace, синк профиля + копия host,
  развёртывание SPA, ключ DeepSeek в `.credentials.yaml`, systemd, health-
  проверка с ретраями.
- Контракты API: типы `dsh-balbes-contracts` + человекочитаемый реестр —
  секция API_CONTRACTS.md.
- CI (GitHub Actions) без LLM: сборка, typecheck, unit-тесты, композиция
  профиля, `bash -n`.
- Runbook эксплуатации (`docs/runbooks/stage2-vps.md`).

### Out of scope

- Git: импорт/клонирование из GitHub/GitLab, ключи и токены для git —
  отдельная будущая инициатива.
- Список сессий в админке, управление runs/скиллами в UI, HTTPS/TLS и домен;
  потоковая доставка ответов модели (SSE/WS); скачивание бинарных файлов из
  Telegram; полноценная многопользовательская модель.
- Наполнение дома сверх стартового набора (`AGENTS.md`/`self.md`/`skills/`
  уже создаются сервером): `notes/`, применение файлов дома и глобальных
  правил в контексте агента, скиллы — последующие шаги.
- Другие каналы (A2A и прочие) — последующие этапы; Telegram реализован только
  для одного владельца, одного разрешённого user ID и личного чата.
- Долговременная память (Qdrant), самообучение.
- Мультиюзерность, аккаунты, роли.
- Замена драйвера агентского цикла; граф-конфиг поведения.
- Полноценный CI с LLM-вызовами (в CI нет ключей); автотесты в модель не ходят
  (R-TEST-1).

## Success signals

- Профиль `balbes` разворачивается на VPS одной командой (проверено на Ubuntu,
  dsh 0.1.2-rc.1); повторный запуск = обновление.
- Сервис-демон `dsh-balbes` активен и переживает reboot; `POST /api/health`
  отвечает `{ok:true}`.
- Админка открывается по `http://IP:8080`; вход логином/паролем из установки;
  неверный пароль → 401; верный → JWT → кнопка; перезагрузка страницы не
  требует входа.
- Кнопка отправляет тестовый промпт; ответ реальной модели показывается над
  кнопкой.
- Страница «Проекты» в админке: панель списка воркспейсов (дом агента
  закреплён и зарезервирован; «⋮» → «Удалить» с модальным подтверждением;
  «+» создаёт проект); выбор воркспейса показывает его каталоги и файлы
  деревом; изменения каталогов извне отражаются в дереве. Создание через UI
  создаёт пустой каталог `$DSH_HOME/projects/<имя>/` и строку реестра;
  удаление удаляет каталог и запись; каталог, созданный руками, виден
  в списке.
- Смена ключа/подключения/дефолтной модели в разделе «Модели» применяется
  к следующему запросу `/api/prompt` без рестарта сервера.
- В разделе «Telegram» владелец сохраняет token, user ID и enabled; проверка
  через Bot API запускает polling без рестарта, а выключение его останавливает.
  В личном чате владелец выбирает дом или проект inline-кнопкой, отправляет
  задачу штатному dsh agent loop, получает ответ с workspace `cwd` и открывает
  дерево/ограниченное текстовое содержимое файлов.
- Запросы к `/api/*` без валидного JWT → 401 (кроме `login` и `health`).
- Обновление не меняет учётные данные; сброс пароля ротирует `jwtSecret`
  (выданные токены становятся недействительными).
- Штатная веб-морда dsh не запускается; headless в профиле отсутствует.
- CI зелёный; REAL-тесты (LLM как HTTP-stub) проходят локально.
- Секреты не хранятся в репозитории: ключ в `.credentials.yaml` (600),
  учётные данные админки в `admin-auth.json` (600) на сервере.
