# Architecture

## Summary

Один процесс dsh (модель B1): ядро и плагины-каналы живут в одном
Cordis-процессе; оркестрации нескольких процессов нет. Всё своё реализуется
механизмами dsh — профилем (`dsh.profile.bundles`), слоем патчей
(`cordis.patch.yml`) и собственными пакетами; установленные `@deepseek-ai/*`
не редактируются и ядро не обходится. Текущее состояние — Этап 1 выполнен
(разворачиваемое ядро), Этап 2 выполнен: профиль `balbes` = `dsh-base` +
собственный host-бандл `dsh-balbes-host` вместо headless; сервер-демон
под systemd с HTTP-админкой (JWT-авторизация, SPA со страницами управления
«Проекты», «Модели», «Telegram», «Память»). Поверх
этапа 2 — воркспейсы на сервере (дом агента и проекты с реестром-индексом,
API `/api/workspaces/*`, создание проекта из GitHub-репозитория, страница
админки), раздел «Модели» и Telegram-канал:
плагин `dsh-balbes-models` управляет подключениями провайдеров, ключами и
дефолтной моделью поверх сервисов движка, а Telegram-плагин даёт владельцу
long polling, выбор воркспейса, persistent dsh-сессии, задачи agent loop и
просмотр файлов (см. Building blocks / Key flows). Дом агента служит
источником глобального контекста процесса: его правила `AGENTS.md`, секция
`self.md` системного промпта и `skills/` действуют во всех воркспейсах, а
проект добавляет локальные `<project>/.dsh/skills` (слои global → project).
GitHub-репозиторий — источник проекта: плагин `dsh-balbes-git` клонирует
публичный или приватный (по токену) репозиторий в обычный проект, не меняя
понятия «воркспейс». Штатная веб-морда dsh не используется.

## System context

Внешние акторы и системы:

- VPS с Ubuntu (целевая — свежая LTS): хост, на котором живёт профиль `balbes`
  и данные dsh в `$DSH_HOME` (по умолчанию `~/.dsh`).
- Браузер владельца: открывает админку по `http://<IP>:${BALBES_PORT}`, ходит
  в `/api/*` с JWT (единственный origin: host раздаёт и SPA, и API).
- npm registry: источник глобального пакета `@deepseek-ai/dsh` и devDeps
  наших пакетов (registry-версии самих `@deepseek-ai/dsh-*` не используются).
- GitHub (`mdikarev/dsh-balbes-server`, ветка `main`): источник профиля и
  скриптов; `raw.githubusercontent.com` отдаёт install.sh для `curl | bash`;
  GitHub Actions — CI. GitHub-репозитории — также источник проектов:
  сервер клонирует репозиторий владельца (публичный или приватный по PAT) в
  `$DSH_HOME/projects/<имя>/`; git-процесс — обычный внешний процесс
  серверного кода, без обхода dsh-ядра.
- API DeepSeek: модель для промптов; ключ хранится в
  `$DSH_HOME/.credentials.yaml` (ref `DEEPSEEK_API_KEY`) и задаётся в админке
  (раздел «Модели») либо, при автоматизированной установке, через env
  `DEEPSEEK_API_KEY`.
- Telegram Bot API: внешний HTTPS API, который сервер вызывает через long
  polling и sendMessage; телефон владельца — обычный Telegram-клиент, прямого
  соединения сервера с телефоном нет. Bot token хранится через credentials.
- dsh как установленный движок: его mirror (`$DSH_HOME/profiles/node_modules`)
  резолвит базовые бандлы; наш host копируется в `node_modules` профиля.

## Building blocks

- `profiles/balbes/` — профиль-манифест: `package.json` с
  `dsh.profile.bundles = ["@deepseek-ai/dsh-base", "dsh-balbes-host"]` и
  `patchReload: startup`; профильный слой патчей `cordis.patch.yml` —
  insert-записи `balbes-workspaces`, `balbes-telegram` и других внешних
  плагинов; профильный слой применяется последним, после патчей бандлов. В
  репозитории профиль живёт без `node_modules`.
- `@deepseek-ai/dsh-base` — бандл ядра: полный стандартный агентский набор
  (агентский цикл, тулы bash/fs/web/workflow/subagent/skill, скиллы, сессии,
  credentials, политики).
- `packages/bundles/dsh-balbes-host/` — собственный Cordis-бандл: патч-слой
  (`cordis.patch.yml`: persona, PTC-режим тулов, вставки
  плагинов) + плагины по экспортным подпутям: `startup` (app-слой CLI; без
  внешних зависимостей), `server` (HTTP на `node:http`, сервис `balbesHttp`:
  POST-роутинг `/api/*` с публичными/bearer-местами, лимит тела 1 МиБ, dispose
  по сигналу), `auth` (сервис `balbesAuth`: scrypt-проверка, JWT HS256
  issue/verify с чтением актуального секрета из файла на каждый вызов,
  rate-limit входа 5/30 мин по IP), `static` (раздача SPA с fallback
  `index.html` только на ENOENT-семейство), `api` (`/api/health`,
  `/api/prompt`; runner повторяет шов headless: `agents.create` →
  `followup` → `whenIdle` → `sessions.flush` → `AgentHandle.dispose` в finally).
  Workspace-aware задачи проходят через общий `AgentTaskService`, который
  использует штатный dsh agent loop, передаёт безопасный `cwd`, удерживает
  отдельный session context на workspace и сериализует задачи одного корня.
- `packages/contracts/` — `dsh-balbes-contracts`: чистые TS-типы
  запросов/ответов API (импортируются SPA-клиентом; host держит структурные
  формы, соответствие проверяется REAL-тестами и typecheck).
- `packages/plugins/dsh-balbes-workspaces/` — плагин воркспейсов: сервис
  `balbesWorkspaces` + доменные функции (валидация имени, обеспечение дома,
  list/create/delete проектов, создание проекта из git-репозитория, чтение/
  запись реестра). Дом —
  `$DSH_HOME/agent/`, проекты — `$DSH_HOME/projects/<имя>/`, реестр-индекс —
  `$DSH_HOME/projects.json`. При обеспечении дома создаётся
  `agent/skills/README` (без `.md`, чтобы провайдер скиллов не парсил стартер
  как скилл), а при создании проекта — `<project>/.dsh/skills/README`.
  Подключается insert-записью в патч профиля;
  собранный пакет копируется в `node_modules` профиля установщиком и CI.
  Дерево воркспейса в админке: scoped-чтение каталогов (лениво, строго внутри
  корня воркспейса, без выхода по `..`/symlink) + watcher внешних изменений
  каталогов с доставкой событий push-каналом в SPA (точные ручки и формат
  событий фиксируются в API_CONTRACTS с реализацией). Чтение файла воркспейса в
  админке: домен `workspaces.file` поверх `readWorkspaceFile` — тот же
  контеймент, что у дерева (лексический и по realpath, строго внутри корня
  воркспейса), лимит 256 КиБ с флагом усечения, бинарность по содержимому,
  финальный симлинк не разыменовывается.
- `packages/plugins/dsh-balbes-git/` — функциональный плагин git-доступа:
  сервис `balbesGit` и ручки `/api/git/*` (статус/сохранение/сброс GitHub-
  токена) плюс клонирование репозитория в целевой каталог. Владеет только
  git-механикой и токеном: допускает лишь `https://github.com/<owner>/<repo>`
  (защита от SSRF и утечки токена на чужой хост), запускает `git` внешним
  процессом с токеном в окружении (не в argv), remote остаётся чистым, ошибки
  санитизируются; клоны сериализуются. Подключается insert-записью в патч
  профиля; собранный пакет копируется в `node_modules` профиля установщиком
  и CI.
- `packages/plugins/dsh-balbes-home/` — функциональный плагин глобального
  контекста дома: инжектит `systemPrompt` и регистрирует синхронную секцию
  `balbes:self` (order 100) с содержимым `$DSH_HOME/agent/self.md`; файл
  читается с кэшем по `mtimeMs`, отсутствие/ошибка чтения → пустая секция,
  `{{` экранируется, отсутствие сервиса `systemPrompt` → warning без
  регистрации. Правила (`AGENTS.md`) и скиллы плагин не читает — за них
  отвечают нативные швы `agent-instructions`/`skill-filesystem`.
  Подключается insert-записью в патч профиля; собранный пакет копируется в
  `node_modules` профиля установщиком.
- `packages/plugins/dsh-balbes-models/` — функциональный плагин «Модели»:
  сервис-ручки `/api/models/*` поверх `balbesHttp` (CRUD подключений
  провайдеров и дефолтной модели). Собственного состояния нет: роуты
  провайдеров — settings-секция `llm-pi-ai`, ключи — refs
  в `$DSH_HOME/.credentials.yaml`, дефолтная модель — `agent-default-model`;
  тонкий слой над `ctx.settings`/`ctx.credentials`/`agentDefaultModel`,
  без правок установленных `@deepseek-ai/*`. Подключается insert-записью
  в патч профиля; собранный пакет копируется в `node_modules` профиля
  установщиком и CI.
- `packages/plugins/dsh-balbes-telegram/` — функциональный Telegram-плагин:
  long polling Bot API, private-chat и allowlist-проверки, настройка token и
  user ID через админку, inline-выбор workspace, task dispatch в общий
  `AgentTaskService`, ленивое дерево и ограниченное чтение text-файлов,
  командная поверхность (карточка-меню, статус, смена воркспейса и модели,
  сброс контекста, список сессий воркспейса и архив, остановка задачи), живая
  карточка прогресса задачи и approval-answerer: канал сам подтверждает у
  владельца гейтованные операции своих агентов и возвращает штатный исход
  (`allowed-once` / `rejected` / `cancelled` / `unavailable`). Канальный
  срез `sessions` соединяет реестр
  воркспейса (канал `telegram`) с движком (`sessionQuery`: заголовок/время/
  доступность) и управляет выбором и архивом; `selectSession` отсоединяет
  текущий хэндл и записывает активную привязку, а следующая задача лениво
  резюмит выбранную. Состояние offset, active workspace, активная привязка
  сессий и архив хранится атомарно в `$DSH_HOME`; polling останавливается
  через Cordis dispose. Плагин не обращается к файловой системе напрямую и не
  вызывает собственный HTTP API.
- `packages/plugins/dsh-balbes-sessions/` — функциональный плагин сессий
  воркспейса: владелец файлового реестра сессий воркспейса
  `$DSH_HOME/workspace-sessions.json` (600, атомарная запись tmp+rename,
  append-only, upsert по `sessionId`), сервиса `balbesSessions` (единственный
  способ записи) и домена ручек `sessions.*`. Реестр хранит только
  принадлежность (`sessionId` + канал сессии); заголовок и время сессии —
  источник правды движок (`sessionQuery`), реестр их не дублирует. Ручка
  `sessions.read` отдаёт диалог сессии: containment — сессия читается, только
  если зарегистрирована за запрошенным воркспейсом (проверка проекта, затем
  записи реестра), и только после этого — чтение у движка
  (`sessionQuery.readSession`). Источник транскрипта гибридный: не-служебные
  реплики (владелец/модель/инструмент) берутся, если событие durable
  append-origin ИЛИ остаётся в текущей модельной поверхности (`inContext`) —
  замещения и компакция не стирают уже увиденное, а заменяющие копии (напр.
  сводка компакции) видны; системный промпт и служебный контекст
  (`source.kind === "plugin"`) — только текущая модельная поверхность
  (`foldSurface`, т.е. `inContext`); флаг `inContext` у каждой строки
  показывает, входит ли событие в текущую поверхность. Нормализация — на сервере
  (`deriveEventMessage`), SPA рендерит.
  Писатели —
  все, кто создаёт сессию для воркспейса: сейчас Telegram-канал через сервис
  `balbesSessions`. Подключается insert-записью в патч профиля; собранный
  пакет копируется в `node_modules` профиля установщиком и CI.
- `packages/frontend/dsh-balbes-admin/` — React SPA (Vite): типизированный
  api-клиент (JWT в localStorage, 401 → logout), экраны Login/Main. Файловый
  таб рендерит содержимое по типу поверх `workspaces.file`: markdown — в
  документ (санитизация на клиенте, сырой HTML не исполняется) с
  переключателем «просмотр/исходник», код известного языка — с подсветкой
  синтаксиса, прочее и неизвестные языки — моноширинным текстом. Рендер,
  санитизация и подсветка — клиентские; серверный контракт не меняется.
- `scripts/install.sh` — одно-командный установщик (`curl | bash`):
  `set -euo pipefail`, идемпотентен; окружение (Node ≥ 22 / pnpm / git /
  глобальный dsh), сборка workspace (`pnpm install` → `node scripts/link-core`
  → сборка пакетов), синк профиля + копия собранного host в его `node_modules`
  (реальный каталог — резолв `@deepseek-ai/*` подъёмом к mirror), развёртывание
  SPA в `$DSH_HOME/balbes/ui`, ключ DeepSeek в `.credentials.yaml` (600)
  только при заданном `DEEPSEEK_API_KEY` (интерактивного запроса нет; иначе
  ключ задаётся в админке, раздел «Модели»),
  генерация/печать учётных данных админки один раз (`scripts/admin-creds.mjs`),
  systemd-юнит `dsh-balbes` (enable + restart), health-проверка с ретраями
  (~120 c), флаг `--reset-admin-password` (ротация пароля и `jwtSecret`).
- `scripts/admin-creds.mjs` — генерация/сброс учётных данных админки через
  собранный `dsh-balbes-host/lib/core.js` (криптография в Node, не в bash).
- `scripts/link-core.mjs` — линковка зеркала `@deepseek-ai/*` в корневой
  `node_modules` для сборки/typecheck (следует симлинкам; nested и hoisted
  раскладки npm).
- `.github/workflows/ci.yml` — CI без LLM: Node 22, corepack pnpm, глобальный
  dsh из пина `scripts/engine-version.txt`, `pnpm install` → `link-core` → сборка
  → typecheck → unit-тесты →
  синк профиля + копия host → `--dump-config` → проверка отсутствия
  headless/web-app → `bash -n` → JSON-валидация манифеста.
- `docs/runbooks/stage1-vps.md`, `docs/runbooks/stage2-vps.md` —
  эксплуатационные runbook'и (установка, smoke, обновление, DoD, неполадки).

## Memory layer

Долговременная память Балбеса (инициатива p10; фундамент — p10a) — host-side
слой знания: durable-источник правды о том, что агент «знает» между сессиями и
воркспейсами, и сервис `balbesMemory` для остальных слоёв. Память
доставляется модели agent-scoped слоем доставки (p10c): ядро и карта входят
в системный промпт, релевантные записи — в runtime-контекст, полный текст
доступен инструментом `recall`. Записывает знание сам агент — инструментом
`remember` (p10e), явно и с провенансом; уровень записи выбирает слой, а не
модель. Запись, порождённая пайплайном, не становится истиной молча: она живёт
предложением и ждёт решения владельца в очереди ревью (p10f, ниже). Знание из
успешной задачи слой извлекает сам: после хода, в котором агент работал, он
инициирует служебный ход извлечения, и агент предлагает единицы знания
инструментом `propose_memory` (p10g, ниже) — снова предложением, не истиной.
Владелец при этом видит и правит записи через админ-поверхность (p10b).
Сессионную память держит движок dsh — она не переизобретается и не
затрагивается.

### Носитель и схема

- Источник правды — SQLite через `node:sqlite` (`DatabaseSync`), файл
  `$DSH_HOME/storages/memory.sqlite` (плюс `-wal`/`-shm` при WAL). Node ≥ 22
  (в контуре 24.x); с json-бэкендом dsh в `$DSH_HOME/storages` не конфликтует —
  у него другие имена.
- При открытии: `journal_mode=WAL`, `foreign_keys=ON`,
  `busy_timeout=5000`. Все запросы — подготовленные выражения;
  единственный writer — сервис.
- Схема v1: таблица `memories` (запись памяти), нормализованная
  `memory_tags`, внешнеконтентный FTS5-индекс `memory_fts`
  (`content='memories'`, `tokenize='unicode61 remove_diacritics 2'`),
  синхронизируемый триггерами `AFTER INSERT / AFTER UPDATE OF text / AFTER
  DELETE`. Теги в полнотекст не входят: фильтр по тегу — точный join с
  `memory_tags`, второй источник правды не заводится. В схеме зарезервирована
  колонка `embedding` (BLOB) — в p10a не заполняется.
- Схема v2 (аддитивно, p10f): таблица `memory_proposals` (предложенная запись)
  с JSON-колонкой `tags` и ссылкой `memory_id` на промоутированную запись
  (`ON DELETE SET NULL`, чтобы строка аудита пережила удаление самой записи).
  Таблица истины `memories`, `memory_tags` и FTS-триггеры не меняются ни
  строкой. Колонки `pinned` у предложения нет, поэтому пайплайн структурно не
  может предложить закрепление — пиннуть запись можно только при одобрении,
  рукой владельца.

### Запись памяти и уровни (scope)

- Запись: `id` — `crypto.randomUUID()`; `type` — `fact |
  preference | decision | note`; `text` — содержательный текст;
  `tags` — массив слагов; `pinned` — булев; `createdAt`/`updatedAt` —
  ISO-8601; `embedding` — зарезервировано.
- Провенанс: `origin` — `owner | agent`, `originRef` — необязательная
  ссылка ≤ 512 символов (для агента — откуда знание).
- Два уровня: `global` — дом, действует во всех воркспейсах
  (`scope_name` IS NULL); `project` — проект по слагу `[A-Za-z0-9._-]`
  ≤ 64 (`scope_name = <слаг>`). Уровни изолированы.
- Scope неизменяем: `update` его не принимает, смена scope — delete + save.
- Валидация (без новых runtime-зависимостей): `text` непустой, обрезается по
  краям, ≤ 8 КиБ; `tags` — слаги `[a-z0-9._-]` ≤ 32, каждый ≤ 32 символов,
  без дублей, сохраняются в нижнем регистре; `originRef` — строка ≤ 512 или
  `null`.

### Сервис `balbesMemory`

Сервис — единственный способ записи в хранилище:

```ts
interface BalbesMemoryService {
  save(draft: MemoryDraft): Promise<MemoryRecord>;
  get(id: string): Promise<MemoryRecord | undefined>;
  update(id: string, patch: MemoryPatch): Promise<MemoryRecord>;
  delete(id: string): Promise<boolean>;
  list(filter?: MemoryFilter): Promise<MemoryRecord[]>;
  search(request: { query: string; filter?: MemoryFilter; limit?: number }): Promise<SearchHit[]>;
  count(filter?: MemoryFilter): Promise<number>;
  propose(draft: MemoryProposalDraft): Promise<MemoryProposal>;
  getProposal(id: string): Promise<MemoryProposal | undefined>;
  listProposals(filter?: MemoryProposalFilter): Promise<MemoryProposal[]>;
  approve(id: string, patch?: MemoryDecisionPatch):
    Promise<{ proposal: MemoryProposal; record: MemoryRecord }>;
  reject(id: string): Promise<MemoryProposal>;
}
```

- Методы `async` (Promise), хотя `DatabaseSync` синхронен: стабильный шов на
  случай смены backend'а и единообразие с `balbesWorkspaces`/`balbesSessions`.
- Фильтры: `scope`/`scopes` (глобальный и текущий проект одним запросом),
  `type`, `tag`, `pinned`, `limit`, `offset`. `list` — порядок
  `pinned DESC, updated_at DESC`, лимит по умолчанию 100, максимум 500;
  `count` игнорирует `limit`/`offset`.
- Поиск — FTS5: `memory_fts MATCH ?` с ранжированием `bm25()`, порядок
  `pinned DESC, rank ASC`, лимит по умолчанию 20, максимум 100; пустой или
  пробельный `query` → `invalid-query`. Векторный retrieval — аддитивный
  слой позже.
- Методы предложений (p10f) — аддитивны и не меняют существующие:
  `propose`/`getProposal`/`listProposals`/`approve`/`reject`; их семантика — в
  «Ревью и автономия записи (p10f)», контракты — в API_CONTRACTS.md.
- Ошибки со стабильными кодами: `secret-detected`, `invalid-record`,
  `invalid-scope`, `invalid-filter`, `invalid-query`, `invalid-status`,
  `not-found` (тип `MemoryError`).
- Дедупликации, TTL и разрешения конфликтов нет — это p10d; `update` не меняет
  `origin` и не трекает «кто последний правил».

### Приватность

- На `save` и на `update` с непустым `text` текст проходит детектор
  секретов. Совпадение → `secret-detected`, ничего не пишется (fail loud).
  Тот же барьер действует на `propose` и на правке при `approve` (p10f, ниже),
  поэтому секрет не попадает в память и через ревью.
- Зафиксированные паттерны: префиксы провайдерских ключей (`sk-`, `ghp_`,
  `github_pat_`, `xoxb-`, `xoxp-`, `AKIA[0-9A-Z]{16}`), Telegram
  bot token (`\d{8,10}:[A-Za-z0-9_-]{35}`), PEM private key
  (`-----BEGIN[^-]*PRIVATE KEY-----`), присваивания
  (`(password|passwd|api[_-]?key|secret|token)\s*[:=]\s*\S+`), connection
  string с паролем (`://[^/:\s]+:[^/@\s]+@`) и
  `Bearer\s+[A-Za-z0-9._-]{16,}`.
- Это «защитный забор», а не доказательство: слова вида «password policy» без
  значения не срабатывают. Инвариант: плагин не читает
  `$DSH_HOME/.credentials.yaml`; `originRef` — непрозрачный текст провенанса
  (идентификатор сессии, путь, URL), он не резолвится и отдельно от `text` на
  секреты не проверяется.

### Миграции и жизненный цикл

- Миграции живут в коде плагина упорядоченным списком `{version, up(db)}[]`;
  прогон при `apply()` на каждом старте: открыть БД и выставить pragmas →
  `PRAGMA user_version` → `0` применить v1–v3 → `< LATEST` сделать бэкап
  (WAL-безопасный `backup()`) в `memory.sqlite.bak-v<текущая>` (хранится
  один предыдущий срез), применить недостающие миграции одной транзакцией и
  выставить `user_version = LATEST` внутри неё → `> LATEST` отказать (не
  открывать на запись, логировать, не предоставлять сервис) → `== LATEST`
  no-op. DDL SQLite транзакционен: ошибка → rollback, БД остаётся на старой
  версии.
- Миграция v2 (p10f) — только `CREATE`: таблица `memory_proposals` и её
  индексы, поэтому свежая БД и апгрейд v1→v2 дают идентичную схему. Записи,
  созданные до p10f, миграции не касаются — они уже истина.
  `validateMemorySchema` расширяется проверкой `memory_proposals`, чтобы чужая
  или побитая БД на v2 отсекалась при старте по той же политике отказа.
- Миграция v3 (p10f) — данные, не схема: удаляет накопленные строки
  `status = 'rejected'`, потому что после отказа строки больше не остаётся.
  Миграция идемпотентна (повторный прогон на чистой таблице не находит ничего),
  `accepted` и `proposed` не трогает, схему и индексы `memory_proposals` не
  меняет; свежая БД и апгрейд дают одинаковый результат. Количество удалённых
  строк логируется на уровне `info` без текста предложений.
- Политика отказа: ошибка миграции/открытия не бросается наружу — плагин
  логирует `balbes-memory: ...` и не предоставляет `balbesMemory`. Сервер
  остаётся живым, потребители деградируют как при отсутствии сервиса,
  `Restart=on-failure` не уходит в цикл; данные целы (rollback и `.bak-vN`).
- Восстановление — заменой `memory.sqlite` на `memory.sqlite.bak-vN` при
  остановленном сервисе; переносимость памяти — вместе с `$DSH_HOME`.

### Композиция

- Отдельный пакет `packages/plugins/dsh-balbes-memory` — функциональный
  Cordis-плагин: `name = "balbes-memory"`, `Config` с опциональными
  `dshHome` и `memoryPath`; `inject` не объявляется, сервисы dsh не
  нужны. Дом резолвится как всеми плагинами
  (`config.dshHome ?? $DSH_HOME ?? ~/.dsh`), путь БД —
  `config.memoryPath ?? <home>/storages/memory.sqlite`.
- `apply(ctx, config)`: обеспечить каталог, открыть БД, прогнать миграции,
  `ctx.provide("balbesMemory", service)`, `ctx.effect(() => () => db.close())`
  (HMR-safe, освобождение хэндла). Регистрация — insert-строка `balbes-memory`
  в `profiles/balbes/cordis.patch.yml`; собранный пакет копируется в
  `node_modules` профиля установщиком и CI.
- Типы записи перенесены в `dsh-balbes-contracts` вместе с HTTP-контрактом
  (p10b); плагин реэкспортирует их из `src/types.ts`.

### Поверхность управления (p10b)

- Отдельный плагин `dsh-balbes-memory-admin` (`name = "balbes-memory-admin"`)
  регистрирует три bearer-ручки `/api/memory/list|save|delete` поверх сервиса
  `balbesMemory` (к ним аддитивно добавляются четыре ручки ревью — p10f,
  ниже); контракты ручек — в API_CONTRACTS.md, типы записи — в
  `dsh-balbes-contracts`. Хранилище при этом остаётся headless-фундаментом.
- `inject = ["balbesHttp"]`; сервис `balbesMemory` читается лениво в
  обработчике (`ctx.get`), поэтому плагин применяется независимо от порядка
  загрузки хранилища, а при недоступном хранилище ручки отвечают
  503 `memory-unavailable`, а не исчезают в общий 404.
- Правка владельца: создание из админки принудительно пишет
  `origin: "owner"` (значение из тела игнорируется), правка не меняет `origin`;
  `scope` неизменяем. Разрешение конфликтов «владелец/агент» и признак
  последнего редактора — p10d (пока действует «последняя запись побеждает»).
- Ответы ручек никогда не содержат секретов; `secret-detected` возвращается
  как 400 с тем же кодом, запись не создаётся.
- Экран «Память» в `dsh-balbes-admin` — см. ADMIN_UI.md; проектная память
  правится в контексте проекта, глобальная — в контексте дома.

### Доставка в контекст (p10c)

- Отдельный пакет `packages/plugins/dsh-balbes-memory-context` — функциональный
  плагин `name = "balbes-memory-context"`, `Config = z.object({})`, без `inject`;
  `apply` делает ровно `ctx.provide("balbesMemoryContext", service)`. Сервис
  читает `balbesMemory`/`systemPrompt`/`tools` лениво в scope агента при
  `attach(agentCtx, scope)` и при отсутствии любого из них деградирует в no-op.
- `attach` регистрирует в scope агента: секцию `balbes:memory` (order 120) —
  ядро закреплённых записей и карту; runtime-контекст `balbes:memory-push`
  (order 200) — релевантный push; scoped-инструмент `recall`. Все регистрации
  снимаются вместе с agent-scoped эффектами.
- Режим — гибрид. **Ядро**: только `pinned` дома и текущего проекта, полный
  текст, жёсткий бюджет 4096 символов; не влезшие записи опускаются со счётчиком.
  **Карта**: по строке на запись `[type · origin · scope] #tags preview…`,
  preview ≈ 100 символов, бюджет 4096, остаток — счётчик `… ещё N`.
  **Push**: FTS-bm25 по тексту задачи, scope дом + текущий проект, до 5 записей
  / 2048 символов; записи, уже показанные в ядре, пропускаются.
- Поисковый запрос строит слой: токены `[\p{L}\p{N}_]+` в нижнем регистре,
  длина ≥ 2, дедуп, максимум 24, каждый в кавычках, соединение ` OR `. Сырой
  текст в FTS5 `MATCH` не попадает (p10a передаёт строку verbatim); фраз,
  префиксов и `NEAR` в v1 нет.
- `recall` — scoped `defineTool`, только чтение: параметры `query`
  (required), `type`, `tag`, `pinned`, `limit` (дефолт 10, максимум 20);
  параметра `scope` нет. Вывод — записи с провенансом (`id`, `origin`,
  `originRef`, время, теги). Все чтения фильтруют
  `scopes: [global, currentProject]`, поэтому память чужого проекта недостижима
  структурно. Запись — отдельный инструмент `remember` (p10e, ниже).
- Текст памяти экранируется `{{` → `{ {` (строгая интерполяция промпта).
  Ошибки хранилища/форматирования ловятся: снапшот пустой, ход агента не
  ломается. `prepare` пишет одну `logger.info`-строку со счётчиками (без
  текста памяти).
- Проводка: host `runner.ts` (`/api/prompt`, scope `global`) и Telegram
  `agentTask.ts` (scope из workspace ref) зовут `attach` в agent-scoped
  `setup` и `await prepare(taskText)` перед `followup`.
- Границы: автоизвлечение (p10g), дедуп, TTL и
  конфликты (p10d). Ревью и автономия (p10f) доставку не меняют: предложения
  лежат в другой таблице, и доставка их структурно не видит. HTTP-ручек и UI у
  доставки нет.

### Запись памяти: инструмент `remember` (p10e)

- `remember` — scoped `defineTool` того же пакета
  `dsh-balbes-memory-context`, регистрируется рядом с `recall` в scope агента.
  Параметры: `text` (required), `type` (`fact | preference | decision | note`,
  необязателен, дефолт `note`), `tags` (необязательно). Параметров `scope` и
  `pinned` у инструмента нет: уровень выбирает слой, пиннинг доступен только
  владельцу.
- Запись идёт ровно одним путём — `balbesMemory.save`; обходных путей нет,
  поэтому барьер секретов и валидация p10a действуют и здесь. Провенанс:
  `origin = "agent"`, `originRef = "<channel> session:<sessionId>"` (канал
  `admin` или `telegram`); текст задачи в провенанс не попадает. `pinned`
  всегда `false`.
- Уровень (scope) выбирает слой. В доме (`/api/prompt`) контекст всегда
  `global`, и классификация не зовётся. В проекте (Telegram) один
  вспомогательный LLM-вызов классифицирует факт как `global` (знание о
  владельце или системе в целом) либо `project` (знание конкретного проекта);
  фолбэк при недоступном `llm`/`selection`, ошибке, таймауте или неоднозначном
  ответе — текущий проект; любая неудачная классификация (пустой, непарсимый
  или неоднозначный ответ, ошибка, таймаут) оставляет `warn` в журнале, поэтому
  тихая деградация до текущего проекта наблюдаема. `project` всегда
  разворачивается в имя из замыкания, поэтому запись в чужой проект структурно
  недостижима.
- Классификатор — one-shot вызов `ctx.llm.stream` текущей моделью агента, без
  `sessionId` и `purpose`: вызов не привязывается к сессии агента и не пачкает
  её лог. Бюджет ответа выбран с запасом: промпт требует одно слово, но
  reasoning-модель вправе потратить токены на рассуждение, а обрезанный ответ
  увёл бы каждый проектный факт в проект — то есть тихо отключил бы глобальное
  повышение.
- Деградация: без `save` у `balbesMemory` или без контекста задачи
  (`channel` + `sessionId`) `remember` не регистрируется, `recall` работает;
  отказ `save` (в том числе `secret-detected`) возвращается как tool error, ход
  агента не ломается.
- Согласованность доставки: запись не трогает снапшот текущего хода — доставка
  видит её со следующего `prepare`; немедленная обратная связь агенту — вывод
  самого инструмента (`id`, `scope`, провенанс).
- Проводка: оба канала передают в `attach` контекст задачи — host `runner.ts`
  (`channel = "admin"`, свежий `sessionId` на промпт, selection текущей модели) и
  Telegram `agentTask.ts` (`channel = "telegram"`, эффективный `sessionId`:
  возобновлённый при успешном resume, иначе созданный); scope по-прежнему задаёт
  канал (`home → global`, `project → текущий проект`).
- Наблюдаемость: одна `logger.info`-строка с каналом, выбранным scope и
  признаком того, что классификация дала результат (`classified=true/false`);
  текст памяти не логируется. Метрики пользы — p10h.

### Ревью и автономия записи (p10f)

- Запись, порождённая пайплайном, не становится истиной молча: она живёт
  **предложением** в отдельной таблице `memory_proposals` и промоутится в
  `memories` только решением владельца. Таблица истины остаётся единственным
  источником доставки, поэтому доставка p10c не меняется ни строкой и
  предложение ей структурно не видно: это не фильтр, а другая таблица.
- Жизненный цикл: `proposed → accepted | rejected`, без обратных переходов и
  без TTL. Повторное решение по уже решённому предложению отклоняется
  `invalid-status` (400). **Отказ удаляет строку предложения**: `rejected` — это
  решение, а не состояние в таблице, поэтому отклонённых строк в
  `memory_proposals` не бывает, аудита отказа нет и отменить его нельзя. Принятая
  строка остаётся аудитом (`decided_at`, `decided_by`, `decided_edit`,
  `memory_id`) и лежит в таблице, где `status` — это `proposed` либо `accepted`.
  Удаление отказанной строки снимает и её tombstone: то же знание можно
  предложить заново, потому что дедуп входа (p10g) смотрит только `proposed`.
- Промоушен (`approve`) — одна транзакция: вставка в `memories` с провенансом
  предложившего (`origin = "agent"`, `originRef` из предложения) → теги в
  `memory_tags` → пометка предложения `accepted`; ошибка → rollback, и
  предложение остаётся `proposed`. Это единственный новый путь записи в
  `memories`: он живёт внутри сервиса `balbesMemory` и переиспользует
  нормализаторы, детектор секретов и insert-стейтменты `save`; обходного пути
  нет.
- Правка при одобрении разрешена и меняет только содержание (`type`, `text`,
  `tags`); владелец может закрепить запись (`pinned`), а `origin`/`originRef`
  предложения не меняются. `decided_edit` истинно тогда и только тогда, когда
  патч меняет содержание: патч только с `pinned` и идентичный патч дают ложь,
  считает сервер сравнением нормализованных значений.
- Приоритет владельца: правка и удаление уже принятой записи — обычный путь
  p10b, и ревью они не порождают; предложение пайплайна не перезаписывает
  существующую запись — без дедупа и слияния (p10d) одобрение только добавляет
  новую.
- **Политика автономии** одна и неизменна: явный `remember` (p10e) и правка
  владельца пишут сразу, предложения пайплайна идут через ревью, автоодобрения
  нет. Режима доверия, настроек и переключателей политики не существует;
  `decidedBy` в v1 всегда `owner`. Политика отдаётся владельцу вместе с
  очередью (тип `MemoryAutonomyPolicy`) и рендерится строкой в админке.
- Очередь — FIFO (`proposed_at ASC`): старое предложение не голодает. Фильтры —
  scope, type, tag, status; без `status` отдаются только `proposed`, явный
  `status` показывает решённые (`accepted`; `rejected` в таблице нет); лимиты как
  у `list`. Теги предложения лежат
  JSON-массивом в его строке, теги промоутированной записи — как и раньше в
  `memory_tags`.
- `remember` (p10e) не меняется: явная запись агента по-прежнему идёт прямо в
  `balbesMemory.save`, минуя очередь.
- Поверхность владельца — четыре bearer-ручки в том же плагине
  `dsh-balbes-memory-admin` (`memory.propose`, `memory.review/list|approve|reject`;
  контракты — в API_CONTRACTS.md) и вкладка «Очередь ревью» на странице
  «Память» (ADMIN_UI.md); Telegram не задействован, нового пункта сайдбара нет.
  `propose` — серверный шов пайплайна, и с p10g (ниже) тот же путь доступен
  агенту инструментом `propose_memory` — только на время служебного хода
  извлечения.
- Приватность и деградация: `propose` и правка при `approve` проходят детектор
  секретов (`secret-detected`, ничего не пишется); при недоступном хранилище
  все четыре ручки отвечают 503 `memory-unavailable`, а не 404. Аудит решения
  живёт в данных, наблюдаемость — по одной `logger.info`-строке на мутацию без
  текста памяти.
- Границы: дедупликация, затухание, забывание и конфликты — p10d;
  автоизвлечение — p10g; метрики — p10h; мультиюзерность, роли, несколько
  ревьюеров, история решений, уведомления и решения по предложениям из
  Telegram — вне контура. Правка или удаление предложения без решения не
  предусмотрены: решение — единственный переход.

### Автоизвлечение знания (p10g)

- Место слоя: `dsh-balbes-memory-context` (write-поверхность памяти в scope
  агента) и канал Telegram (`agentTask.ts`), который оркеструет ход. Хранилище
  (p10a), доставка (p10c) и очередь ревью (p10f) не меняются: новых ручек,
  экранов, миграций и типов контрактов нет.
- Триггер — успешная задача, в которой агент работал: `ok`-результат задачи и
  хотя бы один вызов инструмента в её ходе (шаги сводки прогресса). Разговорный
  ход без инструментов, отменённая, сброшенная и упавшая задача извлечения не
  порождают. Cooldown, расписания и явной команды нет — бюджет задаёт сам гейт.
- Служебный ход: слой инициирует второй ход в той же сессии, но **после**
  выдачи ответа владельцу — результат задачи резолвится раньше, ответ не
  задерживается. На время хода агент занят (`busy`), поэтому следующая задача
  воркспейса ждёт в очереди; глубина очереди не меняется.
- Поверхность инструментов переключается: на время служебного хода `remember`
  снимается, `propose_memory` регистрируется, `recall` остаётся. Инвариант: во
  время извлечения у агента нет ни одного инструмента, пишущего в память сразу,
  поэтому пайплайн структурно не может обойти ревью. Поверхность возвращается в
  `finally` и переживает сбой, отмену и сброс.
- Директива служебного хода — фиксированный текст без подстановки задачи и
  ответа, с производительским `kind` (форма `notice`); в просмотре сессий это
  контекстная строка, а не реплика владельца. Текст и ответ служебного хода
  никогда не становятся текстом ответа задачи.
- `propose_memory` — scoped-инструмент: `text` (required), `type`
  (`fact | preference | decision | note`, дефолт `note`), `tags`; параметров
  `scope` и `pinned` нет. Пишет ровно одним путём — `balbesMemory.propose`,
  поэтому валидация p10a и барьер секретов p10f действуют как в ручке
  `memory.propose`; провенанс — `originRef = "<channel> session:<sessionId>"`,
  промоушен даст `origin = "agent"`.
- Уровень выбирает слой по scope задачи (`home` → `global`, проект → текущий
  проект); классификатор уровня (p10e) в служебном ходе не вызывается — это был
  бы второй вызов модели. Чужой проект недостижим структурно.
- Бюджет: не больше трёх предложений за служебный ход (следующий вызов
  инструмента отвечает ошибкой); дубликаты потолок не тратят.
- Дедуп на входе (узкий, best-effort): нормализованный точный текст сверяется с
  записями (дом + текущий проект, ≤ 500) и с ожидающими предложениями тех же
  уровней; совпадение предложения не создаёт. Нечёткое сходство, слияние,
  затухание и конфликты — p10d; сбой чтения индекса дедупа извлечение не
  блокирует (fail-open).
- Приватность: кандидат с секретом отклоняется детектором (`secret-detected`),
  остальные кандидаты хода продолжают обрабатываться; в журнал попадают только
  счётчики и метки канала/уровня; служебный ход видит ту же сессию и тот же
  воркспейс, что задача.
- Наблюдаемость: одна `logger.info`-строка на ход
  (`extraction channel=... scope=... proposed=N duplicate=M secret=K limit=L`),
  `warn` — на сбои; предложения и их `originRef` владелец видит в очереди ревью
  как «предложено пайплайном».
- Деградация: без write-контекста или без хранилища извлечения нет, задача
  работает как раньше; сбой служебного хода не меняет вычисленный результат
  задачи (максимум `warn`), а срыв драйвера трактуется как испорченный агент —
  handle уничтожается и привязка сессии сбрасывается, как при срыве задачи
  (сама сессия остаётся на диске и выбирается в меню).
- Каналы: извлекает только Telegram — там есть задача, воркспейс и живая
  сессия. Шов канало-нейтрален, но `POST /api/prompt` его не вызывает: у
  промпта админки нет воркспейса и переживающей ход сессии.
- Границы: p10d (дедуп накопленного, затухание, конфликты, перенос уровня),
  p10h (метрики), уведомления о предложениях и решения из Telegram,
  автоодобрение и режим доверия — вне контура.

### Метрики попаданий и пользы (p10h)

- Агрегатор живёт в пакете доставки `dsh-balbes-memory-context` (`metrics.ts`):
  чистый in-memory слой без I/O, которому `prepare` отдаёт событие доставки (id
  ядра/карты/push и размеры блоков), а
  инструмент `recall` — событие запроса (исход `ok`/`empty`/`failed`,
  латентность, выданные id). Сервис `balbesMemoryMetrics` предоставляется
  плагином рядом с `balbesMemoryContext`.
- Состав снимка: объёмные счётчики по ходам, каналам (`admin`/`telegram`) и
  тегам scope (`global`/`project:<name>`); per-record попадания за окно
  (`inCore`/`inMap`/`inPush`/`recallDelivered`/`recallQueries`); `recall`
  (calls/empty/failed/латентность); `unqueriedDelivered` и `dropped`.
- Честный счёт ходов: `turns` инкрементится на каждом успешном событии `prepare`,
  включая ход, который не доставил ни одной записи, поэтому `turns=5,
  deliveries=0` — согласованный снимок, а не сбой. `recallDelivered` и
  `recallQueries` численно совпадают: запись, выданная в N вызовах `recall`,
  получает N в обоих счётчиках — уникальный id вызова учитывается по одному разу
  на вызов (семантика «доставлено или выдано recall»).
- Промах наблюдаем двумя честными сигналами: пустой `recall` (пробел в памяти) и
  запись, доставленная в контекст и ни разу не запрошенная за окно (балласт).
  Вердикта «запись не помогла» слой не выносит, текст ответа модели не читает:
  польза выводится владельцем и p10d (затухание по попаданиям) из этих сигналов.
- Окно in-memory: накопительные тоталы за процесс не сбрасываются; уникальных id
  в окне не больше 512, `dropped` (id сверх потолка) тоже ограничен 512, поэтому
  окно отслеживает не больше 1024 различных id; окно закрывается заменой
  структуры. Снимок пишется `logger.info` по интервалу (дефолт 15 минут) и на
  остановке сервиса (shutdown); `prepare` логирует счётчики уровнем `debug`.
- Приватность: в ответе `memory.metrics` — только документированные поля снимка
  (id, тип, scope, канал, время, счётчики и латентность), размеров блоков в снимке
  нет; строка журнала может дополнительно включать размеры блоков и латентность.
  Текст памяти, `originRef`, теги, промпт и ответ модели не попадают ни в ответ,
  ни в журнал.
- Деградация: без собранного сервиса ручка отвечает `503 metrics-unavailable`, а
  доставка работает как раньше; упавший `prepare` не пишет событие доставки и не
  ломает ход; ошибка агрегатора ловится вызывающим, логируется `warn` без текста
  памяти и оставляет метрику без изменения; сверх потолка 512 уникальных id
  растёт `dropped` (тоже не больше 512), а снимок остаётся валидным; сбой
  хранилища в `recall` — это
  `recall.failed` (деградация, а не промах) плюс прежний tool error агенту.
- Граница с p12: p10h владеет только агрегатами памяти в процессе и их снимком;
  персистентность, расширение health, метрики задач, ротация логов и алертинг —
  p12. UI метрик — отдельная инициатива p10i.

### Границы и успех

- Не входят: дедуп/TTL/конфликты
  (p10d), правка и удаление записи агентом (агент только создаёт), векторный
  backend, заполнение `embedding`, мультиюзерность. Сессионная память движка не
  затрагивается.
- Успех: файл `$DSH_HOME/storages/memory.sqlite` создан, `PRAGMA
  user_version` = `LATEST`, сервис `balbesMemory` предоставлен, CRUD и
  FTS-поиск работают, секрет отклоняется с `secret-detected`, после
  close/reopen записи на месте; ручки `/api/memory/*` отвечают по контракту
  и дают владельцу просмотр/правку/удаление из админки; память доставляется —
  pinned-записи видны в системном промпте, push-записи и `recall` доступны
  агенту, чужой проект не возвращается, при недоступном хранилище доставка
  деградирует в no-op; `remember` сохраняет знание с агентским провенансом и
  уровнем, выбранным слоем, а секрет-подобный текст отклоняется без записи;
  предложение пайплайна не видно доставке и становится истиной только после
  одобрения владельцем, а повторное решение отклоняется `invalid-status`;
  успешная задача, в ходе которой агент вызывал инструменты, порождает
  служебный ход извлечения и предложения с провенансом канала и сессии, а
  разговорный ход без инструментов — нет.

## Key flows

- Установка одной командой: `curl -fsSL <raw install.sh> | bash` → окружение →
  клон репо → dsh (версия — единый пин `scripts/engine-version.txt`: если `dsh`
  нет — глобальная установка этой версии; если есть — сверка фактической версии
  `dsh --version` с пином: совпало — info-строка, разошлось — установка
  пинованной версии (`run_priv npm i -g`, sudo только на расхождении) и
  удаление устаревшего зеркала `$DSH_HOME/profiles/node_modules/@deepseek-ai`)
  → сборка workspace (install → link-core → build)
  → синк профиля → копия host → SPA в `$DSH_HOME/balbes/ui` → ключ только из
  env `DEEPSEEK_API_KEY` (без интерактивного запроса; иначе раздел «Модели»
  в админке) → композиция (`--dump-config`) → генерация/печать
  учётных данных админки (один раз) → systemd enable+restart → health
  (ретраи) → сводка. Повторный запуск = обновление репозитория, движка до
  пинованной версии и сервиса (сервис перезапускается, креды не меняются).
- Вход и промпт: браузер `POST /api/auth/login` {login,password} → JWT →
  SPA хранит токен в localStorage и шлёт `Authorization: Bearer`;
  `POST /api/prompt` → сервер через реестр ядра создаёт свежего агента
  (`agents.create`), отправляет промпт (`followup`), ждёт `whenIdle`, делает
  `sessions.flush` (сессия персистится — задел на чат), в `finally`
  `AgentHandle.dispose()` (агент не копится в долгоживущем процессе); ответ —
  финальный текст ассистента.
- Воркспейсы: при старте сервера дом `$DSH_HOME/agent/` обеспечивается
  (`ensureHome`, идемпотентный `mkdir -p`) — дом существует всегда и
  пользователем не удаляется. При первом старте в доме создаются стартовые
  файлы `AGENTS.md`, `self.md` и каталог `skills/` с `README` — только
  отсутствующие; существующие файлы (в т.ч. правки владельца) никогда не
  перезаписываются. `POST /api/workspaces/list` отдаёт дом + скан
  `$DSH_HOME/projects/*` (каталог — источник правды; `createdAt` дополняется
  из реестра-индекса `$DSH_HOME/projects.json`, осиротевшие строки чистятся);
  `create` создаёт каталог проекта (конфликт с существующим → 409),
  идемпотентно кладёт `<project>/.dsh/skills/README` и upsert строки реестра;
  `create-from-git` клонирует GitHub-репозиторий во временный каталог и
  переименовывает его в проект (имя занято → 409; сбой не оставляет проекта и
  записи реестра), дополняя строку реестра `source`; `delete` рекурсивно
  удаляет каталог и чистит строку.
  Владелец правит файлы воркспейсов напрямую — это обычные файлы. Админка
  показывает выбранный воркспейс деревом каталогов/файлов: чтение каталогов —
  scoped-ручки API (границы — корень воркспейса); изменения каталогов извне
  (агент/владелец) приходят в SPA событиями push-канала, дерево инвалидирует
  и перечитывает затронутые узлы.
- Git-доступ и создание из GitHub: владелец в админке задаёт один GitHub-
  токен (`/api/git/save`, ref `BALBES_GITHUB_TOKEN` в
  `$DSH_HOME/.credentials.yaml`; сам токен не возвращается) или сбрасывает
  его. `POST /api/workspaces/create-from-git` `{url, name}` принимает только
  `https://github.com/<owner>/<repo>`: `balbesGit` клонирует полную историю во
  временный каталог, затем `dsh-balbes-workspaces` переименовывает его в
  `$DSH_HOME/projects/<имя>/` и пишет строку реестра с источником; submodules
  и LFS не подтягиваются, таймаут 120 c, при сбое временный каталог
  удаляется. Выбор ветки/тега и синхронизация после создания не входят.
- Глобальный контекст дома (слои global → project): правила
  `$DSH_HOME/agent/AGENTS.md` (user-global) рендерятся первыми, затем
  проектная цепочка `AGENTS.md` от корня проекта к `cwd` — более конкретный
  файл главнее (дедуп по absolutePath исключает двойной рендер); самоописание
  `agent/self.md` подключается секцией `balbes:self` системного промпта
  (order 100); скиллы — project-dsh `<project>/.dsh/skills` (ранг 100), custom
  `agent/skills` (ранг 300), user-dsh `$DSH_HOME/skills` (ранг 400), причём
  проектный скилл с тем же именем затеняет домашний. Файлы дома владелец
  правит напрямую; изменения подхватываются без переустановки (штатные швы
  читают файлы на задаче/скане).
- Telegram: владелец в админке сохраняет token и Telegram user ID через
  `/api/telegram/save`, проверяет `getMe` (`telegram.test`) и включает polling без рестарта.
  Настройки (enabled, allowedUserId) — зарегистрированный settings-namespace `balbes-telegram`; token — ref в `$DSH_HOME/.credentials.yaml`;
  нечувствительное состояние — атомарный `$DSH_HOME/telegram-state.json` (600): active workspace, активная привязка `workspaceRef → sessionId`, архив `archived[workspaceRef]`, последний update offset.
  Плагин принимает только update из private chat от allowlisted user, отдаёт
  inline-список `home`/projects и сохраняет active workspace. Текстовая задача
  проходит в `AgentTaskService`: workspace разрешается по containment, dsh
  agent loop создаётся/возобновляется с `meta.cwd`, сообщение отправляется
  через `followup`, агент ждёт `whenIdle`, session flush-ится, а ответ делится
  на допустимые сообщения Telegram. Сессия закрепляется за воркспейсом как активная: persistent между задачами, возобновляется после рестарта штатным resume,
  задачи одного воркспейса сериализуются (FIFO до 3 ожидающих); прежние сессии не исчезают. `/reset` отсоединяет живой хэндл и очищает активную привязку (начиная новую сессию), `/sessions` показывает сессии активного воркспейса из реестра (канал `telegram`) и возвращает выбранную, а архив скрывает ненужные; `selectSession` отсоединяет текущий хэндл и включает lazy resume выбранной. Ничего не удаляется: реестр append-only, у persistence движка нет удаления.
  Callback файлов лениво читает каталог или
  ограниченное text-содержимое через `balbesWorkspaces`; старые/чужие paths
  повторно валидируются.
  Командная поверхность: `/menu` (`/start`), `/status`, `/ws`, `/model`,
  `/reset`, `/sessions`, `/stop`, `/help`. Команды регистрируются нативными
  ручками Bot API
  (`setMyCommands`, `setChatMenuButton`) на каждом успешном старте polling,
  best-effort и идемпотентно; список команд и роутинг текста берутся из одного
  источника, поэтому не могут разъехаться, а текст, начинающийся со «/», никогда
  не уходит агенту как задача. Карточка-меню — одно редактируемое сообщение с
  активным воркспейсом, текущей моделью, состоянием задачи, очередью и
  действиями (файлы, смена воркспейса, смена модели, сброс контекста,
  остановка, «Обновить»); под-карточки (список воркспейсов, пикер модели,
  подтверждение сброса) имеют возврат в меню.
  Список соединений и их моделей канал берёт из сервиса `balbesModels`, который
  отдаёт плагин моделей (тот же код валидации, что у ручки `/api/models/default`),
  а не читает settings/credentials сам; выбор идёт только индексами снапшота,
  который отрисовал сервер.
  Смена модели меняет глобальный дефолт `agentDefaultModel` — то же значение,
  что в разделе «Модели» админки: раннер канала читает выбор на каждый запрос
  (живой selection), поэтому смена применяется к живой сессии со следующего шага
  без потери контекста; смена посреди turn доигрывает текущий шаг на прежней
  модели, и это штатная семантика движка, а не дефект.
  Сессию не уничтожает ни одна команда: сброс контекста (`/reset`, с
  подтверждением) отсоединяет хэндл и очищает активную привязку, начиная новую
  сессию, а прежняя остаётся в реестре и доступна через `/sessions`; `/stop`
  отменяет активную задачу и очищает очередь через штатный `Agent.cancel` с
  сохранением inbox — sessionId и контекст остаются, следующая задача
  продолжает ту же сессию.
  Ход задачи владелец видит в одной живой карточке прогресса, которая
  обновляется на месте не чаще раза в 3–4 секунды (идентичный текст не
  редактируется) и превращается в квитанцию «готово/остановлено/ошибка».
  В карточку попадают имена инструментов и короткие цели из белого списка полей
  плюс todo-список агента; результаты инструментов и текст ответа модели в неё
  не попадают — карточка информирует о ходе выполнения и не является потоковой
  доставкой ответа (та остаётся отдельным этапом).
  Границы канала: агентская задача получает полную поверхность инструментов
  процесса — ровно то, что регистрирует композиция, как у Web-агента (за вычетом
  reserved `run_code`-транспорта): файлы, shell, skill, subagent/workflow,
  загрузка произвольного URL (`web_fetch`), jobs и управление агентами.
  Отдельного per-agent allow-фильтра и read-guard у канала нет, поэтому задача
  одного проекта может прочитать другой проект или `$DSH_HOME` — это осознанно
  принято решением владельца. Границы — sandbox-политика процесса и approval
  (`DSH_PERMISSION_MODE ?? workspace-write` + `ask`): чтение доступно настолько,
  насколько позволяет ОС, запись ограничена writable-root, а гейтованная операция
  без ответа владельца отклоняется (fail-closed), а не зависает.
  У канала есть свой approval-answerer: слушатель `approval/request`, повешенный
  на scope агента в `setup` (agent-scoped dispatch — тот же, что у
  `agent/request`), принимает approval-запросы только своих агентов. Владельцу
  уходит сообщение с именем инструмента, `reason` и меткой воркспейса и двумя
  inline-кнопками («разрешить один раз» / «отклонить»); исход — штатный
  (`allowed-once` / `rejected` / `cancelled` / `unavailable`), собственной
  семантики канал не изобретает. Нажатие разрешает ровно один конкретный запрос;
  тайм-аут без ответа (константа 5 минут) даёт `rejected`, недоставка вопроса
  владельцу — `unavailable`, `/stop` или abort сигнала инструмента —
  `cancelled`. Pending-запросы живут в памяти и могут висеть параллельно, а живая
  карточка прогресса показывает строку «⏳ ждёт подтверждения: <tool>». Новых
  настроек и ручек нет: approval всегда включён, когда включён канал.
  Поиск (`web_search`) идёт через провайдера DeepSeek тем же ключом, что и раздел
  «Модели».
- Просмотр диалога сессии в админке: клик по строке таба «Сессии» открывает
  динамический таб с `POST /api/sessions/read` `{scope, name?, sessionId}`.
  Плагин сессий проверяет containment по реестру воркспейса, читает полный лог
  движка (`sessionQuery.readSession`) и строит `TranscriptEntry[]`: реплики —
  из durable append-origin событий или не-append событий, оставшихся в текущей
  поверхности (`isAppendSurfaceEvent || inContext`, поэтому заменяющие копии,
  напр. сводка компакции, видны), системный промпт и служебный контекст — из
  текущей модельной поверхности, `inContext` — membership в `foldSurface`;
  шапка — `id`/`createdAt` из движка, `title` из `readTitle`, `channel` из
  записи реестра. Живого обновления нет: загрузка при открытии таба и по общей
  кнопке «Обновить»; табы сбрасываются при смене воркспейса.
- Просмотр файла в админке: клик по листу дерева открывает файловый таб; SPA
  читает содержимое ручкой `workspaces.file` и по расширению пути (для файлов
  без расширения — по shebang) выбирает режим: markdown-документ с
  переключателем «просмотр/исходник», код с подсветкой синтаксиса или
  моноширинный фолбэк. Markdown санитизируется на клиенте — сырой HTML и
  скрипты не исполняются; неизвестный тип безопасно деградирует. Живого
  обновления нет: загрузка при открытии таба и по общей кнопке «Обновить».
- Настройка моделей (раздел «Модели», ручки `/api/models/*`): чтение/
  запись идут штатными сервисами движка — `ctx.settings` (роуты
  провайдеров, settings-секция `llm-pi-ai`), `ctx.credentials` (refs-ключи
  в `$DSH_HOME/.credentials.yaml`, атомарно) и `agentDefaultModel`
  (settings-секция `agent-default-model`; runner читает selection на каждый
  запрос). Эффект — со следующего запроса `/api/prompt`, без рестарта
  сервера; значения ключей не логируются и не возвращаются API.
  Плагин отдаёт список соединений и смену дефолта сервисом `balbesModels`
  (`ctx.provide`), которым пользуется канал Telegram; ручка
  `/api/models/default` и сервис применяют одну и ту же валидацию, поэтому
  админка и чат не могут разойтись.
- Сброс пароля: `scripts/install.sh --reset-admin-password` → новый пароль и
  НОВЫЙ `jwtSecret` записываются атомарно (600); guard читает секрет на каждый
  вызов — выданные токены становятся недействительными сразу, владелец входит
  заново.
- CI: на push/PR валидирует сборку, типы, тесты и композицию профиля без
  ключей и LLM; REAL-тесты (LLM как HTTP-stub, `RUN_REAL=1`) гоняются локально.

## Boundaries & non-responsibilities

- dsh — зависимость, не форк: установленные `@deepseek-ai/*` не редактируются;
  надстройка общается с ядром только через штатные швы (сервисы/события,
  патчи Loader). `dsh-web-app`/`dsh-client-ui-*` и headless в профиль не
  входят (headless — исторический smoke-инструмент этапа 1).
- `@deepseek-ai/*` не тянутся из registry (версии битые): резолв — зеркало
  установленного dsh (линковка в корневой workspace через `link-core` и копия
  host в `node_modules` профиля); pnpm link/абсолютные пути не используются.
- Не входит (следующие этапы): синхронизация git после создания (pull/fetch,
  upstream), выбор ветки/тега/коммита и подкаталог monorepo, submodules и LFS,
  коммиты/push/PR и работа агента с историей git, хостинги кроме GitHub;
  управление сессиями в UI (создание и удаление сессий),
  управление runs/скиллами в UI (ключи/модели —
  раздел «Модели»), HTTPS/TLS и домен, потоковая доставка ответов модели
  (SSE/WS; живая карточка прогресса — индикатор хода задачи, а не она),
  скачивание бинарных файлов через Telegram, другие каналы (A2A),
  память (направление Qdrant; слой p10a — SQLite — описан в Memory layer),
  самообучение, мультиюзерность, замена драйвера цикла,
  граф-конфиг. В самом Telegram-канале не входят: модель на воркспейс или на
  одну задачу (выбирается глобальный дефолт), промежуточные итоги, написанные
  агентом, подтверждения вызова инструментов через чат сверх штатного approval
  (собственных видов гейтов и «разрешить всегда» нет — только one-shot штатного
  шва).
- Секреты не попадают в git; CI работает без ключей; автотесты в модель не
  ходят (R-TEST-1).

## Tech & constraints

- Технологии: dsh (глобально; версия — единый пин `scripts/engine-version.txt`),
  TypeScript (strict, ESM) — наши
  пакеты, bash (установщик), YAML (профиль/патч/CI), React+Vite (SPA),
  GitHub Actions. Без Python.
- Node ≥ 22 (dsh использует `node:sqlite`); Ubuntu + apt; sudo для системного
  Node и глобального dsh.
- Правила API: R-API-1 — все запросы к `/api/*` только POST; ошибки —
  `{error:{code,message}}`; контракты-типы в `dsh-balbes-contracts`
  (+ человекочитаемый реестр — секция API_CONTRACTS.md).
- Воркспейсы: дом — `$DSH_HOME/agent/` (зарезервирован, не удаляется),
  проекты — `$DSH_HOME/projects/<имя>/`; имена проектов — строгий slug
  `[A-Za-z0-9._-]` (без `/`, `..`, пробелов, ведущих/хвостовых точек,
  ≤ 64 симв.); каталог — источник правды, реестр `$DSH_HOME/projects.json`
  (600) — индекс метаданных (атомарная запись tmp+rename).
- Git-доступ: сервер требует установленный `git` в PATH; допустим только
  `https://github.com/<owner>/<repo>`; GitHub-токен — ref
  `BALBES_GITHUB_TOKEN` в `$DSH_HOME/.credentials.yaml`, передаётся git через
  окружение и не попадает в argv/`.git/config`/логи; клон — полная история,
  ветка по умолчанию, таймаут 120 c, без submodules/LFS. Строка реестра
  проекта может нести `source {provider,url,branch,ref}`.
- Глобальный контекст дома: `agent-instructions.dshHome = <home>/agent`
  (override в host-патче с повторением `maxBytes`) даёт user-global правила
  `agent/AGENTS.md`; `skill-filesystem.customSkillDirs =
  [<home>/agent/skills]` — глобальные скиллы. Дом резолвится одинаково всеми
  плагинами: `config.dshHome ?? $DSH_HOME ?? ~/.dsh`.
- Авторизация: пароль — только scrypt-хэш (N=2^17, r=8, p=1) в
  `$DSH_HOME/admin-auth.json` (600, поля login/passwordHash/jwtSecret/
  createdAt); JWT HS256, TTL 24 ч; guard читает файл на каждый verify/issue
  (ротация `jwtSecret` действует без рестарта); rate-limit входа 5/30 мин по IP.
- HTTP без TLS (граница этапа; пароль/токен идут открыто — защита от
  случайных клиентов, TLS — следующий этап); один origin: host раздаёт API и
  SPA; статика — из `$DSH_HOME/balbes/ui` (`BALBES_UI_DIST`).
- systemd-юнит `dsh-balbes`: `Restart=on-failure`, `RestartSec=3`,
  `TimeoutStopSec=20`; hardening: `NoNewPrivileges`, `PrivateTmp`,
  `ProtectSystem=full` + `ReadWritePaths`, `RestrictSUIDSGID`,
  `ProtectKernel*` (без `ProtectHome=read-only`/`SystemCallFilter` — ломают
  тулы агента).
- Telegram: token хранится через `ctx.credentials` в `$DSH_HOME/.credentials.yaml`,
  user ID и enabled — в settings; polling — один loop на процесс, только
  private chat, временные ошибки повторяются с backoff, token не логируется.
  Настройки применяются без рестарта через админку; при отсутствии настроек
  Telegram-плагин не мешает запуску HTTP/API.
- Профиль в репо — источник правды; синхронизация в `$DSH_HOME/profiles/balbes`
  выполняется заменой каталога целиком, после чего в его `node_modules`
  копируется собранный host (порядок: синк → копия).
- Плагины — функциональные: именованные экспорты `name`/`inject`/`Config`/
  `apply` (Cordis вызывает `apply(ctx, config)`); регистрации — эффекты;
  комментарии/код — английские.
