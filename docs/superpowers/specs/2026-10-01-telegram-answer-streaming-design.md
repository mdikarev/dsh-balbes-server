# Потоковая доставка ответа модели в Telegram (p11) — дизайн

- Status: approved design
- Date: 2026-10-01
- Базируется на: `docs/canon/future_plans/p11-answer-streaming.md`,
  `docs/canon/ARCHITECTURE.md` (Telegram-канал, живая карточка прогресса),
  `docs/canon/API_CONTRACTS.md` (`telegram.status`, `telegram.save`),
  `docs/canon/ADMIN_UI.md` (страница «Telegram»), `docs/canon/GLOSSARY.md`,
  спека `2026-09-11-telegram-control-surface-design.md`

## Цель

Сейчас владелец видит ответ модели только целиком: во время задачи обновляется
живая карточка прогресса (ход выполнения), а текст ответа приходит одним или
несколькими финальными сообщениями после `whenIdle()`. Владелец не понимает,
идёт ли генерация и сколько ждать.

p11 добавляет в Telegram-канал потоковую доставку **текста ответа** по мере
генерации: отдельное сообщение растёт, пока модель пишет, и становится первым
чанком точного финального ответа. Карточка прогресса остаётся индикатором хода —
граница «ход выполнения ≠ текст модели» не размывается, а становится
структурной. Агентский цикл dsh не меняется и не обходится: поток читается со
штатного шва движка.

Админка (SPA) в этом заходе поток не получает — только переключатель,
управляющий каналом. Поток в браузер (SSE/WS) остаётся будущим этапом p11.

## Решения и границы

Согласовано с владельцем:

| Вопрос | Решение |
|---|---|
| Объём | Только Telegram-канал; потока в SPA нет. В админке — переключатель канала |
| Форма доставки | Отдельное растущее сообщение-ответ; карточка прогресса не меняется |
| Длинный ответ | В растущем сообщении виден хвост (последние ~3500 символов); в финале сообщение становится первым чанком точного текста, остаток уходит новыми сообщениями |
| Отмена/ошибка | Фрагмент остаётся без пометки и без удаления; квитанция карточки и тексты ошибок — как сейчас |
| Включение | Настройка «Потоковый ответ» на странице «Telegram»: новый контракт, поле статуса/сохранения и UI-переключатель; по умолчанию включено |
| Источник текста | Штатное событие движка `agent/assistant-stream`, только `text-delta` кадры (`reasoning-delta` не показываем) |
| Транспорт до чата | Опрос: новый read раннера + тикер сообщения в `chat.ts` (как у карточки прогресса) |
| Место кода | Пакет `dsh-balbes-telegram` (+ поле в `dsh-balbes-contracts` и переключатель в SPA) |

Границы:

- Установленные `@deepseek-ai/*` не редактируются; поток читается через штатный
  шов событий (`agent/assistant-stream`), второго драйвера цикла не появляется.
- Источник истины финального текста не меняется: durable `assistant/message` и
  `summarizeTurn()`. Поток — предпросмотр; обрыв потока не влияет на доставку
  ответа.
- `TaskProgress` не расширяется текстом: его инвариант «content-free … the
  assistant's text never appears» остаётся в силе, текст живёт в отдельном read.
- Служебный ход извлечения памяти (p10g) в поток не попадает: окно хода
  открывает только ход задачи.
- Кнопок у сообщения потока нет; роутинг колбэков (`liveCards`, «⬅ Меню»,
  «⏹ Стоп»), квитанции и лимиты Bot API не переизобретаются.
- Поток в админку и SSE/WS-канал `workspaces.events` не затрагиваются.
- Мультиюзерность, другие каналы, вложения и медиа — вне scope.

## Архитектура

### Точка съёма сигнала

Движок уже публикует поток ассистента штатно: событие
`agent/assistant-stream` (`@deepseek-ai/dsh-agent`, `runtime-types.d.ts`:
«Process-local assistant-stream publication. Chunk frames are transient; the loop
appends one final v2 `assistant/message` or `assistant/attempt` with the same
stream before a committed end frame»). Кадр — `AssistantStreamFrame`:
`start` / `chunk` / `end`, где `chunk.chunk` — `StreamChunk` из
`@deepseek-ai/dsh-llm` (`text-delta`, `reasoning-delta`, `tool-call-delta`,
`block-start`, `block-end`, `usage`, `finish`).

Потребитель-референс в поставке движка — `dsh-api-session-controller`
(`history.js`): слушает то же событие в `global`-скоупе и отдаёт кадры в
follow-поток. Значит, шов предназначен для live-наблюдения, а не является
внутренней деталью.

Канал подписывается **в scope агента**, а не глобально: слушатель вешается в
`setup(agentCtx, agent)` (`agentTask.ts`, тот же `setup`, что и у `resume`),
ровно как approval-answerer (`approvals.ts`: `agentCtx.on("approval/request", …)`).
Scope-фильтрация движка сама отсекает чужих агентов и субагентов, а слушатель
снимается вместе со scope при `dispose()`. Глобального реестра «агент → буфер» и
сопоставления по идентичности не требуется.

Кадр описывается структурным срезом (пакет не импортирует типы движка — как
везде в репозитории):

```ts
/** Минимальный срез кадра agent/assistant-stream. */
interface AssistantFrameLike {
  type: string;                    // "start" | "chunk" | "end"
  chunk?: { type: string; text?: string };
}
```

### Буфер живого ответа

Новый чистый модуль `packages/plugins/dsh-balbes-telegram/src/answerStream.ts` —
без I/O, без бота, без движка:

```ts
export const LIVE_ANSWER_LIMIT = 8 * 1024;  // сколько символов держит буфер
export const ANSWER_VIEW_LIMIT = 3500;      // сколько символов показывает витрина

export interface LiveAnswer {
  startTurn(): void;                  // открыть окно: очистить и включить приём
  endTurn(): void;                    // закрыть окно: приём выключен, текст очищен
  accept(frame: AssistantFrameLike): void;  // только text-delta открытого окна
  text(): string;                     // накопленный хвост (<= LIVE_ANSWER_LIMIT)
}

export function createLiveAnswer(): LiveAnswer;
/** Хвостовое окно показа: последние `limit` символов. */
export function answerView(text: string, limit?: number): string;
```

Правила:

- принимаются только кадры `type === "chunk"` с `chunk.type === "text-delta"`;
  `reasoning-delta` (канон не показывает рассуждения), `tool-call-delta`
  (имена инструментов уже несёт карточка), `block-start`/`block-end`/`usage`/
  `finish` игнорируются;
- закрытое окно не принимает ничего — дельта служебного хода не может просочиться;
- буфер держит хвост: при превышении `LIVE_ANSWER_LIMIT` старые символы
  отбрасываются, память не растёт вместе с длиной ответа;
- `startTurn()` и `endTurn()` очищают текст — та же дисциплина, что у
  `entry.firstSeq`/`entry.startedAt` («a settled turn has no live state»).

### Окно хода: задача против служебного хода

`agentTask.ts` создаёт буфер на агента в `acquireHandle` (вместе с `handle`) и
хранит его в `entry.liveAnswer`. Окно открывает только ход задачи:

- `executeTurn`: `entry.liveAnswer.startTurn()` рядом с
  `entry.firstSeq = firstSeq` (перед `agent.followup` задачи);
- `startTurn` (внешний, FIFO): `entry.liveAnswer.endTurn()` в `finally` рядом с
  `entry.firstSeq = undefined` — осевший ход не читается, следующий тик не
  подхватывает чужой текст;
- `runExtractionTurn` окно не открывает: дельты служебного p10g-хода
  отбрасываются, хотя он идёт в той же сессии и тем же агентом;
- `cancel()`/`reset()`: `cancel` абортит ход, `whenIdle` резолвится, `finally`
  закрывает окно; `reset` диспозит агент, слушатель снимается вместе со scope.
  Живого текста после остановки не остаётся.

### Read-шов раннера

Новый метод рядом с `progress()` (`TaskProgress` не трогаем):

```ts
export interface LiveAnswerSnapshot {
  phase: "idle" | "running";
  taskText?: string;
  text?: string;
}

export interface AgentTaskRunner {
  // ...
  /** Живой текст хода задачи этой workspace, или idle. Read-only, без I/O. */
  answer(ref: WorkspaceRef): LiveAnswerSnapshot;
}
```

Условие `running` то же, что у `progress()` (`busy && handle && firstSeq`), плюс
открытое окно; `taskText` — `entry.activeText`, чтобы потребитель сверялся со
«своей» задачей ровно как карточка (`progress.taskText !== taskText`). Read
обязан быть свободен от побочных эффектов: чат читает его, пока ход в полёте.

## Жизненный цикл сообщения в чате

### Растущее сообщение

Новый handle `startAnswerStream(chatId, ref, taskText)` в `chat.ts` — по образцу
`startProgressCard` и с теми же дисциплинами:

- сообщение создаётся **лениво, на первой непустой дельте**: ход, состоящий
  только из вызовов инструментов, лишнего сообщения не оставляет;
- у сообщения нет `reply_markup`, поэтому в `liveCards` оно не регистрируется и
  нажатий на нём быть не может — роутинг колбэков не меняется;
- тик: `deps.runner.answer(ref)`; при `phase === "idle"` или
  `taskText !== taskText` своей задачи — выход (чужая или ещё не начатая задача
  не показывается; ожидающая задача молчит до своего хода, как и карточка);
- `answerView(snapshot.text)`; пустая витрина и неизменившийся текст не
  переотправляются;
- правки идут цепочкой `pending`, `idle()` никогда не reject'ит — по тем же
  причинам, что у карточки: финализация обязана дождаться правки «в полёте»;
- счётчик неудачных правок: после `MAX_CARD_EDIT_FAILURES` подряд поток
  замолкает, сообщение не удаляется, задача не страдает (успешная правка
  обнуляет счётчик);
- интервал: `deps.streamIntervalMs`, по умолчанию равен `progressIntervalMs`
  (3500 мс). Два таймера в одном чате дают ≈2 правки на окно, но карточка правит
  только при смене текста (новые шаги), так что фактическая частота ниже; Bot API
  держит порядка одного сообщения в секунду на чат.

### Финализация

В `runTask` после получения результата:

1. `stream.stop(); await stream.idle();` — доставка не обгоняет правку, уже
   ушедшую в сеть (та же причина, что у карточки в `finally`).
2. `chunks = splitMessage(sanitizeReply(result.text))` — существующий путь.
3. `chunks.length === 0`: если сообщение потока есть — `EMPTY_REPLY` не
   отправляется (фрагмент и есть ответ); если потока не было — как сейчас.
4. Сообщение потока есть: правим **его** на `chunks[0]`, `chunks[1..]` уходят
   новыми сообщениями. Дублей нет — сообщение потока становится началом точного
   ответа. Для ответов короче `ANSWER_VIEW_LIMIT` показанный текст совпадает с
   `chunks[0]`, и правка не уходит вовсе.
5. Правка `chunks[0]` не удалась: чанки отправляются новыми сообщениями по
   существующему пути — ответ не теряется никогда; хвост-предпросмотр в чате
   остаётся (осознанный обмен «дубль фрагмента вместо потери ответа»).
6. Сообщения потока нет (быстрый ответ, кадров не было, все правки упали) —
   поведение прежнее, строка в строку.

Для ответов длиннее `ANSWER_VIEW_LIMIT` в финале происходит одна «перемотка»
сообщения с хвоста на начало ответа. Это сознательный компромисс выбранной формы
(хвост всегда живой); альтернатива «не переписывать» даёт дубль хвоста в чате.

### Отмена, ошибка, рестарт

- `cancelled`: сегодня в чат не уходит ничего («the card IS the answer»); теперь в
  чате может остаться фрагмент ответа — это и есть всё новое поведение,
  дополнительных сообщений нет.
- `agent-error`/`queue-full`/`busy`/`workspace-gone`/reset: тексты и квитанции не
  меняются, фрагмент замирает.
- Рестарт сервиса: сообщение просто перестаёт обновляться — как замирает
  карточка; сверять нечего, второй источник истины не заводится.

## Поверхность: настройка «Потоковый ответ»

Полностью по образцу существующего `enabled`:

1. **Config плагина** (`index.ts`): `streamAnswers: z.boolean().default(true).volatile()`
   + зеркало в `telegramSettingsSchema` (`register`-seam старых движков) —
   обе схемы, как уже сделано для `enabled`/`allowedUserId`.
2. **Секция настроек** (`admin.ts`): `TelegramSettingsSection.streamAnswers?: boolean`;
   чтение — `section.streamAnswers ?? true`. Отсутствующий ключ (документ настроек
   старше поля) означает «включено» — та же толерантность, что у `allowedUserId`.
3. **Контракты** (`dsh-balbes-contracts`):
   `TelegramSettingsStatus.streamAnswers: boolean` (в статусе всегда конкретное
   значение), `TelegramSaveRequest.streamAnswers?: boolean` (отсутствует = не
   менять).
4. **Ручки**: `telegram.status` отдаёт поле (внутренний `TelegramStatus` в
   `admin.ts` тоже получает `streamAnswers`, как `enabled`); `telegram.save`
   принимает его, валидирует `typeof === "boolean"` (400
   `invalid-stream-answers`) и пишет патч только при наличии поля. На
   `enabled`-валидацию поле не влияет; R-API-1 не ломается — поля добавляются в
   существующие POST-ручки, новых ручек нет.
5. **Живое чтение**: `ChatDeps.streamAnswers?: () => boolean` — геттер, который
   `runTask` читает **один раз при старте задачи** (тот же приём, что
   `ownerChatId: () => …` в approval-гейте); отсутствие геттера означает
   «включено» (дефолт настройки — `true`). Значение фиксируется на задачу:
   переключение посреди генерации не отрывает уже растущее сообщение.
6. **UI страницы «Telegram»** (`TelegramPage.tsx`): чекбокс «Потоковый ответ»
   рядом с существующими полями, уходит в тот же `TelegramSaveRequest`,
   `data-testid="telegram-stream-answers-input"`.

При выключенной настройке канал ведёт себя ровно как сегодня: сообщение потока не
создаётся, финальная доставка не меняется.

## Деградация и ошибки

| Случай | Поведение |
|---|---|
| Дельт не было / ход без текста | Сообщения потока нет; доставка как сегодня |
| Ошибки `editMessageText` подряд | Поток замолкает после `MAX_CARD_EDIT_FAILURES`, сообщение остаётся, задача идёт |
| Правка финального `chunks[0]` упала | Чанки уходят новыми сообщениями — ответ не теряется |
| Обрыв генерации / ошибка хода | Фрагмент остаётся без пометки, квитанция и текст ошибки как сегодня |
| Служебный ход p10g | В поток не попадает (окно закрыто) |
| Рестарт сервиса | Сообщение замирает; reconcile не нужен |
| Rate limit Bot API | Частота правок ограничена интервалом и правилом «идентичный текст не переотправляется» |

## Тестирование

Юнит (`answerStream`):

- принимаются только `text-delta`; `reasoning-delta`, `tool-call-delta`,
  `block-start`, `block-end`, `usage`, `finish` игнорируются;
- закрытое окно не принимает дельты; `startTurn`/`endTurn` очищают текст;
- буфер держит хвост `LIVE_ANSWER_LIMIT` и не растёт на длинном ответе;
- `answerView` режет по `ANSWER_VIEW_LIMIT` (в том числе короткий текст и границы).

Юнит (`agentTask`):

- `answer(ref)` → `idle` до хода и после хода, `running` с текстом внутри хода;
- текст **служебного** extraction-хода в `answer()` не виден;
- `cancel()`/`reset()` не оставляют живого текста;
- `progress()` не изменился (инвариант «content-free»).

Юнит (`chat`):

- сообщение создаётся только на первой непустой дельте;
- идентичный текст не переотправляется;
- финализация правит сообщение на `chunks[0]` и отправляет остаток новыми;
- при отсутствии потока — прежний путь строка в строку;
- при падении правки чанки уходят новыми сообщениями;
- отмена и ошибка сообщение потока не трогают;
- счётчик неудач глушит поток, но не задачу;
- выключенная настройка не создаёт сообщения.

REAL-композиция (гейт `RUN_REAL=1`, рецепт `agentTask.real.test.ts` + fake Bot
API): стаб-LLM уже отдаёт `content_block_delta`; helper расширяется так, чтобы
текст приходил **несколькими** `text_delta` с паузой. Проверяется: сообщение потока
появилось, обновилось не менее двух раз, финальный текст совпал с точным ответом,
служебный extraction-ход в потоке не виден.

Поверхность настроек: `admin.test.ts` (по умолчанию `true`; отсутствие ключа →
`true`; `save` пишет и возвращает поле; не-boolean → 400 `invalid-stream-answers`),
тест контрактов, `TelegramPage.test.tsx` (переключатель сохраняется и
восстанавливается из статуса), сборка SPA.

## Канон

Изменения вносятся через `canon-write` **до** кода:

- `ARCHITECTURE.md` — Telegram-канал: источник (`agent/assistant-stream`, только
  `text-delta`), окно хода и отсечение служебного хода, буфер и хвостовое окно,
  финализация сообщения первым чанком, фрагмент при отмене/ошибке, настройка
  `streamAnswers`; из Boundaries убирается/переформулируется «потоковая доставка
  ответов модели (SSE/WS)» — потоковая доставка в канале больше не «не входит».
- `GLOSSARY.md` — термин «поток ответа модели (streaming)» и его отличие от
  «живой карточки прогресса» (сейчас там сказано «Это НЕ streaming ответа
  модели» — определение достраивается, а не ломается).
- `OVERVIEW.md` — streaming уходит из out-of-scope, попадает в сигналы успеха.
- `API_CONTRACTS.md` — поля `streamAnswers` у `telegram.status`/`telegram.save`;
  scope-исключения переформулируются: SSE/WS для админки остаются отдельным
  этапом, канал Telegram отдаёт ответ по мере генерации без SSE/WS. Новых ручек
  нет.
- `ADMIN_UI.md` — переключатель «Потоковый ответ» на странице «Telegram».
- `future_plans/p11-answer-streaming.md` + `INDEX.md` (через
  `canon-future-plan`): Telegram-часть поглощается, админская честно остаётся
  будущим этапом, ADMIN_UI уходит из «Absorbs into» этого захода.

Функциональное изменение поверхности канала и админки — `docs/runbooks/stage2-vps.md`
обновляется в том же коммите:

  и что он меняет;

  карточка показывает «остановлено»; выключенный переключатель — сообщение потока
  не появляется;
- выкат обычный: `git pull --ff-only` → `scripts/install.sh` на VPS.
