# Спека MVP: dsh-balbes-server

- Дата: 2026-09-05
- Статус: черновик на ревью
- Тип: продуктовая спека минимального продукта (MVP)

## 1. Цель и позиционирование

**dsh-balbes-server** — серверная дистрибуция DeepSeek Harness на фундаменте
dsh: собственная сборка движка dsh (без форка, без правки ядра), которая
работает на VPS в single-user режиме, не поднимает штатную веб-морду dsh и
предоставляет свою админку.

MVP — первый работающий вертикальный срез продукта: **headless агентский
сервис + своя админка**. Через админку владелец сервера общается с агентом
(чат), видит прошлые сессии и запуски, смотрит каталог скиллов и управляет
ключами моделей.

Долгосрочный вектор развития продукта — самообучаемый агент с долговременной
памятью. Внешний референс этого направления — продукт **Hermes Agent**
(упоминался в обсуждении как ориентир «самообучающегося агента», а не как
имя данного проекта). Память, самообучение и дополнительные каналы — вне
границ MVP и фиксируются здесь только как контекст будущих фаз.

### Ключевые рамки

- dsh используется как есть: движок = зависимость, не форк.
- Всё своё реализуется механизмами dsh: профиль (список бандлов в
  `package.json` → `dsh.profile.bundles`) + слой патчей `cordis.patch.yml`
  + собственные бандлы, подключаемые как `link:`-зависимости
  (проверенный паттерн — `dsh-filetree` в web-профиле).
- Штатная веб-морда dsh (бандлы `dsh-web-app` / `dsh-client-ui-*`) в профиль
  не включается; вместо неё работает наш host-бандл.
- Архитектура закладывает шов «агентский сервис ↔ клиенты»: админка — первый
  канал, будущие мессенджеры (например Telegram) — следующие. Контракт канала
  проектируется сейчас, реализация дополнительных каналов — вне MVP.

## 2. Пользователь и сценарии

Пользователь — один владелец сервера (single-user). Основные сценарии:

1. Войти в админку по HTTPS (простая аутентификация: пароль/токен).
2. Увидеть список прошлых сессий агента и открыть любую для просмотра.
3. Начать новый чат с агентом и получить ответ.
4. Посмотреть запуски (runs) и каталог скиллов.
5. Управлять ключами моделей: добавить, заменить, отключить.
6. Убедиться, что сервис работает как демон на VPS (переживает рестарт).

## 3. Границы MVP

### Входит в MVP (M1)

- Монорепо-дистрибуция в этом репозитории: профиль dsh + наши бандлы +
  админка (`packages/` + `docs/`).
- Профиль dsh, собирающий headless агентский сервис: ядро dsh (агент, сессии,
  LLM, инструменты, скиллы) **без** штатной веб-морды.
- Свой host-бандл: поднимает HTTP/WS API и раздаёт админку; заменяет штатную
  морду, но не трогает агентский цикл ядра.
- Админка: просмотр сессий, чат с агентом, просмотр runs, каталог скиллов,
  управление ключами моделей.
- Простая аутентификация (один пароль/токен) + HTTPS.
- Деплой: сервис работает на VPS (автозапуск, данные dsh в `$DSH_HOME`).

### Не входит в MVP (будущие фазы, пунктиром)

- Долговременная память: индексация завершённых сессий и поиск по ним
  (Qdrant + retrieval-инструмент).
- Самообучение: система пишет себе скиллы (через `skill-filesystem`),
  в перспективе — плагины для себя.
- Дополнительные каналы: мессенджеры (Telegram и др.). Шов под них
  закладывается, реализация — позже.
- Замена драйвера агентского цикла; граф-конфиг поведения.
- Мультиюзерность, аккаунты и роли.
- **Детальный UX-дизайн админки** (экраны, состав панелей, визуальное
  устройство) — вынесен в отдельную сессию, в этой спеке не проектируется.

## 4. Функциональные требования M1

Обозначения приоритетов: P0 — без этого MVP не принимается; P1 — желательно
в M1; P2 — отложено.

### 4.1 Headless агентский сервис

- P0. Профиль dsh запускается на VPS без штатной веб-морды (`dsh-web-app`
  и `dsh-client-ui-*` не загружаются).
- P0. Свой host-бандл поднимает HTTP-сервер с API и раздачей статики админки.
- P0. Агентский цикл и ядро dsh не модифицируются; надстройка общается с
  ядром только через штатные швы (API/события/хранилища dsh).
- P1. Сервис запускается как демон и переживает рестарт VPS (автозапуск).

### 4.2 Сессии

- P0. Админка показывает список сессий агента (реальные данные dsh).
- P0. Открытие сессии показывает её содержимое (ход диалога/задачи).
- P1. Источник данных сессий — штатное хранилище dsh
  (уточняется в спайке, см. раздел 7).

### 4.3 Чат

- P0. Из админки можно начать новую сессию и отправить сообщение агенту.
- P0. Ответ агента возвращается в админку и отображается.
- P1. Потоковая доставка ответа (по мере генерации), если позволяет шов.

### 4.4 Runs

- P0. Админка показывает список запусков (runs) и их статус.
- P1. Открытие запуска показывает его детали (что делал агент/воркфлоу).
- P2. Управление запусками (остановить/повторить) — вне MVP, если не
  получится дёшево через штатный API.

### 4.5 Скиллы

- P0. Админка показывает каталог скиллов из штатного хранилища dsh
  (`skill-filesystem`).
- P1. Просмотр содержимого/описания скилла.
- P2. Редактирование скиллов из админки — вне MVP.

### 4.6 Ключи моделей

- P0. Админка позволяет добавить ключ модели, заменить и отключить.
- P0. Изменения ключей применяются к работающему сервису (горячее применение
  или документированный безопасный рестарт — решает спайк, раздел 7).
- P1. Хранение секретов — в штатном хранилище dsh
  (например `~/.dsh/.credentials.yaml`), не в открытом виде в репозитории.

### 4.7 Аутентификация и транспорт

- P0. Доступ к админке по HTTPS.
- P0. Простая аутентификация: один пароль/токен владельца.
- P1. Защита от перебора/грубых атак (базовая: rate limiting или аналог).

### 4.8 Деплой

- P0. Сервис разворачивается на VPS по документированной процедуре
  (одна команда/runbook).
- P1. HTTPS настроен (обратный прокси или встроенный TLS — решает спайк).
- P1. Обновление дистрибуции — документированный путь (git pull + пересборка
  профиля или аналог).

## 5. Нефункциональные требования

- **Single-user безопасность**: один владелец, секреты не попадают в git,
  админка не открыта без аутентификации.
- **Простота установки/обновления**: runbook для VPS; минимум ручных шагов.
- **Расширяемость**: шов «агентский сервис ↔ клиенты» позволяет добавить
  второй канал (Telegram) без переписывания ядра и админки.
- **Наблюдаемость**: состояние сервиса (запущен/нет, ошибки) видно владельцу
  (логи dsh + статус в админке, P1).
- **Технический стек**: TypeScript (надстройка и админка); без Python.

## 6. Критерии готовности (DoD)

MVP принимается, когда на VPS после документированного деплоя:

1. Профиль dsh запущен как агентский сервис (один процесс dsh-base с нашим
   host-бандлом); штатная веб-морда dsh **не** поднимается (проверяется по
   процессам/портам/логам).
2. Админка доступна по HTTPS, вход — по паролю/токену владельца.
3. В админке виден список реальных сессий dsh; любая сессия открывается
   и показывает содержимое.
4. Через админку можно начать новый чат: сообщение уходит агенту, ответ
   возвращается и отображается.
5. В админке видны runs и каталог скиллов (реальные данные dsh).
6. Ключи моделей добавляются/заменяются/отключаются через админку, и
   изменение применяется (горячо или документированным рестартом).
7. Сервис переживает рестарт VPS (автозапуск работает).
8. Секреты не хранятся в репозитории; аутентификация обязательна для доступа
   к админке.

## 7. Открытые вопросы / спайки

Перед или в начале реализации M1 требуются спайки по реальным механизмам dsh:

1. **Host-бандл**: что переиспользовать из существующих кирпичей
   (`dsh-host-webserver`, `dsh-api-gateway`, `dsh-api-*-controller`) против
   написания своего минимального host (HTTP/WS + статика админки).
2. **Источник данных сессий** для админки: читать ли штатное хранилище
   (`dsh-session-query-sqlite`, `dsh-session-persistence-jsonl`) напрямую
   или через API-контроллеры dsh.
3. **Раздача статики админки**: механизм отдачи фронтенда нашим host-бандлом.
4. **Формат runs**: что именно показывать (запуски агента, `dsh-workflow`
   запуски) и откуда брать статусы.
5. **Применение ключей**: горячее применение через штатные механизмы
   настроек/credentials или документированный рестарт сервиса.
6. **Аутентификация и TLS**: встроенная в host-бандл или обратный прокси
   перед ним.

### Вынесено в отдельную сессию

- **Детальный UX-дизайн админки**: экраны, композиция панелей, визуальное
  устройство, пользовательские сценарии на уровне UI. В этой спеке админка
  определена только функционально (разделы 2 и 4).

## 8. Этап 1 (детально): разворачиваемое ядро dsh-base на сервере

M1 состоит из последовательных этапов; детально проработаны первый (раздел 8)
и второй (раздел 9), границы остальных этапов выделяются в отдельных сессиях
на основании опыта и границ предыдущего. Каждый этап — законченное рабочее
решение с ограниченным функционалом. Пунктирные следующие этапы: сессии/чат и
ключи/runs/скиллы в UI, память, самообучение, каналы (telegram/A2A).

### 8.1 Цель этапа

Заложить **основу для дальнейшего роста**: получить разворачиваемый на VPS
профиль dsh (ядро `dsh-base`) с лёгкой установкой, минимальным CI и
проверяемостью. Результат этапа — готовое решение с ограниченным функционалом:
**сервер с работающим агентским ядром dsh, без UI**.

### 8.2 Модель (зафиксированные решения)

- **Один процесс dsh** (модель B1): ядро + будущие плагины-каналы живут в одном
  Cordis-процессе; никакой оркестрации нескольких процессов.
- **Интеграции — клиенты одного API, а не отдельные хосты.** Штатная морда dsh
  не используется; наш будущий host/API — плагин над dsh-base в этом же
  процессе. Админка = плагины над dsh-base (host: веб-сервер + раздача статики;
  api: роуты управления ключами/сессиями/скиллами/runs; ui: фронтенд).
- **sdk-app не является фундаментом**: его протокол покрывает только диалог
  (initialize / session.prompt / события), а админке нужны сессии, ключи,
  скиллы, runs — доступ к ним даёт прямой плагин в процессе dsh-base.
- **headless — инструмент проверки, а не сервер**: one-shot запуск задачи из
  CLI. В проде не живёт, используется для smoke.

### 8.3 Состав этапа

1. **Монорепо-структура** (`packages/` + `docs/`), профиль dsh как пакет.
2. **Профиль dsh на базе `dsh-base`**: полный стандартный агентский набор
   (агентский цикл, тулы bash/fs/web/workflow/subagent/skill, скиллы, сессии,
   credentials, политики). Штатная веб-морда (`dsh-web-app` / `dsh-client-ui-*`)
   в профиль **не** включается.
3. **Лёгкая развёртка на VPS**: документированный runbook + команда/скрипт
   установки профиля в `$DSH_HOME/profiles`, настройка ключа модели.
4. **Минимальный CI**: валидация конфига профиля и структуры репозитория; без
   реальных LLM-вызовов (нет ключей в CI).
5. **Smoke-проверка** (вручную на сервере, по SSH): запуск задачи через
   headless-CLI и проверка ответа агента.

### 8.4 Границы этапа (не входит)

- Админка, свой host/HTTP-API, sdk-профиль.
- Каналы (telegram, A2A) — только архитектурное решение B1, без реализации.
- Долговременная память (Qdrant), самообучение.
- Полноценный CI с LLM-вызовами.

### 8.5 Критерии готовности этапа

1. По runbook'у профиль разворачивается на VPS (установка + ключ модели).
2. Smoke-задача через headless-CLI реально выполняется агентом с тулами и
   возвращает ответ.
3. Штатная веб-морда dsh не запускается (проверяется по процессам/логам).
4. Минимальный CI проходит (валидация конфига профиля).
5. Секреты не хранятся в репозитории.

## 9. Этап 2 (детально): собственный host + авторизация + админка-срез «одна кнопка»

Этап детализирован в отдельной дизайн-сессии 2026-09-05. Цель — вертикальный
срез всего пути «браузер → авторизация → свой host → ядро dsh → LLM → ответ в
UI», замена headless постоянным host-слоем и превращение профиля в демон.
Результат этапа — готовое решение с ограниченным функционалом: **сервер-демон с
админкой: логин + одна кнопка тестового промпта**.

### 9.1 Модель (зафиксированные решения)

- Один процесс dsh (B1). **Host — Cordis-плагин внутри процесса**; **админка —
  не плагин dsh**, а React SPA (статика), которую host раздаёт браузеру. Связь —
  только HTTP API. Будущие каналы (Telegram и др.) — отдельные плагины в том же
  процессе, клиенты того же API; к админке отношения не имеют.
- **Время жизни процесса (спайк 9.5.1 закрыт):** launcher «оставляет время
  жизни смонтированным плагинам» — `bin.js` делает `await runProfile(...)` и
  ничего не держит: процесс живёт, пока в event loop есть активные хендлы.
  headless выходит сам — вызывает `ctx.appExit` после задачи (one-shot). Наш
  host **не вызывает** `appExit`: процесс держит слушающий HTTP-сервер (сокет =
  хендл event loop); плагин регистрирует `ctx.on("dispose", ...)` и закрывает
  сервер при SIGTERM/SIGINT (systemd stop/restart), которые обрабатывает
  launcher (`interrupt` → dispose фибры). Проверено по коду:
  `dsh/lib/profile-boot-*.js` (`provideCmdline`: `cmdlineArgs`/`appExit`/
  `appReady`) и `@deepseek-ai/dsh-cmdline`.
- **Подход A — свой минимальный host** (`node:http`), без штатных
  host/API-кирпичей: `dsh-host-frontend-static` жёстко требует сервис
  `connection` (архитектура веб-клиента dsh), `dsh-api-*` — typert-RPC под
  клиентскую платформу; отказ от них соответствует спеке. Свой SPA — обычный
  Vite-выхлоп, без `__DSH_BOOT__`/инъекций индекса.
- Профиль `balbes`: `dsh.profile.bundles = ["@deepseek-ai/dsh-base",
  "dsh-balbes-host"]`; **headless удаляется** (два app-слоя конфликтуют за
  `cmdlineArgs`); `code-runtime-worker-thread` и PTC-режим сохраняются (ядро
  тулов, не веб).
- **R-API-1:** все запросы к `/api/*` — **только POST** (исключение — статика
  SPA, это не API). Метод-правило снимает REST-споры и одинаково ложится на
  будущие каналы.
- **Контракты:** пакет `dsh-balbes-contracts` (чистые TS-типы
  `XxxRequest`/`XxxResponse`/`ApiError`, импортируются host'ом и SPA) + реестр
  контрактов в доке по шаблону (method POST, path, auth, request, response,
  errors, notes). В canon контракты попадут через `canon-write` после
  стабилизации.
- **Авторизация:** JWT HS256, `jwtSecret` в `$DSH_HOME/admin-auth.json` (600);
  пароль — только scrypt-хэш, открытый пароль не хранится; печать пароля один
  раз при генерации; сброс — `install.sh --reset-admin-password`. TTL 24 ч;
  блокировка login 5 неудач/30 мин по IP; **каждый** `/api/*`-хендлер кроме
  `login` и `health` требует валидный JWT (401 до бизнес-логики); токен
  stateless, в браузере — localStorage + `Authorization: Bearer`.
- **Транспорт:** HTTP по `http://IP:${BALBES_PORT:-8080}`; TLS/домен —
  отдельным этапом (осознанный риск перехвата на линии, документируется в
  runbook).
- **SPA:** Vite + React + TS (strict), пакет `dsh-balbes-admin`; структура
  `api/auth/pages` на вырост; роутер и дизайн-система — позже (UX-сессия);
  один origin + dev-proxy; vitest.
- **R-TEST-1:** автотесты **не ходят в модель** — fetch в SPA мокается, LLM-
  провайдер в host мокается на границе модели; реальный LLM — только ручной
  smoke на VPS (в CI нет ключей).
- **Демон:** systemd-юнит через install.sh, автозапуск, переживает reboot.
  Артефакт SPA — `$DSH_HOME/balbes/ui` (env `BALBES_UI_DIST`), без привязки к
  путям репо.
- **Дистрибуция:** git-репо — источник правды (модель 1); пакеты держатся
  npm-совместимыми (валидный `package.json`/`exports`/версия), чтобы переход на
  npm-доставку (мета-пакет) был сменой механизма, а не рефакторингом.

### 9.2 Состав этапа

1. Пакеты: `dsh-balbes-host` (бандл с `cordis.patch.yml` + плагины
   `startup`/`server`/`auth`/`api`/`static` — по образцу структуры
   `dsh-headless`), `dsh-balbes-contracts` (типы), `dsh-balbes-admin` (SPA).
2. Профиль `balbes`: base + host; патч host — persona, PTC-режим тулов,
   `code-runtime`.
3. Auth: генерация `admin-auth.json` один раз, `POST /api/auth/login`,
   `POST /api/auth/me`, JWT-middleware, rate-limit, `--reset-admin-password`.
4. API: `/api/health` (публичный), `/api/auth/login` (публичный),
   `/api/auth/me` (JWT), `/api/prompt` (JWT). Prompt повторяет проверенный шов
   headless-раннера: `loader.await()` → `agentDefaultModel.currentSelection()` →
   `agents.create({sessionId: "session-<uuid>", meta:{cwd}, agentOptions,
   setup: installModelSelection})` → `followup(createUserMessage(...))` →
   `whenIdle()` → `sessions.flush()` → текст из событий сессии → JSON.
5. SPA: страницы Login и Main (кнопка «Отправить тестовый промпт», ответ над
   ней); фиксированный промпт («Напиши "ok" и больше ничего»).
6. install.sh: сборка host/SPA/contracts; SPA → `$DSH_HOME/balbes/ui`;
   синхронизация профиля + симлинки наших пакетов в `node_modules` профиля;
   генерация/печать учётных данных; systemd-юнит; health-проверка; печать
   адреса и команд smoke. Обновление = повторный запуск (идемпотентно), пароль
   не перегенерируется. `--reset-admin-password` — отдельный флаг.
7. Runbook этапа 2 (деплой, обновление, сброс пароля, устранение неполадок,
   ufw).
8. CI: typecheck host/SPA/contracts; vitest; `vite build`; композиция профиля
   (`--dump-config`); `bash -n install.sh`. Без ключей и LLM.
9. Реестр контрактов: четыре эндпоинта по шаблону.

### 9.3 Границы этапа (не входит)

- Список сессий, история, чат с удержанием `sessionId` между запросами (на
  запрос создаётся свежий агент; сессии при этом реально персистятся через
  `sessions.flush` — бесплатный задел).
- **Задел на чат (следующий этап), проверено по коду dsh web
  (`dsh-api-session-controller`, `dsh-agent`):** одна сессия = один агент в
  реестре `agents` (`store: Map<sessionId, agent>`). При сообщении в сессию:
  жив агент → reuse (`followup`); живого нет, но сессия на диске →
  `agents.resume({resumeSessionId, agentOptions, setup})`; сессии нет →
  `agents.create({sessionId, ...})`. Контекст диалога живёт между запросами;
  после рестарта агенты resume'ятся по требованию (не грузятся все сразу).
  Наш host вызывает реестр `agents`/`sessions`/`sessionQuery` напрямую — без
  api-контроллеров и typert dsh.
- Ключи/runs/скиллы в UI; HTTPS/TLS; потоковая доставка (SSE/WS); ротация
  пароля (только разовый сброс); мультиюзерность; память (Qdrant);
  самообучение; каналы telegram/A2A; детальный UX-дизайн админки; публикация
  пакетов в npm.

### 9.4 Критерии готовности этапа (DoD)

1. Демон: systemd-юнит активен (`enabled`), переживает reboot VPS.
2. Админка открывается по `http://IP:8080` (или `BALBES_PORT`) — собранный SPA;
   штатная веб-морда не поднята (процессы/порты/логи); в профиле нет
   `dsh-web-app` и headless.
3. Вход логин/паролем из установки; неверный → 401; верный → JWT → кнопка;
   перезагрузка страницы с токеном не требует входа (`/api/auth/me`).
4. Кнопка отправляет тестовый промпт; ответ реальной модели показывается над
   кнопкой.
5. `/api/prompt` и `/api/auth/me` без валидного JWT → 401 (проверено curl'ом
   «из интернета»); health/login открыты.
6. Обновление: повторный `install.sh` обновляет сервис; логин и пароль не
   меняются; данные сессий целы.
7. `--reset-admin-password` выдаёт новый пароль, старый перестаёт работать.
8. Секреты не в git: `admin-auth.json` и `.credentials.yaml` в `$DSH_HOME`
   (600).
9. CI зелёный (см. 9.2.8).
10. Реестр контрактов заполнен; типы `dsh-balbes-contracts` импортируются
    host'ом и SPA.

### 9.5 Спайки (закрыты в дизайн-сессии; точная проводка механизмов — уровень плана)

1. ~~Паттерн «app-слой держит процесс»~~ — **закрыт**: решение в 9.1 «Время
   жизни процесса».
2. ~~Линковка пакетов в профиль~~ — **закрыт**: install.sh собирает host из
   клона репо и копирует собранный пакет **реальным каталогом** в
   `$DSH_HOME/profiles/balbes/node_modules/dsh-balbes-host`; импорты
   `@deepseek-ai/*` резолвятся подъёмом к зеркалу
   `$DSH_HOME/profiles/node_modules` (проверено на этапе 1). Паттерн
   web-профиля (`link:` + pnpm + абсолютные пути, target несёт собственный
   `node_modules`) — dev-механика, для установщика не используется.
3. ~~Сборка на VPS~~ — **закрыт**: host — `pnpm install && pnpm build` (tsc);
   SPA — `pnpm install && vite build` → `$DSH_HOME/balbes/ui`
   (`BALBES_UI_DIST`); билд выполняется до рестарта сервиса — при падении
   install.sh выходит с ошибкой, работающий сервис не трогается; CI повторяет
   ту же рецептуру (зелёный CI ≈ install.sh соберётся).
4. ~~Корневая оркестрация~~ — **закрыт**: root `package.json` +
   `pnpm-workspace.yaml` (`packages: ["packages/*"]`), per-package `scripts`
   + корневые convenience-команды (`pnpm -r --if-present typecheck/test/lint/
   build`); `profiles/*` в workspace **не входят** (деплой-манифесты);
   `@deepseek-ai/*` не тянутся из registry (версии битые) — резолвятся
   bootstrap-линковкой зеркала dsh в корневой `node_modules` (скрипт
   `scripts/link-core`; проводка — в плане).
5. ~~JWT: библиотека vs своя~~ — **закрыт**: собственная HMAC HS256 на
   `node:crypto`: фиксированный header `{alg:"HS256","typ":"JWT"}`; payload
   `{sub,iat,exp}`; base64url; верификация — пересчёт подписи +
   `timingSafeEqual` + проверка `exp`. Ноль зависимостей.
6. ~~scrypt и атомарная запись~~ — **закрыт**: N=2^17, r=8, p=1, keylen=32,
   соль 16 Б, `maxmem` поднят (≈128 МиБ по формуле N·r·128); формат значения
   `scrypt$N$r$p$salt$hash`; запись атомарно: tmp-файл (режим 600) → fsync →
   rename; битый файл при чтении → auth отвечает ошибкой конфигурации.
7. ~~Воспроизводимость шва в тестах~~ — **закрыт**: REAL-композиция
   (тестовый `cordis.yml` через Loader, base + host); LLM мокается **как
   HTTP-эндпоинт**: in-process stub (`node:http`) с canned chat-completion;
   конфиг-строка `llm-deepseek` в тестовом патче указывает endpoint на stub
   (ключ-заглушка), `agent-default-model` → provider `deepseek` + модель.
   Путь агента реальный до провайдерской границы (по коду: дефолтная модель —
   настройки `agent-default-model`, адаптер ходит по HTTP).
8. ~~systemd-hardening~~ — **закрыт**, шаблон юнита:

```ini
[Unit]
Description=dsh-balbes server (agent host + admin API)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=<владелец>
WorkingDirectory=<HOME>
Environment=DSH_HOME=<HOME>/.dsh
Environment=BALBES_PORT=8080
Environment=BALBES_UI_DIST=<HOME>/.dsh/balbes/ui
ExecStart=/usr/local/bin/dsh --profile balbes
Restart=on-failure
RestartSec=3
TimeoutStopSec=20
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ReadWritePaths=<HOME>/.dsh <HOME>
RestrictSUIDSGID=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true

[Install]
WantedBy=multi-user.target
```

   Без `ProtectHome=read-only` и `SystemCallFilter` (ломают тулы агента и
   worker-рантайм — защита, ломающая функцию, не берётся).
