# Спека MVP: dsh-balbes-server

- Дата: 2026-09-05
- Статус: черновик на ревью
- Тип: продуктовая спека минимального продукта (MVP)

## 1. Цель и позиционирование

**dsh-balbes-server** — серверная дистрибуция DeepSeek Harness на фундаменте
dsh: собственная сборка движка dsh (без форка, без правки ядра), которая
работает на VPS в single-user режиме, не поднимает штатную веб-морду dsh и
предоставляет свою админку.

MVP — первый работающий вертикальный срез продукта: **headless агентский
сервис + своя админка**. Через админку владелец сервера общается с агентом
(чат), видит прошлые сессии и запуски, смотрит каталог скиллов и управляет
ключами моделей.

Долгосрочный вектор развития продукта — самообучаемый агент с долговременной
памятью. Внешний референс этого направления — продукт **Hermes Agent**
(упоминался в обсуждении как ориентир «самообучающегося агента», а не как
имя данного проекта). Память, самообучение и дополнительные каналы — вне
границ MVP и фиксируются здесь только как контекст будущих фаз.

### Ключевые рамки

- dsh используется как есть: движок = зависимость, не форк.
- Всё своё реализуется механизмами dsh: профиль (список бандлов в
  `package.json` → `dsh.profile.bundles`) + слой патчей `cordis.patch.yml`
  + собственные бандлы, подключаемые как `link:`-зависимости
  (проверенный паттерн — `dsh-filetree` в web-профиле).
- Штатная веб-морда dsh (бандлы `dsh-web-app` / `dsh-client-ui-*`) в профиль
  не включается; вместо неё работает наш host-бандл.
- Архитектура закладывает шов «агентский сервис ↔ клиенты»: админка — первый
  канал, будущие мессенджеры (например Telegram) — следующие. Контракт канала
  проектируется сейчас, реализация дополнительных каналов — вне MVP.

## 2. Пользователь и сценарии

Пользователь — один владелец сервера (single-user). Основные сценарии:

1. Войти в админку по HTTPS (простая аутентификация: пароль/токен).
2. Увидеть список прошлых сессий агента и открыть любую для просмотра.
3. Начать новый чат с агентом и получить ответ.
4. Посмотреть запуски (runs) и каталог скиллов.
5. Управлять ключами моделей: добавить, заменить, отключить.
6. Убедиться, что сервис работает как демон на VPS (переживает рестарт).

## 3. Границы MVP

### Входит в MVP (M1)

- Монорепо-дистрибуция в этом репозитории: профиль dsh + наши бандлы +
  админка (`packages/` + `docs/`).
- Профиль dsh, собирающий headless агентский сервис: ядро dsh (агент, сессии,
  LLM, инструменты, скиллы) **без** штатной веб-морды.
- Свой host-бандл: поднимает HTTP/WS API и раздаёт админку; заменяет штатную
  морду, но не трогает агентский цикл ядра.
- Админка: просмотр сессий, чат с агентом, просмотр runs, каталог скиллов,
  управление ключами моделей.
- Простая аутентификация (один пароль/токен) + HTTPS.
- Деплой: сервис работает на VPS (автозапуск, данные dsh в `$DSH_HOME`).

### Не входит в MVP (будущие фазы, пунктиром)

- Долговременная память: индексация завершённых сессий и поиск по ним
  (Qdrant + retrieval-инструмент).
- Самообучение: система пишет себе скиллы (через `skill-filesystem`),
  в перспективе — плагины для себя.
- Дополнительные каналы: мессенджеры (Telegram и др.). Шов под них
  закладывается, реализация — позже.
- Замена драйвера агентского цикла; граф-конфиг поведения.
- Мультиюзерность, аккаунты и роли.
- **Детальный UX-дизайн админки** (экраны, состав панелей, визуальное
  устройство) — вынесен в отдельную сессию, в этой спеке не проектируется.

## 4. Функциональные требования M1

Обозначения приоритетов: P0 — без этого MVP не принимается; P1 — желательно
в M1; P2 — отложено.

### 4.1 Headless агентский сервис

- P0. Профиль dsh запускается на VPS без штатной веб-морды (`dsh-web-app`
  и `dsh-client-ui-*` не загружаются).
- P0. Свой host-бандл поднимает HTTP-сервер с API и раздачей статики админки.
- P0. Агентский цикл и ядро dsh не модифицируются; надстройка общается с
  ядром только через штатные швы (API/события/хранилища dsh).
- P1. Сервис запускается как демон и переживает рестарт VPS (автозапуск).

### 4.2 Сессии

- P0. Админка показывает список сессий агента (реальные данные dsh).
- P0. Открытие сессии показывает её содержимое (ход диалога/задачи).
- P1. Источник данных сессий — штатное хранилище dsh
  (уточняется в спайке, см. раздел 7).

### 4.3 Чат

- P0. Из админки можно начать новую сессию и отправить сообщение агенту.
- P0. Ответ агента возвращается в админку и отображается.
- P1. Потоковая доставка ответа (по мере генерации), если позволяет шов.

### 4.4 Runs

- P0. Админка показывает список запусков (runs) и их статус.
- P1. Открытие запуска показывает его детали (что делал агент/воркфлоу).
- P2. Управление запусками (остановить/повторить) — вне MVP, если не
  получится дёшево через штатный API.

### 4.5 Скиллы

- P0. Админка показывает каталог скиллов из штатного хранилища dsh
  (`skill-filesystem`).
- P1. Просмотр содержимого/описания скилла.
- P2. Редактирование скиллов из админки — вне MVP.

### 4.6 Ключи моделей

- P0. Админка позволяет добавить ключ модели, заменить и отключить.
- P0. Изменения ключей применяются к работающему сервису (горячее применение
  или документированный безопасный рестарт — решает спайк, раздел 7).
- P1. Хранение секретов — в штатном хранилище dsh
  (например `~/.dsh/.credentials.yaml`), не в открытом виде в репозитории.

### 4.7 Аутентификация и транспорт

- P0. Доступ к админке по HTTPS.
- P0. Простая аутентификация: один пароль/токен владельца.
- P1. Защита от перебора/грубых атак (базовая: rate limiting или аналог).

### 4.8 Деплой

- P0. Сервис разворачивается на VPS по документированной процедуре
  (одна команда/runbook).
- P1. HTTPS настроен (обратный прокси или встроенный TLS — решает спайк).
- P1. Обновление дистрибуции — документированный путь (git pull + пересборка
  профиля или аналог).

## 5. Нефункциональные требования

- **Single-user безопасность**: один владелец, секреты не попадают в git,
  админка не открыта без аутентификации.
- **Простота установки/обновления**: runbook для VPS; минимум ручных шагов.
- **Расширяемость**: шов «агентский сервис ↔ клиенты» позволяет добавить
  второй канал (Telegram) без переписывания ядра и админки.
- **Наблюдаемость**: состояние сервиса (запущен/нет, ошибки) видно владельцу
  (логи dsh + статус в админке, P1).
- **Технический стек**: TypeScript (надстройка и админка); без Python.

## 6. Критерии готовности (DoD)

MVP принимается, когда на VPS после документированного деплоя:

1. Профиль dsh запущен как агентский сервис (один процесс dsh-base с нашим
   host-бандлом); штатная веб-морда dsh **не** поднимается (проверяется по
   процессам/портам/логам).
2. Админка доступна по HTTPS, вход — по паролю/токену владельца.
3. В админке виден список реальных сессий dsh; любая сессия открывается
   и показывает содержимое.
4. Через админку можно начать новый чат: сообщение уходит агенту, ответ
   возвращается и отображается.
5. В админке видны runs и каталог скиллов (реальные данные dsh).
6. Ключи моделей добавляются/заменяются/отключаются через админку, и
   изменение применяется (горячо или документированным рестартом).
7. Сервис переживает рестарт VPS (автозапуск работает).
8. Секреты не хранятся в репозитории; аутентификация обязательна для доступа
   к админке.

## 7. Открытые вопросы / спайки

Перед или в начале реализации M1 требуются спайки по реальным механизмам dsh:

1. **Host-бандл**: что переиспользовать из существующих кирпичей
   (`dsh-host-webserver`, `dsh-api-gateway`, `dsh-api-*-controller`) против
   написания своего минимального host (HTTP/WS + статика админки).
2. **Источник данных сессий** для админки: читать ли штатное хранилище
   (`dsh-session-query-sqlite`, `dsh-session-persistence-jsonl`) напрямую
   или через API-контроллеры dsh.
3. **Раздача статики админки**: механизм отдачи фронтенда нашим host-бандлом.
4. **Формат runs**: что именно показывать (запуски агента, `dsh-workflow`
   запуски) и откуда брать статусы.
5. **Применение ключей**: горячее применение через штатные механизмы
   настроек/credentials или документированный рестарт сервиса.
6. **Аутентификация и TLS**: встроенная в host-бандл или обратный прокси
   перед ним.

### Вынесено в отдельную сессию

- **Детальный UX-дизайн админки**: экраны, композиция панелей, визуальное
  устройство, пользовательские сценарии на уровне UI. В этой спеке админка
  определена только функционально (разделы 2 и 4).

## 8. Этап 1 (детально): разворачиваемое ядро dsh-base на сервере

M1 состоит из последовательных этапов; детально проработан только первый,
границы остальных этапов выделяются в отдельных сессиях на основании опыта и
границ предыдущего. Каждый этап — законченное рабочее решение с ограниченным
функционалом. Пунктирные следующие этапы: админка (host + api + ui-плагины над
dsh-base), память, самообучение, каналы (telegram/A2A), ключи/runs/скиллы в UI.

### 8.1 Цель этапа

Заложить **основу для дальнейшего роста**: получить разворачиваемый на VPS
профиль dsh (ядро `dsh-base`) с лёгкой установкой, минимальным CI и
проверяемостью. Результат этапа — готовое решение с ограниченным функционалом:
**сервер с работающим агентским ядром dsh, без UI**.

### 8.2 Модель (зафиксированные решения)

- **Один процесс dsh** (модель B1): ядро + будущие плагины-каналы живут в одном
  Cordis-процессе; никакой оркестрации нескольких процессов.
- **Интеграции — клиенты одного API, а не отдельные хосты.** Штатная морда dsh
  не используется; наш будущий host/API — плагин над dsh-base в этом же
  процессе. Админка = плагины над dsh-base (host: веб-сервер + раздача статики;
  api: роуты управления ключами/сессиями/скиллами/runs; ui: фронтенд).
- **sdk-app не является фундаментом**: его протокол покрывает только диалог
  (initialize / session.prompt / события), а админке нужны сессии, ключи,
  скиллы, runs — доступ к ним даёт прямой плагин в процессе dsh-base.
- **headless — инструмент проверки, а не сервер**: one-shot запуск задачи из
  CLI. В проде не живёт, используется для smoke.

### 8.3 Состав этапа

1. **Монорепо-структура** (`packages/` + `docs/`), профиль dsh как пакет.
2. **Профиль dsh на базе `dsh-base`**: полный стандартный агентский набор
   (агентский цикл, тулы bash/fs/web/workflow/subagent/skill, скиллы, сессии,
   credentials, политики). Штатная веб-морда (`dsh-web-app` / `dsh-client-ui-*`)
   в профиль **не** включается.
3. **Лёгкая развёртка на VPS**: документированный runbook + команда/скрипт
   установки профиля в `$DSH_HOME/profiles`, настройка ключа модели.
4. **Минимальный CI**: валидация конфига профиля и структуры репозитория; без
   реальных LLM-вызовов (нет ключей в CI).
5. **Smoke-проверка** (вручную на сервере, по SSH): запуск задачи через
   headless-CLI и проверка ответа агента.

### 8.4 Границы этапа (не входит)

- Админка, свой host/HTTP-API, sdk-профиль.
- Каналы (telegram, A2A) — только архитектурное решение B1, без реализации.
- Долговременная память (Qdrant), самообучение.
- Полноценный CI с LLM-вызовами.

### 8.5 Критерии готовности этапа

1. По runbook'у профиль разворачивается на VPS (установка + ключ модели).
2. Smoke-задача через headless-CLI реально выполняется агентом с тулами и
   возвращает ответ.
3. Штатная веб-морда dsh не запускается (проверяется по процессам/логам).
4. Минимальный CI проходит (валидация конфига профиля).
5. Секреты не хранятся в репозитории.

## Связанные артефакты

- Дизайн-обсуждение и зафиксированные решения M1 — в истории этой сессии
  (выборы: walking skeleton; свой host-бандл вместо штатной морды;
  headless agent-сервис + клиенты; простая аутентификация; монорепо =
  дистрибуция; дорожная карта детально только для M1; Этап 1 = разворачиваемое
  ядро dsh-base на сервере с минимальным CI и лёгким деплоем).
- Модель сервера: один процесс dsh (B1), интеграции — бандлы-клиенты единого
  API; sdk-app и headless не являются фундаментом сервера (проверено по коду
  dsh: `dsh-sdk-protocol` покрывает только диалог; `dsh-headless` — one-shot).
- Canon-документация `docs/canon/` — наполняется позже, при появлении
  стабильных поведенческих контрактов (по правилу canon-first).
