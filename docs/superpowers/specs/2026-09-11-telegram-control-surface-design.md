# Управляющая поверхность Telegram-канала — дизайн

- Status: draft design (на ревью владельца)
- Date: 2026-09-11
- Базируется на: `docs/superpowers/specs/2026-09-10-telegram-integration-design.md`

## Цель

Владелец, работая в Telegram, должен в любой момент диалога уметь:

1. вызвать меню (сегодня — только кнопка в первом сообщении, дальше её не найти);
2. сменить воркспейс посреди диалога;
3. обнулить контекст;
4. сменить модель, не заходя в админку;
5. видеть промежуточный ход задачи (сейчас — «Задача принята…» и тишина);
6. остановить затянувшуюся задачу, **не теряя контекст**.

Сегодня: команды бота в Telegram не зарегистрированы вообще; панель действий
отправляется отдельным сообщением и уезжает вверх по мере задач; задача
запускается с моделью, замороженной при создании сессии; прогресса нет;
единственный способ остановить задачу — «Сбросить контекст», который
уничтожает сессию вместе с контекстом.

## Решения и границы

Согласовано с владельцем:

| Вопрос | Решение |
|---|---|
| Как вызывается меню | Нативные команды Telegram (`setMyCommands` + `setChatMenuButton`) и карточка-меню |
| Уровень выбора модели | Глобальный дефолт `agentDefaultModel` — тот же, что и в разделе «Модели» админки |
| Промежуточные итоги | Одна живая карточка, редактируемая на месте (не отдельные сообщения) |
| Остановка задачи | `/stop`: отмена активной задачи + очистка очереди, контекст сессии сохраняется |

Следствия, зафиксированные как границы:

- Модель **на воркспейс** и модель **на одну задачу** не входят.
- Потоковая выдача текста ответа (streaming как таковой) не входит — канон
  (`API_CONTRACTS.md`, `ARCHITECTURE.md`, `OVERVIEW.md`) продолжает относить
  её к следующему этапу. Карточка прогресса — не streaming: она показывает
  ход выполнения задачи, а не текст ответа модели по мере генерации.
- Связные итоги, сформулированные агентом, не входят.
- Единственная операция, уничтожающая сессию, — «Сбросить контекст»
  (остаётся с подтверждением). `/stop` сессию не трогает.
- Новых HTTP-ручек не появляется: всё новое — внутриканальное (Cordis-сервисы,
  события сессии, Bot API).

## Архитектура

### Раннер задач (`packages/plugins/dsh-balbes-telegram/src/agentTask.ts`)

Три узких добавления к `AgentTaskRunner`.

**1. Живой выбор модели.** Сейчас `acquireHandle` создаёт
`{ current: selection, assembled: undefined }` и замораживает выбор на всю
жизнь сессии, поэтому смена дефолта не долетает до уже созданной сессии.
Станет ref с геттером на `deps.defaultModel.currentSelection()`
(`{ get current() { … }, assembled: undefined }`), установленный в `setup` при
create/resume — ровно так это делает штатный
`@deepseek-ai/dsh-api-session-controller` (`selectionFor`).
`agentOptions` при create/resume по-прежнему получает конкретную пару
(`provider`, `model`) — движок требует её в момент вызова, — а на каждый
следующий запрос выбор читается заново, и waterfall-слушатель
`installModelSelection` подставляет его в `agent/request`.

Эффект: смена дефолта — из Telegram или из админки — применяется к живой
сессии со следующего шага, контекст и sessionId сохраняются. Смена модели
посреди turn доигрывает текущий шаг на прежней модели: это штатная семантика
движка («takes effect on a later step»), она документируется, а не лечится.

**2. `cancel(ref): Promise<{ cancelled: boolean; dropped: number }>`.**
Ставит на запись флаг `cancelled` (мягкий аналог существующего `retired` от
reset), очищает очередь, резолвя каждую ожидающую задачу как
`{ ok: false, code: "cancelled" }`, и вызывает
`agent.cancel({ kind: "user" }, { keepInbox: true })` — штатный шов движка
(`Agent.cancel`, `CancelOptions.keepInbox`: «the active turn is still aborted»).
Хэндл **не** уничтожается, sessionId не меняется, следующая задача продолжает
ту же сессию. `dispose()` остаётся только у `reset()`.

Причина отмены доезжает до лога сессии как `turn/end` с
`reason.kind === "aborted"` и `reason.reason.kind === "user"`. Благодаря этому
происхождение остановки различается **кодом результата**, а не текстом, и
существующее сопоставление по точным фразам (`RESET_ABORT_PHRASES`) удаляется
вместе с зеркальными константами в чате: сейчас корректность распознавания
«сброс, а не падение агента» держится на совпадении строк.

**3. `snapshot(ref)`** — read-only сводка для карточки прогресса:
`{ phase: "idle" | "running" | "queued"; taskText?: string; startedAt?: number;
steps: Array<{ name: string; target?: string; status: "running" | "ok" | "failed" }>;
todos?: Array<{ text: string; status: "pending" | "in_progress" | "done" }>;
queued: number }`. Собирается чистой функцией-суммаризатором над срезом лога
сессии текущего turn (`tool/call`, `tool/result`, `todo/write`, `step/start`) —
рядом с существующим `summarizeTurn` и в том же стиле. Никакого I/O, никаких
новых подписок.

Реализация карточки — **опрос** `snapshot()` из чата (таймер на выполняющуюся
задачу), а не подписка на `ctx.on("session/event")`. Причина: карточка всё
равно троттлится до 3–4 секунд, поэтому событийный firehose не даёт видимой
пользы, но приносит scope-фильтры, карту «сессия → карточка» и
недетерминированные тесты. Если понадобятся мгновенные переходы
«в очереди → выполняется», подписка добавляется отдельным шагом.

`TaskResult` получает код `cancelled`; существующие коды не меняются.

### Сервис моделей (`packages/plugins/dsh-balbes-models`)

Перечисление соединений и их моделей сегодня существует только внутри
HTTP-ручек (`readConnections` в `src/index.ts`), а Telegram-плагину нужен тот
же список в процессе. Дублировать чтение `llm-pi-ai` + `credentials` нельзя —
разъедется.

Новый `src/service.ts`: `createModelsService({ settings, credentials, defaultModel, reader })`
с `list(): Promise<ModelConnection[]>`, `current(): { provider, model }` и
`saveDefault(provider, model): Promise<void>` (та же проверка «модель
предложена этим соединением», что сегодня в `/api/models/default`).
Плагин отдаёт сервис через `ctx.provide("balbesModels", …)` — репозиторный
паттерн `balbesWorkspaces` (`packages/plugins/dsh-balbes-workspaces/src/index.ts`),
а ручка `/api/models/default` начинает переиспользовать `saveDefault`, чтобы
админка и Telegram ходили через одну валидацию.

`dsh-balbes-telegram` добавляет `balbesModels` в `inject`; отсутствие сервиса
(профиль собран без моделей) — деградация: `/model` отвечает «Раздел моделей
недоступен», бот продолжает работать.

### Bot API (`packages/plugins/dsh-balbes-telegram/src/bot.ts`)

Два новых метода клиента:

- `setMyCommands(commands: Array<{ command: string; description: string }>)`;
- `setChatMenuButton({ type: "commands" })` — явный пин нативной кнопки «Меню».

Список команд — единый источник: описания для `setMyCommands` берутся из той
же таблицы, из которой работает роутинг текста (`commands.ts`), чтобы список в
Telegram и поведение бота не могли разъехаться.

Регистрация — на каждом успешном старте polling и после смены токена,
идемпотентно и best-effort: сбой логируется предупреждением и не влияет на
polling. Фейковый Bot API в тестах отвечает на оба метода.

### Разделение модулей Telegram-плагина

`chat.ts` — 907 строк, тесты — 1207; четыре новые фичи в нём дали бы файл на
1400+ строк с четырьмя смешанными ответственностями. Разделение:

- `commands.ts` — таблица «команда → описание → обработчик», роутинг текста,
  обработка неизвестной команды;
- `cards.ts` — чистые билдеры пар «текст + клавиатура» (меню, статус, список
  соединений, список моделей, подтверждение сброса, квитанции), собранные из
  примитивов существующего `keyboards.ts`;
- `chat.ts` — состояние: снапшоты отрисованных вьюх, рендер, диспетчер
  callback-кодов, запуск задачи, таймер карточки прогресса, квитанции;
- `keyboards.ts` — без изменений в роли (чистые примитивы кнопок);
- `index.ts` — проводка: `balbesModels` в deps, регистрация команд на
  transition, передача `defaultModel`/`cancel` в раннер.

Новых видов снапшотов два — `modelConnections` и `modelList`; они
переиспользуют существующий LRU-предел на 64 записи и правило «снапшот
привязан к чату».

### Протокол callback-кодов

Новые коды (payload остаётся далеко ниже лимита Telegram в 64 символа):

```text
mnu                    карточка-меню
mnu:refresh            перерисовать карточку (кнопка «Обновить»)
mdl                    карточка модели: текущая + список соединений
mdl:c:<i>              i-е соединение из последнего отрисованного списка
mdl:pg:<n>             страница списка моделей соединения
mdl:m:<i>              i-я модель из последнего отрисованного списка
mdl:back               назад к списку соединений
stp                    остановить активную задачу и очистить очередь
```

Существующие коды (`ws`, `ws:pg:*`, `ws:pick:*`, `act:*`, `reset:yes|no`,
`e:*`, `up`, `pg:*`) не меняются — старые сообщения в истории чата продолжают
работать. Неизвестный или устаревший код — как сейчас, «Действие устарело»,
без обращения к диску.

## Состояние

`$DSH_HOME/telegram-state.json` **не меняется**: модель глобальная, новый
персистентный ключ не нужен, `version` остаётся `1`, миграции нет. Восстановление
на старте (`restoreTelegramBoot`) не трогается. В памяти, как и раньше,
остаются активный воркспейс, хэндлы агентов и снапшоты отрисованных вьюх.

## Telegram UX

### Команды

| Команда | Действие |
|---|---|
| `/start`, `/menu` | карточка-меню |
| `/status` | карточка-меню с расширенной строкой состояния |
| `/ws` | список воркспейсов (уже работает) |
| `/model` | пикер модели: соединение → модель |
| `/reset` | сброс контекста с подтверждением (уже работает кнопкой) |
| `/stop` | отмена активной задачи + очистка очереди, контекст сохраняется |
| `/help` | короткая текстовая справка |

Инварианты, которые сохраняются:

- команда обрабатывается только после `isAuthorized` (private chat +
  allowlisted user ID);
- текст, начинающийся с «/», **никогда** не уходит агенту как задача;
- неизвестная команда (`/foo`) отвечает «Не знаю такой команды» и показывает
  карточку-меню.

### Карточка-меню

```text
🤖 Агент сервера

Воркспейс: Проект: balbes
Модель: deepseek-v4-pro · deepseek-official
Задача: выполняется · 2:14 · шаг 5
Очередь: 1

[ 📄 Файлы ]      [ 🧠 Модель ]
[ 📁 Воркспейс ]  [ 🔄 Сбросить контекст ]
[ ⏹ Стоп ]        [ 🔄 Обновить ]
```

- Строка «Задача» при простое — «нет активной задачи»; строка «Очередь»
  появляется только когда очередь непуста.
- «Обновить» перерисовывает карточку: она снапшот, а состояние живое.
- «Стоп» при простое отвечает всплывающим «Сейчас ничего не выполняется» и не
  плодит сообщений.
- Нет активного воркспейса — карточка показывает подсказку и кнопку
  «Воркспейсы» вместо «Файлы».
- Под-карточки (список воркспейсов, пикер модели, подтверждение сброса)
  получают строку «⬅ Меню»: из любого места чата до меню два тапа, плюс
  `/menu` в любой момент.

### Пикер модели

`/model` → карточка «Модель сейчас: …» + кнопки соединений из `balbesModels`
(у соединения без ключа — подпись «нет ключа»; нажатие отвечает «Ключ не
задан — добавьте в админке») → список моделей соединения с пагинацией
(8 в странице, как в существующих списках) → выбор модели →
`saveDefault(provider, model)` → карточка «Модель: …» с «⬅ Меню».

Правила:

- Выбор идёт **только** индексами в снапшоте, который отрисовал сервер; строки
  `provider`/`model` из callback никогда не принимаются (как в выборе
  воркспейса).
- `saveDefault` валидирует, что модель предложена именно этим соединением.
- Карточка честно пишет, что смена применится со следующего шага, и что
  текущий шаг доигрывается на прежней модели.
- В админке после смены видно то же значение — это одна и та же настройка.

### Карточка прогресса задачи

Заменяет нынешнее «Задача принята…».

```text
⏳ Проект: balbes · 1:12 · шаг 4

☑ Разобрать логи
☐ Починить парсер
☐ Прогнать тесты

🔧 read notes.txt ✔
🔧 grep "TODO" ✔
🔧 edit notes.txt …

[ ⏹ Стоп ]  [ ⬅ Меню ]
```

Правила рендера:

- обновление не чаще раза в 3–4 секунды; идентичный текст не редактируется
  (иначе Telegram отвечает «message is not modified»);
- показываются имя инструмента и **короткая безопасная цель** — только из
  белого списка полей (`file_path`, `path`, `pattern`, `query`), с обрезкой и
  схлопыванием переводов строк;
- **результаты инструментов и текст ответа модели в карточку не попадают** —
  иначе в чат поедут куски файлов и шум;
- todo-список берётся из события `todo/write` и показывается, только если агент
  его заполнил;
- задачи в очереди видны: карточка новой задачи сразу пишет «🕓 в очереди №2» и
  превращается в живую, когда доходит ход;
- в карточке показываются последние 5 шагов, чтобы она не росла.

Финал: карточка превращается в квитанцию — `✅ Готово · 1:40 · 6 шагов`,
`⏹ Остановлено владельцем`, `⏹ Остановлено сбросом контекста`, `⚠️ Ошибка` —
кнопка «Стоп» убирается, остаётся «⬅ Меню». Финальный ответ агента приходит
отдельным сообщением (длинный — по-прежнему делится по лимиту Telegram).

### Стоп, сброс и их тексты

- `/stop` — **без подтверждения** (иначе теряется смысл «останови сейчас»), с
  честным ответом: «Остановил. Отменено задач в очереди: 2. Контекст сохранён —
  можно ставить новую задачу». Ноль в очереди — текст без этой строки.
- `/reset` — подтверждение остаётся (`reset:yes|no`), потому что уничтожается
  сессия; текст подтверждения подчёркивает отличие от стопа.
- Смена воркспейса во время задачи разрешена (как сейчас). Карточка прогресса
  остаётся подписана воркспейсом выполняющейся задачи, а карточка-меню
  показывает новый активный воркспейс.

## Ошибки и края

- Сбой Telegram-вызова — как сейчас: код в лог, сообщение не отправлено, poller
  не клинит.
- Три подряд неудачных редактирования карточки — обновление прекращается
  (карточка «замирает»), задача продолжает выполняться. Это поведение по
  дизайну и описано в runbook.
- Таймер карточки гасится в `finally` при любом исходе задачи (успех, ошибка,
  отмена, сброс) — «висящих» обновлений после квитанции не остаётся.
- `/stop` без активной задачи — только всплывающий ответ.
- Отмена активной задачи и отмена задач в очереди различимы: очередь отдаётся
  раннером с кодом `cancelled`, чат не пишет про них «Агент не смог выполнить
  задачу».
- Сброс во время задачи — поведение прежнее (задача прерывается, сессия
  уничтожается), но карточка получает явную квитанцию вместо прежнего
  сопоставления по тексту ошибки.
- Воркспейс удалён при живом канале — прежнее поведение (выбор сбрасывается),
  карточка-меню показывает подсказку.
- Предел снапшотов (64, LRU) не меняется; пикер модели им пользуется.

## Безопасность и containment

- Обработка команд и callback'ов идёт только после `isAuthorized`; групп и
  чужих user ID это не касается — они игнорируются как раньше.
- Карточка прогресса — новая поверхность вывода, поэтому в неё попадает только
  то, что перечислено в правилах рендера: имена инструментов, короткие цели из
  белого списка, todo-текст. Аргументы `write`/`edit` (содержимое файлов) и
  результаты инструментов не рендерятся.
- Модель выбирается только из соединений, которые вернул `balbesModels`, и
  только по индексу снапшота; `saveDefault` повторно валидирует пару.
- Новые команды **не** расширяют поверхность инструментов агентской задачи:
  allow-фильтр (`KEPT_TOOL_NAMES`) и containment-guard чтения остаются как есть.
- Остановка задачи не даёт новых прав: `agent.cancel` — управление своей же
  сессией канала.

## Тестирование

Чистые:

- `cards.ts` — тексты и клавиатуры карточек (меню, модель, статус, квитанции);
- `commands.ts` — роутинг, неизвестная команда, инвариант «текст со “/” не
  уходит агенту»;
- суммаризатор прогресса — обрезка цели, схлопывание переводов строк,
  отсутствие результатов инструментов в рендере, поведение при пустом логе.

`agentTask.test.ts`:

- живой selection: смена глобального дефолта долетает до следующего turn **той
  же** сессии (sessionId не меняется);
- `cancel`: активная задача отменена, очередь отдана как `cancelled`, sessionId
  и контекст целы, следующая задача выполняется;
- `cancel` на простое — безопасный no-op;
- `reset` не сломан (по-прежнему уничтожает сессию);
- `snapshot()` отражает фазы `queued`/`running`/`idle`.

`chat.test.ts`:

- карточка-меню и её кнопки, включая «Обновить» и «Стоп» при простое;
- пикер модели: индексы вместо строк, соединение без ключа, устаревший снапшот;
- `/stop` без подтверждения, с очисткой очереди и без сообщений об «ошибке»;
- жизненный цикл карточки: очередь → выполняется → квитанция; троттлинг;
  «идентичный текст не редактируем»; таймер не переживает исход задачи;
- смена воркспейса во время задачи не путает подписи карточек.

`models`:

- юнит-тесты нового сервиса (`list`, `current`, `saveDefault`, отказ на модель
  чужого соединения);
- проверка, что `/api/models/default` и `saveDefault` используют одну валидацию.

REAL-композиция:

- `integration.test.ts` с фейковым Bot API: `setMyCommands` вызван с ожидаемым
  списком, команды и callback'и проходят end-to-end, карточка прогресса
  редактируется, `/model` меняет `agentDefaultModel`;
- агентский REAL-тест: отмена длинной задачи не разрушает контекст — следующая
  задача в той же сессии помнит предыдущую, а `/reset` забывает;
- containment-регрессии текущего набора остаются зелёными (поверхность
  инструментов, запрет чтения вне воркспейса).

## Канон и эксплуатация

Канон правится только через `canon-write`:

- `docs/canon/ARCHITECTURE.md` — блок Telegram (командная поверхность и
  нативная регистрация команд, смена глобальной модели живым selection, состав
  карточки прогресса и что в неё не попадает, стоп без потери контекста против
  сброса с потерей) и список «Не входит» (модель на воркспейс, связные итоги
  агента); ссылки на подтверждённые факты движка (`Agent.cancel`,
  `installModelSelection` с мутабельным ref, `ctx.provide`).
- `docs/canon/GLOSSARY.md` — «Telegram-канал»: состав команд; отдельная строка,
  что карточка прогресса не является streaming.
- `docs/canon/OVERVIEW.md` — перечень возможностей канала.
- `docs/canon/API_CONTRACTS.md` — новых ручек нет; уточняется формулировка про
  финальные сообщения, чтобы карточка прогресса не читалась как противоречие.
- `docs/canon/ADMIN_UI.md`, `docs/canon/DISCREPANCIES.md` — без изменений.

Runbook (`docs/runbooks/stage2-vps.md`) обновляется тем же коммитом
(требование AGENTS.md):

- шаг «Первый контакт» — `/start` → карточка-меню, список команд по «/» и
  нативная кнопка «Меню», `/foo` → «Не знаю такой команды»;
- шаг «Задача» — живая карточка вместо «Задача принята…», финальная квитанция;
- шаг «Файлы и сброс контекста» — добавляются проверки `/model` (значение
  совпадает с админкой, следующая задача идёт на новой модели без сброса
  контекста) и `/stop` (длинная задача останавливается, следующая задача
  помнит предыдущую);
- шаг «Данные на диске» — форма `telegram-state.json` не изменилась;
- диагностика — команд нет в Telegram → смотреть предупреждение про
  `setMyCommands` и проверять `getMyCommands`; карточка перестала обновляться
  после трёх неудачных правок — это по дизайну.

Хендовер проверки на сервере (команды выполняет владелец, канонический путь —
`docs/runbooks/stage2-vps.md`): повторный запуск `scripts/install.sh` на VPS →
смоук `/api/telegram/status` (ожидаемо `connected`) → `ls -l
$DSH_HOME/telegram-state.json` (права `600`, версия 1, новых полей нет) →
шаги чеклиста Telegram в личном чате по обновлённому runbook.

## Критерии готовности

1. В Telegram `/menu` (и нативная кнопка «Меню») доступны в любой момент
   диалога; `/foo` отвечает подсказкой и не уходит агенту.
2. Воркспейс меняется и контекст сбрасывается из середины диалога, не разыскивая
   старое сообщение с кнопками.
3. `/model` меняет модель; значение совпадает с разделом «Модели» админки;
   следующая задача идёт на новой модели **без** сброса контекста.
4. Карточка прогресса показывает ход задачи и превращается в квитанцию;
   содержимое файлов и результаты инструментов в неё не попадают.
5. `/stop` останавливает активную задачу и очищает очередь, следующая задача
   продолжает ту же сессию; `/reset` по-прежнему уничтожает сессию.
6. `pnpm typecheck`, `pnpm lint`, `pnpm test` — зелёные; REAL-наборы прогоняются
   локально с `RUN_REAL=1`.
7. Runbook описывает новые шаги; изменения на `origin/main` (после разрешения
   владельца на push).

## Не входит в этот этап

- streaming текста ответа модели (SSE/WS);
- модель на воркспейс и модель на одну задачу;
- связные промежуточные итоги, сформулированные агентом;
- подтверждения вызова инструментов через Telegram;
- отмена только активной задачи с сохранением очереди;
- webhook, отдельный процесс/юнит для Telegram, другие каналы (A2A),
  многопользовательский доступ;
- список сессий в админке, git, память, самообучение.

## Открытые технические проверки до реализации

Проверки реализации, а не незаполненные продуктовые решения; они не меняют
согласованный scope.

1. `setMyCommands`/`setChatMenuButton` в фейковом Bot API тестовой фикстуры —
   методы нужно добавить в фейк, иначе REAL-набор упадёт на неизвестном методе.
2. `Agent.cancel` на idle-агенте: по документации no-op («with no active
   activity, cancellation is a no-op») — подтвердить тестом, что сессия не
   портится.
3. Смена глобального дефолта не ломает resume сессии, в логе которой уже есть
   `request/header` с прежней моделью: наш раннер всегда использует живой
   selection — подтвердить на REAL-наборе, что turn не падает.
4. `session.append("model/selection", …)` вне turn: убедиться, что проекции и
   квитанции (`foldSurface`) не страдают; если есть сомнения — отказаться от
   записи события, смена модели работает и без него.
5. Лимиты Telegram на редактирование: при троттлинге 3–4 секунды ретраи клиента
   не должны превращаться в шторм; при 429 карточка просто пропускает
   обновление.
