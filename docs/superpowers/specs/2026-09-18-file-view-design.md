# Просмотр файла в админке — дизайн

- Status: approved design
- Date: 2026-09-18
- Инициатива: `docs/canon/future_plans/p3-file-view.md`

## Цель

Владелец открывает файл воркспейса прямо из админки и читает его содержимое, не
покидая страницу «Проекты» и не заходя на сервер. Дерево даёт состав каталогов и
файлов; этот шаг даёт чтение одного файла. Редактирование, создание и скачивание
файлов остаются вне админки.

## Решения и границы

- **Открытие файла — динамический таб правой зоны.** Клик по листу дерева
  добавляет (или фокусирует) таб, внутри — содержимое файла. Это тот же механизм,
  что табы сессий из p2 (инициатива `p2-session-view`): таб «Сессии» остаётся
  первым и незакрываемым; открытых файловых табов может быть сколько угодно; «×»
  закрывает, активируя соседа слева. Табы не переживают перезагрузку, уход со
  страницы и смену воркспейса — состояние UI-локальное. Правая зона уже
  называется «Содержимое воркспейса» и имеет независимый скроллер, поэтому
  компоновка страницы не меняется.
- **Источник данных — серверная ручка `workspaces.file`,** переиспользующая
  доменную функцию `readWorkspaceFile` (`dsh-balbes-workspaces/src/file.ts`),
  которой уже пользуется Telegram. Новой семантики чтения не вводится: тот же
  контеймент (лексический + realpath), тот же признак бинарности, тот же лимит.
- **Три формы результата — данные, а не ошибки.** `text` / `binary` / `link`
  возвращаются с HTTP 200 в поле `file`; ошибки (400/404/401/500) — только про
  форму запроса, отсутствие файла и внутренний сбой. Так UI различает «файл
  есть, но не показывается» и «файла нет».
- **Лимит — `DEFAULT_MAX_FILE_BYTES` = 256 КиБ** (уже принят Telegram-каналом),
  с флагом `truncated: true`. Новый порог не вводится; при обрезании UI
  показывает пометку, а не молча неполный текст.
- **Бинарность — по содержимому, а не по расширению:** NUL в первых 8 КиБ
  (`BINARY_SNIFF_BYTES`). Расширение обманывает, поэтому файл показывается как
  «бинарный (N байт) — просмотр недоступен», без декодирования.
- **Симлинки не разыменовываются.** Финальный симлинк даёт `kind: "link"` и в UI
  «Символические ссылки не открываются» — то же правило контеймента, что у
  `workspaces.tree`. Чтение через промежуточный симлинк за корень воркспейса
  отвергается как `not-found`.
- **Кодировка — UTF-8** (как в существующем `readWorkspaceFile`); детект прочих
  кодировок не делается.
- **Каталог — не файл.** Путь, ведущий на каталог (в т.ч. пустой `path`), —
  `404 not-found`: ручка читает только листья-файлы, зеркально тому, как
  `workspaces.tree` отвечает `not-found` на путь-файл.
- **Живого обновления открытого файла нет.** Чтение — при открытии таба и по
  общей кнопке «Обновить»; fs-события, как и сейчас, перечитывают только дерево.
- **Read-only:** ручка и UI ничего не пишут на диск.
- Вне границ: редактирование/сохранение/создание файлов; загрузка и скачивание;
  рендер по типу (markdown-превью, изображения, подсветка синтаксиса); показ
  бинарных файлов как содержимого; пагинация; права и роли (сервер single-user).

## Архитектура

### Плагин `dsh-balbes-workspaces`

Домен `readWorkspaceFile` и сервис `balbesWorkspaces.readFile` уже существуют;
добавляется HTTP-ручка и одно уточнение домена.

- `src/index.ts` — ручка `POST /api/workspaces/file` (bearer). Читает тело
  `{scope, name?, path}`, зовёт `readWorkspaceFile(dshHome, scope, name, path)`
  с дефолтным лимитом и отдаёт `{file: WorkspaceFileResult}`. Маппинг ошибок —
  как у `workspaces.tree`: `invalid-name`/`invalid-path` → 400,
  `not-found` → 404, прочее → 500.
- `src/file.ts` — после проверки `lstat` добавляется отказ на каталог:
  `st.isDirectory()` → `workspaceError("not-found", …)`. Сейчас открытие
  каталога на чтение даёт `EISDIR` и улетает в 500; пустой `path` (корень
  воркспейса) — тот же случай. Поведение для файлов не меняется.

### Контракты и клиент

- `dsh-balbes-contracts` — `WorkspaceFileKind`, `WorkspaceFileResult`
  (`text`/`binary`/`link`), `WorkspaceFileRequest`, `WorkspaceFileResponse`.
- `dsh-balbes-admin` `api/client.ts` — `readWorkspaceFile(scope, name, path)` →
  POST `/api/workspaces/file`; `AdminApi` расширяется.

### Фронтенд

- `FileTree.tsx` — листья становятся кнопками (клавиатура и фокус) и открывают
  файл через новый проп `onOpenFile(relPath)`; папки по-прежнему раскрываются.
  Симлинк тоже кликабелен и приводит к сообщению «не открывается». `relPath`
  листа собирается из пути каталога и имени записи.
- `WorkspacesPage.tsx` — владеет выделенным воркспейсом и деревом, поэтому
  принимает `onOpenFile` от `FileTree` и передаёт в правую зону одноразовый
  запрос на открытие файла `{id, refKey, path}` (`id` монотонно растёт, чтобы
  повторный клик по тому же пути тоже фокусировал таб). Запрос несёт `refKey`
  воркспейса: чужая зона его игнорирует, поэтому клик не открывает файл в
  новом воркспейсе.
- `WorkspaceRightPane.tsx` — табы обобщаются до union `session | file`
  (`id` файлового таба — `file:<refKey>:<path>`, `refKey` хранится в записи
  таба, как у сессий). Проп `openFile` — одноразовый запрос; панель открывает
  (или фокусирует) таб, когда приходит новый `id` и `refKey` совпадает с
  текущим. Сессионные табы и вся их логика не трогаются.
- `FileView.tsx` (новый) — пропы `api, workspace, path, reloadKey`. Чтение при
  монтировании, смене пути/воркспейса и `reloadKey`, с приёмом «поколение +
  счётчик запроса» (как `FileTree`/`SessionTranscript`). Рендер:
  - «Загрузка…»;
  - ошибка + кнопка «Повторить»;
  - `kind: "text"` — `<pre>` с содержимым (моноширинный, независимая
    прокрутка) и, при `truncated`, пометка «Файл показан не полностью (лимит
    256 КиБ)»; пустое содержимое — «Файл пуст»;
  - `kind: "binary"` — «Это бинарный файл (N байт) — просмотр недоступен»;
  - `kind: "link"` — «Символические ссылки не открываются».
- Подпись файлового таба — имя файла (basename), `title` — полный
  относительный путь для различения одноимённых.

## Контракты API

Типы — компиляторный SoT в `packages/contracts/src/index.ts`.

### `workspaces.file` — чтение содержимого файла воркспейса

- method: POST
- path: /api/workspaces/file
- auth: bearer
- request: `{scope: "home"|"project", name?: string, path: string}` (`name` —
  только при `scope: "project"`; `path` — относительный путь файла внутри
  корня воркспейса, непустой)
- response:

```json
{
  "file": { "kind": "text", "content": "…", "truncated": false }
}
```

  где `file` — одна из форм:
  - `{kind: "text", content: string, truncated: boolean}`
  - `{kind: "binary", size: number}`
  - `{kind: "link"}`

- errors: 400 `invalid-name` (нет/битый `name` у project), 400 `invalid-path`
  (неверный путь, в т.ч. traversal за корень), 404 `not-found` (файла нет,
  путь ведёт на каталог, промежуточный симлинк выводит за воркспейс), 401, 500
- notes: ленивое чтение одного файла; контеймент — лексический и по realpath,
  как у `workspaces.tree`; финальный симлинк не разыменовывается (`link`);
  бинарность — NUL в первых 8 КиБ; лимит текста 256 КиБ с флагом `truncated`;
  кодировка UTF-8; ничего не пишется.

```ts
export type WorkspaceFileKind = "text" | "binary" | "link";
export type WorkspaceFileResult =
  | { kind: "text"; content: string; truncated: boolean }
  | { kind: "binary"; size: number }
  | { kind: "link" };
export interface WorkspaceFileRequest {
  scope: WorkspaceScope;
  name?: string;
  path: string;
}
export interface WorkspaceFileResponse {
  file: WorkspaceFileResult;
}
```

## Риски

- Очень большой, но < 256 КиБ `<pre>` даёт крупный DOM; пагинация отложена, но
  серверный DTO её не блокирует (`truncated` уже есть).
- Открытый файл, удалённый извне, покажет ошибку с «Повторить» — приемлемо.
- Файл, изменённый извне после открытия, покажет старую версию до «Обновить»;
  живого обновления нет by design.
- Не-UTF-8 текст без NUL отобразится с заменяющими символами; детект кодировок
  вне границ.

## Отложено (не в этом шаге)

- Редактирование/сохранение/создание файлов из админки.
- Рендер по типу: markdown-превью, изображения, подсветка синтаксиса.
- Пагинация/догрузка больших файлов.
- Живое обновление открытого файла.
- Скачивание/загрузка файлов.
