- Базируется на: `docs/canon/future_plans/p10g-memory-extraction.md`,
  `p10-memory-system.md`, `p10a-memory-store.md`, `p10c-memory-context.md`,

  `docs/canon/ARCHITECTURE.md`, `docs/canon/GLOSSARY.md`,

  спеках `2026-09-27-memory-context-design.md`,

## Цель

Знание из успешной задачи не теряется: после задачи, в которой агент реально
работал, слой сам инициирует извлечение — агент делает **служебный ход** в той
же сессии и предлагает единицы долговременного знания инструментом
`propose_memory`. Предложения уходят в очередь ревью (p10f) и не становятся
истиной до решения владельца; запись даёт p10a, политику автономии — p10f,
чистку — p10d. Слой не меняет ни доставку (p10c), ни явный `remember` (p10e),
ни поведение задачи: ответ владельцу выдаётся до извлечения.

## Решения и границы

Согласовано с владельцем:

| Вопрос | Решение |
|---|---|
| Триггер | После каждой **успешной** задачи, с предохранителем; расписания и ручной команды нет |
| Кто извлекает | Агент: служебный второй ход в той же сессии + инструмент `propose_memory` |
| Гейт | `ok === true` И в ходе задачи был хотя бы один вызов инструмента |
| Cooldown | Нет: бюджет задаёт сам гейт |
| Потолок | Не больше 3 предложений за служебный ход |
| Каналы | Telegram сейчас; host-шов (`/api/prompt`) прокидывается, но не вызывается |
| Латентность | Ответ владельцу отдаётся сразу после задачи; извлечение идёт фоном |
| Уровень записи | Выбирает слой (scope задачи), не модель: параметра `scope` у инструмента нет |
| Дедуп на входе | Точное совпадение нормализованного текста с памятью и ожидающими предложениями |
| Секреты | Барьер p10a/p10f (`propose`, `secret-detected`); кандидат отбрасывается |
| `remember` во время извлечения | Снимается с поверхности: во время служебного хода агент не может писать в память сразу |
| Носитель предложений | Существующая таблица `memory_proposals` (p10f); миграций нет |
| HTTP-контракты | Не меняются: новых ручек нет, извлечение — внутрипроцессное |
| Владелец видит | Предложения и их провенанс в существующей вкладке «Очередь ревью» |

Границы:

- Доставка (p10c) не меняется ни строкой: извлечение пишет только
  предложения, а их доставка структурно не видит. `prepare` служебного хода не
  вызывается — снапшот задачи не перечитывается.
- Явный `remember` (p10e) не меняется: в ходе задачи он пишет прямо, как
  раньше; во время служебного хода он недоступен, потому что служебный ход —
  это пайплайн, а политика p10f требует для пайплайна ревью.
- Задача (p1/p5/p9, очередь и прогресс) не меняется в наблюдаемом поведении:
  результат, тексты, коды ошибок и глубина очереди те же. Извлечение не влияет
  на результат задачи даже при собственной ошибке.
- Никакой новой серверной поверхности: ни ручек, ни экранов, ни пунктов
  сайдбара, ни миграций `memory.sqlite`, ни изменений `dsh-balbes-contracts`.
- Дедуп здесь узкий и входной (не создавать заведомый дубль); нечёткий,
  семантический дедуп, затухание, TTL и конфликты — p10d.
- Метрики попаданий и пользы — p10h; уведомления в Telegram о предложениях,
  решения по предложениям из бота, автоодобрение и режим доверия — вне контура.
- Извлечение из промптов админки (`POST /api/prompt`) в этой итерации не
  выполняется, хотя шов канало-нейтрален.

## Архитектура

### Разделение ответственности

| Компонент | Ответственность |
|---|---|
| `dsh-balbes-memory-context` (расширяется) | Write-поверхность памяти в scope агента: `remember` (задача), `propose_memory` (служебный ход), дедуп, счётчики, выбор уровня |
| `dsh-balbes-telegram` (`agentTask.ts`) | Оркестрация хода: гейт, запуск служебного хода, порядок «ответ → извлечение», восстановление поверхности, обработка сбоя |
| `dsh-balbes-host` (`runner.ts`) | Шов на будущее: получает handle извлечения, но не вызывает его |
| `dsh-balbes-memory` (p10a/p10f) | Не меняется: `propose` уже сериализует валидацию, секреты и запись предложения |
| `dsh-balbes-memory-admin` (p10b/p10f) | Не меняется: очередь ревью уже показывает «предложено пайплайном · originRef» |

Новый пакет не заводится: `remember` и `propose_memory` — одна write-поверхность
одного агента, и переключение «задача ↔ извлечение» должно быть атомарным в
одном владельце. Отдельный плагин заставил бы два пакета координировать снятие
`remember`, не давая ничего взамен.

Шов (`dsh-balbes-memory-context`):

```ts
interface MemoryContextAttachment {
  prepare(taskText: string): Promise<void>;
  /** Есть только тогда, когда слой может извлекать (write-контекст + save + propose). */
  extraction?: MemoryExtractionHandle;
}

interface MemoryExtractionHandle {
  /** Дешёвый гейт без вызовов модели. */
  qualifies(facts: { ok: boolean; toolCalls: number }): boolean;
  /** Снять `remember`, зарегистрировать `propose_memory`, вернуть директиву. */
  begin(): { message: string };
  /** Снять `propose_memory`, вернуть `remember`, записать счётчики. Идемпотентен. */
  end(): void;
}
```

Канал потребляет этот шов структурно (как остальные deps `agentTask.ts`), не
импортируя пакет.

### Триггер и предохранитель

Извлечение запускается ровно тогда, когда все условия истинны:

1. ход задачи завершился `{ ok: true }` (`TaskResult` канала) — не `busy`,
   `queue-full`, `cancelled`, `agent-error`, `workspace-gone`;
2. в ходе задачи был хотя бы один вызов инструмента
   (`summarizeProgress(agent.session, firstSeq).steps.length > 0`) — признак
   «агент что-то делал» без единого дополнительного вызова модели;
3. запись не отменена и не сброшена владельцем (`retired`/`cancelled` ложны);
4. у агента есть handle извлечения (то есть плагин memory-context с write-контекстом
   скомпозитован и хранилище доступно).

Разговорный ход без инструментов («привет», «спасибо») извлечения не порождает.
Cooldown не вводится: стоимость ограничена гейтом, а пропуск извлечения из-за
таймера терял бы знание из быстро идущих подряд задач.

### Служебный ход

Порядок в канале (`startTurn` → `executeTurn`), с сохранением всех текущих
семантик очереди и отмены:

1. ход задачи выполняется как сегодня; `summarizeTurn` даёт результат, шаги
   считаются до служебного хода (интервал `firstSeq..session.seq` закрыт);
2. промис задачи **резолвится результатом** — владелец получает ответ, не
   ожидая извлечения;
3. если гейт пройден: `begin()` регистрирует `propose_memory` и снимает
   `remember`, возвращая текст директивы;
4. `entry.firstSeq`/`entry.startedAt` переводятся на начало служебного хода —
   прогресс-карточка описывает текущую активность, а не завершённую задачу;
5. в сессию уходит служебное сообщение:
   `createUserMessage({ content: [{type:"text", text: директива}],
   source: { kind: "balbes-memory-extraction", form: "notice",
   summary: "memory extraction" } })` — producer-declared `kind` (типы
   `MessageSourceMap` merge-extensible, при необходимости объявляется
   модульным расширением), поэтому в просмотре сессий это контекстная строка,
   а не реплика владельца;
6. `await agent.whenIdle()` → `await deps.sessions.flush(agent.session)`;
7. в `finally` — `end()`: снять `propose_memory`, вернуть `remember`, записать
   счётчики; идемпотентен и вызывается даже при сбое, отмене и сбросе.

Директива — фиксированный текст без подстановки текста задачи и ответа:

```
Служебный шаг после успешной задачи — извлечение долговременного знания.
Если в этой задаче появилось знание, полезное в будущих сессиях (факт о проекте
или владельце, предпочтение владельца, принятое решение), предложи его
инструментом propose_memory — по одному вызову на единицу знания, не больше
трёх за шаг. Предложения уходят владельцу в очередь ревью; в память сразу
ничего не пишется. Не предлагай секреты, credentials, разовые детали задачи и
то, что уже есть в памяти. Если достойного знания нет — инструмент не вызывай
и ответь одной строкой.
```

Пока служебный ход идёт, `entry.busy` остаётся истинным: следующая задача
владельца встаёт в очередь воркспейса (до 3 ожидающих) и получает задержку в
один ход. Это осознанная цена за сериализацию одного агента и за то, что
поверхность инструментов переключается только между ходами.

### Поверхность инструментов: `remember` ↔ `propose_memory`

- В ходе задачи поверхность агента не меняется: `recall` и `remember`, как в
  p10c/p10e.
- На время служебного хода `remember` снимается (disposer регистрации), а
  `propose_memory` регистрируется; `recall` остаётся (чтение безвредно).
- Переключение использует штатные эффекты `tools.register`/disposer, то есть
  попадает в `tools/change` и следующую сборку запроса. Регистрация происходит
  до `followup`, снятие — после `whenIdle`.
- Инвариант: в служебном ходе у агента нет ни одного инструмента, пишущего в
  память сразу. Обход политики p10f («пайплайн идёт через ревью») структурно
  невозможен, а не запрещён текстом.
- Динамическая регистрация инструмента после `setup` — главный технический
  риск; он проверяется REAL-тестом первым (см. «Тестирование»). Если шов
  окажется непригодным, запасной вариант — регистрация обоих инструментов в
  `setup` с гейтом активности внутри `execute`; это меняет tool-поверхность
  задачи и потому требует отдельного решения.

### Инструмент `propose_memory`

Тот же пакет `dsh-balbes-memory-context`, scoped-регистрация.

- Параметры: `text` (required, строка), `type` (enum
  `fact | preference | decision | note`, необязателен, дефолт `note`), `tags`
  (необязательный массив слагов). Параметров `scope` и `pinned` нет: уровень
  выбирает слой (scope задачи, дом → `global`), пиннинг доступен только
  владельцу при одобрении (p10f).
- Путь записи ровно один — `balbesMemory.propose({ scope, type, text, tags,
  originRef })`. Обходных путей нет: валидация p10a и барьер секретов p10f
  действуют здесь так же, как в ручке `memory.propose`.
- Провенанс: `originRef = "<channel> session:<sessionId>"` (тот же формат, что
  у `remember`, без текста задачи). Промоушен даст `origin = "agent"`,
  `status = "proposed"`.
- Потолок: не больше 3 успешных предложений за служебный ход; на четвёртом
  вызове инструмент отвечает ошибкой `propose_memory: extraction limit
  reached (3 proposals per turn)`, счётчик `limit` растёт. Повторные вызовы с
  дублем потолок не тратят.
- Вывод: `{ status: "proposed" | "duplicate", proposal? }`; `render` даёт
  короткую строку («Предложено на ревью: `type` · уровень» либо «Уже известно —
  пропущено»). Полный текст предложения в вывод не дублируется сверх
  необходимого.
- Ошибки — tool error, ход агента не ломается: `secret-detected` →
  «текст похож на секрет, не предложено» (счётчик `secret`),
  `invalid-record`/`invalid-scope` → сообщение валидатора, прочее → общая
  ошибка без внутренних деталей.

### Дедуп на входе

Дедуп — предохранитель от заведомых дублей, а не барьер безопасности, поэтому
он best-effort:

- Нормализация: `text.trim().toLowerCase()` + схлопывание пробельных серий.
- Индекс строится лениво на первом вызове инструмента в ходе:
  `balbesMemory.list({ scopes: [global, scope задачи], limit: 500 })` и
  `listProposals({ status: ["proposed"], scope })` для `global` и для scope
  задачи (фильтр предложений принимает один `scope`, лимит ≤ 500).
- Совпадение нормализованного текста → `{ status: "duplicate" }`, предложение
  не создаётся, счётчик `duplicate`. Успешное предложение сразу добавляется в
  индекс, поэтому два одинаковых кандидата в одном ходе не создают двух строк.
- Сбой чтения индекса → `warn` и продолжение без дедупа (fail-open): секреты и
  валидацию всё равно держит `propose`.
- Отсутствие совпадения — не доказательство новизны: нечёткое сходство,
  перефразы и слияние записей остаются p10d.

### Латентность, очередь и состояния

- Резолв промиса задачи до служебного хода означает: ответ владельцу не
  задерживается; `entry.busy` держится до конца извлечения, поэтому следующая
  задача воркспейса ждёт (семантика `QUEUE_MAX_WAITING` не меняется).
- `cancel()` во время служебного хода обрывает именно его (`keepInbox`),
  `finally` возвращает поверхность; результат уже выданной задачи не
  переписывается, `entry.cancelled` очищается в общем `finally`, как сегодня.
- `reset()` во время служебного хода уничтожает handle и scope: disposer'ы
  вызываются в `finally` под guard'ом, повторное снятие безопасно.
- Прогресс-карточка во время извлечения описывает служебный ход (его вызовы
  `propose_memory`) — это знак жизни, как и раньше, а не ответ; тексты задачи и
  ответа в прогресс не попадают.
- Служебный ход не участвует в дедупе задач (`activeText` не перезаписывается),
  не считается задачей в очереди и никогда не попадает в текст ответа.

### Провенанс и уровень

- Scope: `home` → `global`, проект → `project:<имя>`; кросс-проектных чтений и
  записей не добавляется, чужой проект недостижим структурно, как в p10e.
- Уровень выбирает слой и только он: классификатор уровня (p10e) в служебном
  ходе **не** вызывается — это был бы второй вызов модели вопреки бюджету.
  Если знание, найденное в проектной задаче, на самом деле относится к дому,
  владелец видит это при одобрении; перенос между уровнями — p10d.
- `originRef` фиксированного формата и не резолвится: это непрозрачный
  провенанс, видимый в очереди ревью.

### Приватность и секреты

- Служебный ход видит ту же сессию и тот же воркспейс, что задача: новых
  источников данных не появляется.
- Текст кандидата проходит детектор секретов внутри `propose`;
  `secret-detected` = кандидат не записан, остальные кандидаты хода продолжают
  обрабатываться. Директива отдельно запрещает секреты и credentials.
- В журнал не попадают ни текст памяти, ни текст задачи, ни ответ: только
  счётчики и метки канала/уровня.

### Шов для admin-канала

- `runner.ts` (`POST /api/prompt`) читает handle извлечения из attachment и
  продолжает вызывать только `prepare`. Условие для будущего включения
  описано в каноне: у `/api/prompt` нет воркспейса и сессии, переживающей ход
  (агент уничтожается в `finally`), поэтому включение потребует решения о
  scope и о хранении сессии — отдельная итерация.
- Шов канало-нейтрален: `attach(...).extraction` не знает про Telegram, а
  `qualifies/begin/end` не зависят от канала.

## Ошибки и деградация

| Ситуация | Поведение |
|---|---|
| Нет плагина memory-context или write-контекста | `extraction` отсутствует; задача работает как сегодня |
| Нет хранилища (сервис не предоставлен) | как сегодня: `attach` деградирует, `propose_memory` не регистрируется |
| `begin()` бросил | `warn`, служебный ход не выполняется, результат задачи не тронут |
| Ошибка инструмента (`secret-detected`, валидация, потолок) | tool error в служебном ходе; предложение не создано; `whenIdle` завершается нормально |
| Директивный ход завершился `error`/`aborted` | `warn` со счётчиками; поверхность восстановлена; результат задачи не тронут |
| `whenIdle` отверг (срыв драйвера) | как для задачи сегодня: handle признаётся испорченным, dispose и сброс привязки сессии; `warn`. Сессия остаётся на диске и выбирается из меню сессий — цена ограничена привязкой |
| `flush` бросил | `warn`; поверхность восстановлена; задача не тронута |
| Дедуп не смог прочитать индекс | `warn`, продолжение без дедупа (fail-open) |

Правило: служебный ход никогда не меняет уже вычисленный результат задачи и не
превращает успешную задачу в ошибку.

## Наблюдаемость

- Одна `logger.info`-строка плагина на служебный ход (в `end()`):
  `balbes-memory: extraction channel=telegram scope=global|project:<имя>
  proposed=N duplicate=M secret=K limit=L` — без текста памяти.
- `warn`-строки: сбой индекса дедупа, сбой служебного хода, срыв драйвера.
- Владельцу: предложения и `originRef` видны в существующей вкладке «Очередь
  ревью»; отдельного счётчика извлечений и метрик пользы нет (p10h).
- В просмотре сессий служебный ход виден как контекстное сообщение
  (`form: "notice"`, summary «memory extraction») и последующие вызовы
  `propose_memory`; это след аудита, а не реплика владельца.

## Тестирование

Unit (`dsh-balbes-memory-context`):

- `qualifies`: матрица «ok × toolCalls × retired/cancelled»; ход без инструментов
  не извлекается.
- дедуп: нормализация (регистр, пробелы), совпадение с записью, совпадение с
  ожидающим предложением, два одинаковых кандидата в одном ходе, fail-open при
  сбое чтения.
- потолок: четвёртый вызов — tool error, счётчик `limit`; дубли потолок не
  тратят.
- секрет: `secret-detected` → tool error, предложение не создано, счётчик
  `secret`, остальные кандидаты продолжают.
- путь записи: вызов уходит в `propose`, а не в `save`; `originRef` формата
  `<channel> session:<id>`; scope — из слоя.
- поверхность: `begin()` снимает `remember` и регистрирует `propose_memory`;
  `end()` возвращает поверхность и идемпотентен; при исключении внутри хода
  поверхность всё равно восстановлена.

Unit (`dsh-balbes-telegram`, fake deps):

- после `ok`-хода с шагами: промис задачи резолвится **до** служебного
  `followup` (порядок проверяется явно), директива уходит служебным сообщением,
  `remember` возвращён;
- после `ok`-хода без инструментов служебного хода нет;
- `agent-error`/`cancelled`/`busy`/`queue-full` — извлечения нет;
- ошибка извлечения не меняет результат задачи и не мешает следующей задаче из
  очереди;
- `cancel`/`reset` во время служебного хода: поверхность восстановлена, сброс
  не приводит к двойному dispose.

REAL-composition (`dsh-balbes-telegram`, `RUN_REAL=1`, стаб-LLM):

- сквозной прогон через Loader: ход задачи с вызовом инструмента → служебный
  ход → `propose_memory` → в `balbesMemory` появилось предложение (и не
  появилось записи в `memories`);
- запрос служебного хода (записан стабом) не содержит `remember` и содержит
  `propose_memory` — проверка динамической регистрации;
- ход «привет» → предложений нет;
- повторная одинаковая задача → второй предложения нет (дедуп);
- секрет-подобный кандидат → предложения нет, счётчик в журнале.

Регрессии: тесты p10a/p10b/p10c/p10e/p10f остаются зелёными без правок — схема,
ручки и доставка не меняются. `pnpm typecheck`, `pnpm lint`, `pnpm test`
(обязательные), REAL-набор — по `RUN_REAL=1`.

## Обновление на сервере и проверка

Код попадает на сервер только через `main` → повторный `scripts/install.sh` на
VPS (git pull --ff-only, сборка, синк профиля, копия плагинов, SPA, рестарт
`dsh-balbes`); новых пакетов и insert-строк в профиле нет, но повторный
install.sh обязателен, потому что меняются тела `dsh-balbes-telegram` и
`dsh-balbes-memory-context` в `node_modules` профиля.

Проверка (по каноническим командам runbook):

1. Позитивный сценарий: в Telegram дать задачу, которая требует инструмента
   (например, попросить прочитать файл проекта). Затем в админке/через curl
   `POST /api/memory/review/list` (bearer) — ожидается новое предложение с
   `originRef` вида `telegram session:<id>`, `status: "proposed"`, и его нет в
   `POST /api/memory/list`.
2. Негативный сценарий: отправить «привет» — число ожидающих предложений не
   меняется.
3. Журнал: `journalctl -u dsh-balbes -n 200 | grep balbes-memory` — строка
   `balbes-memory: extraction channel=telegram scope=... proposed=1 ...` без
   текста памяти; при сбое — `warn`.
4. Админка: вкладка «Очередь ревью» показывает предложение с провенансом;
   одобрение промоутит его в запись (существующий smoke p10f), повторное
   решение по-прежнему `invalid-status`.
5. Регресс: обычная задача-ответ (без извлечения) отвечает как раньше; глубина
   очереди и `cancel` не изменились.
6. Целостность: `PRAGMA user_version` = `LATEST`, новых миграций нет; после
   рестарта предложения на месте.

## Отложено

- Метрики извлечений и пользы — p10h.
- Нечёткий/семантический дедуп, слияние, затухание, TTL, конфликты и перенос
  между уровнями — p10d.
- Включение извлечения для `POST /api/prompt` (нужны решение о scope и
  переживающая ход сессия) — отдельная итерация.
- Уведомления в Telegram о новых предложениях и решения по ним из бота.
- Автоодобрение, режим доверия, настройка политики владельцем.
- Извлечение владельческих фактов из проектных задач с автоматическим выбором
  уровня (второй вызов модели) — сознательно не делаем в этой итерации.
