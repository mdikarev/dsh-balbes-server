# Сессии воркспейса в правой панели — дизайн

- Status: approved design
- Date: 2026-09-11

## Цель

Показать владельцу, какие сессии принадлежат выбранному воркспейсу, не выходя из
админки. На странице «Проекты» правая зона перестаёт быть зарезервированной
пустой областью: сверху появляется плашка табов, в ней пока один таб — «Сессии»,
под ним список сессий выбранного воркспейса (заголовок, канал, время создания).

Это первый шаг инициативы «сессии и чат в воркспейсе» (её отсутствие
зафиксировано в `future_plans/p0-agent-workspaces.md`): витрина сессий. Просмотр
диалога, создание сессий и чат из правой панели — последующие шаги.

## Решения и границы

- **Источник правды — явный серверный реестр «воркспейс → сессии»**, а не
  совпадение `cwd` сессии с корнем воркспейса. В реестр попадают только сессии,
  созданные для воркспейса самим продуктом (сейчас — telegram); сессии с тем же
  `cwd`, созданные иначе, в списке не появляются.
- Реестр — новый файл `$DSH_HOME/workspace-sessions.json`, принадлежащий новому
  плагину `dsh-balbes-sessions`. Он append-only: записи добавляются upsert'ом по
  `sessionId` и никогда не удаляются — ни сбросом контекста в telegram, ни
  чтением из админки.
- **Миграции как отдельного кода нет.** Telegram сам отдаёт свой текущий
  маппинг в реестр (при `apply` и при каждой успешной задаче), поэтому текущая
  telegram-сессия воркспейса видна сразу после обновления, а плагин сессий не
  читает чужой `telegram-state.json`.
- Список — только чтение: клик по строке ничего не делает, диалог не
  открывается, сессии из админки не создаются и не удаляются.
- Время и заголовок строки берутся из движка (`sessionQuery`), а не из реестра:
  реестр хранит только принадлежность (`sessionId` + канал) и не дублирует факты
  сессии.
- Живости через SSE на этом шаге нет: список перечитывается при выборе
  воркспейса, при клике по табу и по кнопке «Обновить».
- Вне границ: просмотр диалога/сообщений, создание, переименование и удаление
  сессий, стриминг, признак «активна/live», удаление записей реестра, сессии
  субагентов, другие каналы (кроме telegram), лимит на размер реестра.

## Архитектура

### Плагин `dsh-balbes-sessions`

Новый пакет `packages/plugins/dsh-balbes-sessions`, функциональный плагин
(`name: "balbes-sessions"`), вставляется в `profiles/balbes/cordis.patch.yml`
перед `balbes-telegram`.

- `inject: ["balbesHttp", "balbesWorkspaces", "sessionQuery"]`. `dshHome`
  резолвится как у соседей: config → `$DSH_HOME` → `~/.dsh`.
- `src/registry.ts` — файловое хранилище реестра: ленивая загрузка в память,
  строгая проверка формы, атомарная запись с правами 600 (тот же рецепт, что в
  `telegram/src/state.ts`).
- `src/service.ts` — фасад домена: `register(ref, sessionId, channel)` (upsert) и
  `list(ref)` (записи воркспейса).
- `src/index.ts` — ручка `sessions.list` поверх `balbesHttp` и
  `ctx.provide("balbesSessions", …)`; реестр читается лениво, при первом
  обращении.

Владелец файла — только этот плагин (в процессе одна копия состояния, запись
сериализуется). Сбой записи логируется громким `logger.warn` и **не** меняет
исход задачи в telegram: реестр — витрина, а не граница долговечности задачи.

### Форма реестра

```json
{
  "version": 1,
  "workspaces": {
    "home": [{ "sessionId": "session-…", "channel": "telegram" }],
    "project:alpha": [{ "sessionId": "session-…", "channel": "telegram" }]
  }
}
```

- Ключ воркспейса — существующий формат (`home` / `project:<имя>`), тот же, что
  использует telegram для своего маппинга. Общий хелпер не заводится: плагины не
  зависят от `dsh-balbes-contracts`, а кросс-импорт между плагинами запрещён —
  в плагине сессий живёт свой локальный `refKey`.
- Проверка формы: `version === 1`; `workspaces` — plain object; значения —
  массивы объектов `{sessionId: непустая строка, channel: строка вида
  `^[a-z][a-z0-9-]{0,31}$`}`; дубли `sessionId` внутри воркспейса при загрузке
  сводятся к первому вхождению; неизвестные поля отбрасываются (нормализованная
  копия, как в `parseState` telegram).
- Битый/чужой файл — громкая ошибка, а не молчаливая потеря: чтение отдаёт 500 с
  текстом, запись не перезаписывает невалидный файл. Неудачная загрузка не
  кэшируется как «пусто»: следующий запрос перечитывает файл, поэтому
  исправленный реестр подхватывается без рестарта, а отсутствующий файл
  создаётся первой успешной записью.
- Порядок в файле не значим; ответ API сортирует сессии по времени создания
  (новейшие первыми).

### Интеграция Telegram

- В `inject` плагина telegram добавляется `balbesSessions` — жёстко: «создал
  сессию для воркспейса → она в реестре» должно быть инвариантом композиции, а
  не тихим опциональным поведением. Тестовый профиль telegram дополняется
  insert'ом `balbes-sessions`.
- Регистрация вызывается в обёртке `run()` после `result.ok` (`ref` и
  `result.sessionId` уже под рукой) и при `apply` — для каждой пары текущего
  `live.sessions` (ключ разбирается обратно в `{scope, name}` без обращения к
  списку проектов).

### Правая панель админки

- `WorkspacesPage` вместо пустого `div.ws-void-pane` рендерит
  `WorkspaceRightPane`.
- `WorkspaceRightPane.tsx` — плашка табов (`role="tablist"`) и активная панель
  (`role="tabpanel"`). Табы описаны данными (`[{id, label, render}]`), сейчас
  одна запись «Сессии»; добавление следующего таба — одна запись в массиве.
  Плашка видна всегда; без выбранного воркспейса панель показывает «Выберите
  воркспейс». Активный таб — локальный `useState`.
- `SessionsTab.tsx` — список: заголовок сессии (fallback «Без заголовка»), канал,
  локальное время (`toLocaleString("ru-RU")` с fallback на ISO, как в
  `TelegramPage.tsx`). Состояния: «Загрузка…», «Сессий пока нет», ошибка +
  «Повторить». Загрузка при выборе воркспейса, при клике по табу и по кнопке
  «Обновить» в плашке. Ответы защищены от гонок тем же приёмом «поколение +
  счётчик запроса», что в `FileTree.tsx`: ответ прошлого воркспейса не
  применяется.
- CSS: `.ws-void-pane` заменяется на `.ws-right-pane` + `.ws-tabstrip` /
  `.ws-tab` / `.ws-tabpanel` на существующих токенах `:root`.

## Контракты API

### `sessions.list` — сессии воркспейса

- method: POST
- path: /api/sessions/list
- auth: bearer
- request: `{scope: "home" | "project", name?: string}` (`name` обязателен для
  `project` и запрещён для `home`)
- response: `{sessions: [{id: string, title: string | null, channel: string,
  createdAt: string(ISO)}]}`, новейшие первыми
- errors: 400 (`bad-request`: битая форма тела, неизвестный scope, лишний
  `name`), 401, 404 (`not-found`: проект отсутствует в списке воркспейсов), 500
  (`internal`: реестр нечитаем/битый, отказ движка)
- notes: список — записи реестра для этого воркспейса; для каждой записи
  заголовок и `createdAt` берутся из движка одним вызовом
  `sessionQuery.readTitleSnapshots(ids)`; `title` отсутствует в логе → `null`;
  `id`, неизвестный движку, из ответа выпадает (реестр чтением не
  переписывается). Проверка существования воркспейса — через
  `balbesWorkspaces.list()`, чтобы опечатка в имени давала 404, а не пустой
  список.

Типы-проекции для SPA: `WorkspaceSessionInfo`, `SessionsListRequest`,
`SessionsListResponse` в `dsh-balbes-contracts` (компиляторный источник правды
форм).

## Канон (canon-first)

Правки канона делаются через `canon-write` **до** кода приложения:

- `API_CONTRACTS.md` — раздел `sessions.list`, домен добавляется в Scope.
- `ADMIN_UI.md` — правая зона: плашка табов и таб «Сессии» (состояния, копирайт);
  формулировка «правая пустая зона (зарезервирована под будущее содержимое,
  шапки нет)» заменяется.
- `ARCHITECTURE.md` — серверный реестр сессий воркспейса (файл, владелец, кто
  пишет), домен `sessions.*`, роль `sessionQuery` как источника заголовков и
  времени.
- `GLOSSARY.md` — термины «реестр сессий воркспейса», «ключ воркспейса»
  (`home` / `project:<имя>`), «канал сессии».
- `OVERVIEW.md` — строка про поверхность сессий воркспейса, если состав
  API-поверхности там перечисляется.
- `future_plans/` — новый future-plan «Сессии и чат в воркспейсе»
  (`canon-future-plan`), фиксирующий направление и то, что первый шаг (витрина
  сессий) реализуется; `future_plans/INDEX.md` синхронизируется.

## Установщик и рунбук

- `scripts/install.sh`: блок `copy_sessions_into_profile` по образцу соседних
  плагинов, вызов в основном потоке, строка в шапке-комментарии и в итоговом
  summary. Без этого плагин не появится в `node_modules` профиля на сервере.
- `docs/runbooks/stage2-vps.md` (тот же коммит): шаг smoke для `sessions.list`
  (`curl` с ожидаемым JSON), проверка файла
  (`ls -l $DSH_HOME/workspace-sessions.json` → 600 и форма), UI-проверка таба;
  раздел «Где лежат данные»; troubleshooting битого реестра.

## Тесты и проверки

Плагин `dsh-balbes-sessions`:

1. реестр: отсутствующий файл → пустой; битый → ошибка; upsert идемпотентен;
   атомарная запись 600; неизвестные поля отброшены; дубли `sessionId` сведены;
2. ручка: 400 (форма, scope, лишний `name`), 404 (неизвестный проект), 401;
   маппинг ответа (`title` → `null` при отсутствии, ISO `createdAt`, отсев
   неизвестных движку id, порядок новейшие первыми);
3. REAL-composition тест через Loader: профиль `dsh-base` + host-бандл +
   `balbes-workspaces` + `balbes-sessions`; сценарий: создать проект →
   зарегистрировать сессию через сервис → `POST /api/sessions/list` по реальному
   HTTP.

Фронтенд:

4. `SessionsTab.test.tsx`: загрузка, пустое состояние, строки, ошибка + повтор,
   смена воркспейса (старые строки не остаются), отсутствие запроса без выбора;
5. `WorkspaceRightPane.test.tsx`: плашка с одним табом, связка tab/tabpanel,
   заглушка без выбранного воркспейса;
6. существующие тесты: фейки `AdminApi` дополняются `listSessions`,
   `client.test.ts` — проверка метода/пути/тела, `WorkspacesPage.test.tsx` —
   правая панель и загрузка сессий для выбранного воркспейса.

Telegram:

7. тест «успешная задача регистрирует сессию в реестре» и «apply синхронизирует
   текущий маппинг»; insert `balbes-sessions` в тестовый профиль.

Прогон: `pnpm typecheck`, `pnpm test` (по пакетам), сборка плагинов и SPA.

## Открытые вопросы

- Нужен ли признак «текущая сессия воркспейса» (какая из списка продолжится) —
  потребует поля активности в реестре или чтения маппинга канала.
- Удаление записей реестра (сессия исчезла из движка) — сейчас запись остаётся в
  файле и просто выпадает из ответа; нужна ли уборка и когда.
- Живое обновление списка (событие в существующем SSE-потоке воркспейсов или
  отдельный поток сессий).
