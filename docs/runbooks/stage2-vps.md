# Runbook Этапа 2: сервер `dsh-balbes` с админкой на VPS одной командой

## Цель

Runbook описывает развёртывание профиля dsh `balbes` как **сервера-демона с
админкой**: HTTP-сервер (systemd-юнит `dsh-balbes`) слушает порт и отдаёт
собранный SPA админки (`http://<IP>:8080`) с экраном логина, воркспейсами
(с табом «Сессии» на странице «Проекты»), настройками моделей и
Telegram-интеграцией. Вход — по логину/паролю,
сгенерированным при установке и напечатанным **один раз**; запросы к API —
через JWT. Все `/api/*` — POST (R-API-1). Telegram использует long polling,
работает только для одного разрешённого владельца в личном чате и не требует
входящего порта, webhook, домена или HTTPS endpoint.

Профиль `balbes` на Этапе 2 собирается из бандлов `@deepseek-ai/dsh-base` и
`dsh-balbes-host` (наш host: сервер + статика + auth + api + startup);
поверх них в профиль подключён плагин воркспейсов `dsh-balbes-workspaces`
(API `/api/workspaces/list|create|delete|tree|events`, bearer): список,
создание и удаление воркспейсов-проектов, чтение дерева каталогов
(`tree`) и push-канал их изменений (`events`), на котором админка
обновляет дерево без перезагрузки страницы. Также подключается плагин
`dsh-balbes-telegram`: long polling Bot API, настройки через админку,
workspace-aware задачи штатного dsh agent loop и чтение ограниченных
текстовых файлов. В профиль плагины вносятся патч-слоем
`profiles/balbes/cordis.patch.yml`, а собранный пакет копируется в
`node_modules` профиля рядом с host. Headless и веб-морда (`dsh-web-app`) в
профиль **не входят** — «мордой» теперь служит собственная админка host'а.

Критерий готовности этапа: по этому runbook'у сервер разворачивается на VPS и
проходит ручную проверку — список команд и ожидаемых результатов в разделе
«Ручная проверка (DoD, спека 9.4)» ниже. Источник профиля и скриптов —
репозиторий https://github.com/mdikarev/dsh-balbes-server, ветка `main`.

## Требования

- Ubuntu (установщик использует `apt`; целевая — свежая Ubuntu LTS) и
  пользователь с правами `sudo` — как в Этапе 1.
- `curl` (если нет: `sudo apt-get install -y curl`).
- Доступ в интернет: `raw.githubusercontent.com`, npm registry и API DeepSeek.
- Свободный TCP-порт `8080` (или другой, см. `BALBES_PORT` ниже); сервер
  слушает `0.0.0.0` — порт должен быть открыт в файрволе хоста (см.
  «Файрвол»), а для VPS за облачным файрволом (security group) — ещё и в
  панели провайдера.
- **Этап 1 выполнять не нужно**: установщик Этапа 2 сам ставит окружение
  (Node ≥ 22, pnpm, git), dsh, профиль и ключ. Если Этап 1 уже был выполнен на
  этой машине — повторный запуск установщика аккуратно обновит профиль до
  сервера (ключ в `$DSH_HOME/.credentials.yaml` при этом сохраняется).

## Установка одной командой

Установка выполняется скриптом `scripts/install.sh` из репозитория:

```bash
curl -fsSL https://raw.githubusercontent.com/mdikarev/dsh-balbes-server/main/scripts/install.sh | bash
```

В ходе выполнения скрипт (как и в Этапе 1) интерактивно запросит DeepSeek API
key — запрос читается с терминала (`/dev/tty`) и работает даже внутри
конвейера `curl ... | bash`. Пустой ввод пропускает установку ключа. Чтобы не
вводить ключ вручную, экспортируйте его заранее (без `export` переменную
увидит только curl, а не bash, исполняющий скрипт):

```bash
export DEEPSEEK_API_KEY=sk-ваш-ключ
curl -fsSL https://raw.githubusercontent.com/mdikarev/dsh-balbes-server/main/scripts/install.sh | bash
```

Скрипт идемпотентен: повторный запуск безопасен и работает как обновление
(см. раздел «Обновление»).

В конце установки скрипт печатает сводку: адрес админки
`http://<IP>:8080`, напоминание, где логин/пароль (они напечатаны чуть выше в
логе — **при первом** запуске), и команды smoke-проверки без браузера. Если
вы сохраняли лог установки в файл (`| tee install.log`) — удалите или
ограничьте доступ к нему после того, как сохраните пароль: в нём лежит
единственная копия пароля.

## Что делает установщик (по шагам)

1. **Окружение.** Если `node` ниже 22 или нет `npm` — подключает репозиторий
   NodeSource и ставит Node 22 LTS через `apt`; если нет pnpm — ставит его
   глобально через npm; если нет git — ставит `git` через `apt`.
2. **Репозиторий.** Клонирует https://github.com/mdikarev/dsh-balbes-server в
   `$HOME/dsh-balbes-server` (или в каталог из `$DSH_BALBES_REPO_DIR`); если
   клон уже есть — обновляет его через `git pull --ff-only`. Репозиторий
   обновляется раньше движка: из него установщик берёт пин версии
   `scripts/engine-version.txt`.
3. **dsh.** Версия движка читается из единственного источника —
   `scripts/engine-version.txt` (поиск: сначала рядом со скриптом, затем в
   клоне репозитория; при запуске через `curl | bash` файла рядом со скриптом
   нет, поэтому пин приезжает именно с клоном). Если команда `dsh`
   отсутствует — ставит глобально:
   `sudo npm i -g "@deepseek-ai/dsh@$(cat scripts/engine-version.txt)"`.
   Если `dsh` уже установлен, установщик **сверяет его версию** с пином:
   совпадение — обычная info-строка; расхождение — громкое предупреждение в
   stderr (какая версия стоит, какая ожидается, чем это грозит и точная команда
   обновления). Автоматической переустановки нет: обычный запуск не требует
   sudo, а сознательно выбранная на хосте версия не затирается (см.
   «Устранение неполадок → Предупреждение о рассинхроне версии dsh»).
4. **Сборка workspace.** В клоне репозитория: `pnpm install` и
   `pnpm -r --if-present run build` — собираются `dsh-balbes-contracts`
   (типы), `dsh-balbes-host` (tsc) и SPA админки `dsh-balbes-admin`
   (vite → `packages/frontend/dsh-balbes-admin/dist`). Сборка идёт **до**
   рестарта сервиса: если она падает, установщик выходит с ошибкой, а уже
   работающий сервис не трогается.
5. **Профиль.** Синхронизирует `profiles/balbes` из репозитория в
   `$DSH_HOME/profiles/balbes` (замена каталога целиком; профиль в репо —
   источник правды).
6. **Host в профиль.** Собранный бандл копируется реальным каталогом в
   `$DSH_HOME/profiles/balbes/node_modules/dsh-balbes-host` (из него
   выкидываются `src/`, `tests/`, `lib/types`, `tsconfig.json`). Тем же
   способом туда копируются собранные плагины `dsh-balbes-workspaces`,
   `dsh-balbes-models`, `dsh-balbes-sessions`, `dsh-balbes-telegram` и
   `dsh-balbes-home`. Импорты
   `@deepseek-ai/*` резолвятся подъёмом к зеркалу
   `$DSH_HOME/profiles/node_modules` (механика Этапа 1).
7. **SPA.** Собранный дистрибутив админки копируется в
   `$DSH_HOME/balbes/ui` (старый каталог удаляется целиком).
8. **Ключ API.** Если `DEEPSEEK_API_KEY` не задан в окружении — запрашивает
   ключ интерактивно и записывает в `$DSH_HOME/.credentials.yaml` (права
   `600`), по правилам Этапа 1: существующий файл и чужие записи не
   перезаписываются.
9. **Проверка композиции.** `dsh --profile balbes --dump-config`; падение
   считается ошибкой установки.
10. **Учётная запись администратора.** `scripts/admin-creds.mjs ensure`
    создаёт `$DSH_HOME/admin-auth.json` (права `600`, один раз): случайный
    логин вида `balbes-<8 hex-символов>`, scrypt-хэш пароля, `jwtSecret` и
    `createdAt`. Логин и пароль печатаются **один раз**:
    ```
    Admin credentials generated (stored hashed, printed once):
      login:    balbes-1a2b3c4d
      password: <случайный пароль>
    ```
    При повторном запуске файл не перезаписывается, пароль не печатается —
    только `Admin login (unchanged): <login>` и подсказка про сброс пароля.
11. **systemd.** Пишет юнит `/etc/systemd/system/dsh-balbes.service`
    (описание в разделе «Проверка демона») и выполняет
    `systemctl daemon-reload` + `systemctl enable` + `systemctl restart`.
    Рестарт происходит на **каждом** запуске установщика: после обновления
    демон сразу поднимается на новом коде, ручной рестарт не нужен.
12. **Health и финал.** `POST http://127.0.0.1:<порт>/api/health` должен
    вернуть `{"ok":true,...}`; иначе установка считается неудачной
    (диагностика — в «Устранении неполадок»). Затем печатается итоговая
    сводка с адресом админки и smoke-командами.

Переменные окружения, которые учитывает установщик:

- `DEEPSEEK_API_KEY` — ключ DeepSeek (иначе интерактивный ввод);
- `DSH_HOME` — каталог данных dsh (по умолчанию `$HOME/.dsh`);
- `DSH_BALBES_REPO_DIR` — каталог клона репозитория (по умолчанию
  `$HOME/dsh-balbes-server`);
- `BALBES_PORT` — порт сервера (по умолчанию `8080`); прописывается в юнит и
  используется health-проверкой и сводкой.

## Файрвол

Порт, на котором слушает сервер (по умолчанию `8080`), должен быть открыт в
файрволе хоста. Если ufw ещё не включён — сначала разрешите SSH, чтобы не
потерять доступ, затем порт админки, затем включите ufw:

```bash
sudo ufw allow OpenSSH
sudo ufw allow 8080/tcp        # или порт из BALBES_PORT
sudo ufw enable                # только если ufw ещё не активен
sudo ufw status verbose        # ожидается: 8080/tcp ALLOW
```

Если порт менялся (`BALBES_PORT`), откройте именно его. Для VPS за облачным
файрволом (security group) добавьте правило и там.

## Доступ

Админка открывается в браузере по адресу из сводки установки:
`http://<IP>:8080` (IP — первый адрес `hostname -I`; посмотреть вручную:
`hostname -I | awk '{print $1}'`). Собранный SPA отдаёт сам сервер.

Страница — экран входа («balbes admin»). Логин и пароль — из лога установки
(строки `login:` / `password:` выше блока сводки). После входа — рабочая
зона с сайдбаром: **«Тестовая страница»** (промпт `Напиши 'ok' и больше
ничего` и кнопка **«Отправить тестовый промпт»**: ответ реальной модели
появляется над кнопкой), **«Проекты»** — страница воркспейсов (smoke —
в подразделе ниже), **«Модели»** — подключения моделей и дефолтная модель, и
**«Telegram»** — настройка бота (раздел «Настройка Telegram через админку»
ниже). JWT хранится в localStorage и при перезагрузке страницы
проверяется через `POST /api/auth/me` — повторный вход не требуется, пока
токен жив (24 часа).

Неверный пароль → ошибка 401; после 5 неудачных попыток с одного IP вход
блокируется на 30 минут (429).

### Страница «Проекты» (три панели)

В сайдбаре выберите **«Проекты»** (группа «Работа»). Страница — три панели:
слева список воркспейсов, в середине дерево каталогов выбранного
воркспейса, справа зона с табами (сегодня один таб — **«Сессии»**).

Список (панель «Воркспейсы»): вверху закреплён **«Дом агента»** (без меню
действий), ниже — проекты; у каждого проекта справа кнопка «⋮» с меню
действий (сегодня — «Удалить»); «+» над списком открывает модалку создания
проекта. Ожидается: клик по строке подсвечивает её, выбор переживает
перезагрузку страницы (localStorage). На свежем сервере дерево «Дома
агента» содержит стартовые файлы `AGENTS.md`, `self.md` и каталог `skills/`
с `README` (сервер создаёт их один раз при первом старте).

Дерево: пока воркспейс не выбран, средняя панель показывает «Выберите
воркспейс»; после выбора (дом или проект) появляется дерево корня —
каталоги раскрываются кликом, содержимое читается лениво, по одному
каталогу (`/api/workspaces/tree`). Для пустого проекта ожидается «Каталог
пуст» вместо списка.

Правая зона: сверху плашка табов — **«Сессии»** и кнопка **«Обновить»**
справа, ниже содержимое активного таба. Таб «Сессии» показывает сессии
выбранного воркспейса (`POST /api/sessions/list`, bearer), от новых к старым.
Строка — «заголовок · канал · время создания»: заголовок сессии из её лога
(если события заголовка в логе нет, показывается «Без заголовка»), канал,
создавший сессию (сейчас `telegram`), и её время создания. Состояния: пока
ответ не пришёл — «Загрузка…», у воркспейса без сессий — «Сессий пока нет»,
при ошибке — «Не удалось загрузить сессии: …» и кнопка **«Повторить»**;
без выбранного воркспейса правая зона показывает «Выберите воркспейс» (как
и средняя). Список перечитывается при выборе воркспейса, по **«Обновить»**
и по «Повторить»; сам он не «живой»: новая сессия появляется в нём после
«Обновить».

Живое обновление: создайте файл на сервере, не трогая страницу —
`touch "$DSH_HOME/projects/<имя проекта>/x.txt"` — ожидается появление
`x.txt` в дереве в течение пары секунд **без перезагрузки страницы**
(страница подписана на `/api/workspaces/events`; тот же канал обновляет
список при создании/удалении проектов и дерево «Дома агента» —
`$DSH_HOME/agent/`).

### Глобальный контекст дома агента

Дом агента `$DSH_HOME/agent/` — не только домашний воркспейс, но и
**глобальный контекст** всех сессий сервера: и Telegram-задач, и админского
тестового промпта. Владелец правит файлы дома напрямую (редактором на
сервере, через SFTP или из дерева админки); правки подхватываются **без
переустановки** — запускать установщик или рестартовать сервис не нужно.

- `agent/AGENTS.md` — глобальные правила (user-global инструкции). Они
  рендерятся первыми, затем идёт проектная цепочка `AGENTS.md` от корня
  проекта к рабочему каталогу: более конкретный файл главнее. Правка действует
  на следующую задачу во **всех** воркспейсах.
- `agent/self.md` — самоописание агента: содержимое подставляется в системный
  промпт отдельной секцией `balbes:self`. Файл перечитывается по времени
  изменения, поэтому достаточно сохранить файл. Символы `{{` экранируются и
  не ломают сборку промпта; если файла нет или он нечитаем — секция просто
  пустая, задача не падает.
- `agent/skills/` — глобальные скиллы. Каталог `agent/skills/<имя>/SKILL.md`
  (или плоский `agent/skills/<имя>.md` с frontmatter `name`/`description`)
  виден во всех воркспейсах. Стартовый `agent/skills/README` — инструкция по
  формату; провайдер скиллов его не парсит.
- `<project>/.dsh/skills/` — скиллы проекта (нативный project-корень): видны
  только в задачах этого проекта. При совпадении имени со скиллом дома
  проектный затеняет домашний. Каталог создаётся при создании проекта (со
  стартовым `README`).

Слои применяются в порядке global → project: домашние правила и скиллы — база,
проектные их дополняют и уточняют.

Как это видно из Telegram: выбранный воркспейс (`Дом агента` или проект)
задаёт рабочий каталог задачи, но глобальный контекст дома действует всегда.
Проверка в чате — попросить агента пересказать правило из `AGENTS.md` или
открыть файл дома через «📄 Файлы»; вызов скилла виден в карточке прогресса.
Скилл из `<project>/.dsh/skills` доступен только при выбранном проекте, а
`agent/skills` — и в проекте, и в доме.

## Настройка Telegram через админку

Откройте админку и войдите обычными учётными данными. В сайдбаре выберите
**«Telegram»** — страница с карточкой статуса и формой: поля **«Токен бота»**
и **«User ID»**, чекбокс **«Включить бота»** и кнопки **«Проверить
подключение»**, **«Сохранить»**, **«Отключить»**, **«Удалить токен»**. Всё
настраивается из этой формы: рестарт сервиса не нужен, настройки применяются
на лету.

1. Создайте бота через BotFather и скопируйте bot token.
2. Узнайте свой числовой Telegram User ID через доверенного Telegram-бота.
3. Вставьте token и User ID в форму. Пустое поле означает «оставить как есть»,
   а не «очистить»: пустой токен сохраняет текущий токен, пустой User ID —
   текущий id (заменить User ID можно только другим положительным числом,
   сбросить его из формы нельзя). Сам токен в интерфейсе не показывается
   никогда — при сохранённом токене карточка печатает `Токен: ••••`.
4. Нажмите **«Сохранить»**. Сохранение с включённым ботом требует, чтобы был
   сохранён токен **и** положительный User ID: `{"enabled":true}` без токена
   или без User ID сервер отклоняет целиком — `400 invalid-config`, при этом
   не записывается ни токен, ни настройки. Нечисловой или нулевой User ID —
   `400 invalid-user-id` (в форме это видно раньше: кнопка «Сохранить»
   заблокирована, если введён неположительный id или включён бот без id).
5. Нажмите **«Проверить подключение»**. Кнопка проверяет **сохранённый**
   токен одним вызовом `getMe` и больше ничего: ничего не сохраняет, не
   включает и не меняет статус. Ожидается строка
   `Подключение работает: @имя_бота`. Поэтому порядок такой: сначала
   «Сохранить» токен, потом проверять (введённый, но не сохранённый токен не
   проверяется). Если токена ещё нет — `400 not-configured`, неверный токен —
   `400 invalid-token`, недоступный Telegram — `502 telegram-error`.
6. Включите чекбокс «Включить бота» и сохраните — long polling стартует **без
   рестарта сервиса**. Карточка статуса показывает **«подключено»**, а через
   несколько секунд — и `Последний успешный опрос`. Если сразу после
   сохранения статус ещё не «подключено», это нормально: цикл стартует фоном,
   а статус страница перечитывает на каждой операции.
7. В личном чате с ботом отправьте `/start` — ожидается карточка-меню
   **«🤖 Агент сервера»**: строки состояния (`Воркспейс не выбран`, `Задача:
   нет активной задачи`, `Модель: <модель> · <подключение>`) и кнопки
   **«📁 Воркспейсы»**, **«🧠 Модель»**, **«🔄 Обновить»**. Нажмите
   «📁 Воркспейсы» и выберите `Дом агента` или проект — бот присылает **новым
   сообщением** `Выбран: …` с кнопками карточки: **«📄 Файлы»**,
   **«🧠 Модель»**, **«📁 Воркспейс»**, **«🔄 Сбросить контекст»**,
   **«⏹ Стоп»** и **«🔄 Обновить»**. Список команд бот регистрирует в Telegram
   сам: по «/» у поля ввода виден список `/menu`, `/status`, `/ws`, `/model`,
   `/reset`, `/stop`, `/help`, а рядом с полем — кнопка **«Меню»**; `/help`
   присылает ту же справку текстом, `/menu` и `/start` — карточку, а
   `/status` — ту же карточку плюс строку `Сессия: активна` или
   `Сессия: не создана`. Неизвестная команда (например `/foo`) отвечает
   «Не знаю такой команды.» и той же карточкой; текст, начинающийся с `/`,
   агенту не уходит — его обрабатывает бот.
8. Отправьте текстовую задачу; ожидается живая карточка **«⏳ <воркспейс> ·
   время · шаг N»** со списком шагов инструментов (`🔧 read notes.txt ✔`) и
   кнопками **«⏹ Стоп»** / **«⬅ Меню»**. Она обновляется на месте не чаще
   раза в 3–4 секунды, пока задача выполняется, и превращается в квитанцию
   **«✅ Готово · время · N шагов»** — существительное согласуется с числом
   (`1 шаг`, `2 шага`, `5 шагов`). Финальный ответ штатного dsh agent loop
   приходит отдельным сообщением (длинный ответ — несколькими сообщениями).
   Пока задача идёт, следующее сообщение получает карточку **«🕓 <воркспейс> ·
   в очереди №N»** и стартует после текущей. Кнопка **«📄 Файлы»** открывает
   дерево выбранного воркспейса: каталоги раскрываются кликом, текстовые файлы
   показываются постранично. Бинарные файлы и симлинки не открываются.
   **«🔄 Сбросить контекст»** завершает текущую сессию воркспейса — следующая
   задача начнётся с чистого контекста; **«⏹ Стоп»** (и команда `/stop`)
   останавливает задачу вместе с очередью, но сессию **сохраняет** — следующая
   задача продолжает тот же диалог.

Порядок проверки после обновления сервера (шаги, ожидаемые результаты и что
делать при расхождении) — в разделе «Чеклист проверки Telegram (после
обновления)»; типовые сбои — в «Устранение неполадок».

Задача из Telegram выполняется с **полной поверхностью инструментов процесса** —
той же, что у Web-агента: файлы (`read`, `read_image`, `write`, `edit`, `glob`,
`grep`), поиск в интернете (`web_search`, `web_fetch`), оболочка (`bash`; на
Windows — `pwsh`), навыки (`skill`), делегирование (`subagent`, `subagent_fork`,
`workflow`, `ralph`), управление заданиями и агентами (`job_list`, `job_output`,
`job_kill`, `send_message`, `interrupt_agent`, `list_agents`) и планирование
(`todo_write`, цели) — то есть всё, что регистрирует композиция процесса. У
канала **нет** отдельного per-agent allow-фильтра и read-guard: доступ к сети и
файлам — как у Web-агента, поэтому задача может прочитать файл вне выбранного
воркспейса, включая `$DSH_HOME` и файлы других проектов. Это осознанное решение
владельца: единственный пользователь канала — владелец, и риск indirect prompt
injection принят.

Границы задачи — **sandbox-политика процесса** и approval
(`DSH_PERMISSION_MODE ?? workspace-write` + `ask`): чтение доступно настолько,
насколько позволяет ОС, запись вне writable-root ограничена sandbox, а
гейтованная операция без интерактивного отвечающего отклоняется (fail-closed), а
не зависает.

Поиск в интернете идёт через провайдера DeepSeek и использует **тот же**
`DEEPSEEK_API_KEY`, что и чат (тот же ключ, что в разделе «Модели»): отдельный
ключ для поиска не нужен, поиск ничего не записывает и не меняет настройки.
Если ключ доступен чату, но не виден поисковому провайдеру, вызов `web_search`
завершится ошибкой инструмента (код `WEB_PROVIDER_CREDENTIAL_MISSING`, в тексте —
«no API key»), и задача при этом не сломается: остальные инструменты работают, а
агент сообщит об ошибке поиска. Такое расхождение требует разведённых ключей: у
модели по умолчанию должно стоять подключение со своим `apiKeyEnv` (не штатный
`deepseek-official`, который берёт тот же `DEEPSEEK_API_KEY`), либо в профиле
вручную переопределён `apiKeyEnv` у строки `web-search-deepseek` — в штатной
конфигурации ключ у чата и поиска один, и этой ошибки быть не должно. Если же
ключа нет **вообще**, дело не в поиске: без ключа не проходит сам вызов модели,
поэтому задача падает раньше поиска и ровно так же, как в разделе «Нет ключа
модели» (ошибка агента, а не отчёт о поиске) — сначала восстановите ключ, потом
проверяйте поиск.

Кнопки формы и состояния карточки:

- **«Отключить»** — выключает бота (`enabled: false`), **токен сохраняется**;
  входящие update больше не обрабатываются.
- **«Удалить токен»** (через подтверждение в модалке) — удаляет токен из
  хранилища и выключает бота: состояние становится **«не настроено»**.
- Состояния: **«не настроено»** (токена нет), **«выключено»** (токен есть, бот
  выключен), **«подключено»** (цикл опроса работает), **«ошибка»** (включено,
  но цикл не работает — рядом строка `Ошибка бота: …`).

Что происходит с polling при отключении: состояние в `/api/telegram/status`
меняется **сразу** (оно читается из настроек), а сам цикл опроса дожидается
уже начатого `getUpdates` и только потом встаёт — до ~50 с при живом Telegram
и до ~180 с при мёртвой сети (повторы по таймауту). Это не зависание: ручки
отвечают, не дожидаясь остановки, поэтому «выключено» в статусе сразу после
нажатия — ожидаемое поведение.

Окно остановки — ровно **одна уже полученная пачка** update, и это стоит
знать при отключении или удалении токена:

- если `getUpdates` вернул батч до нажатия «Отключить», батч обрабатывается до
  конца: задачи уходят агенту, а ответы приходят в чат уже **после** того, как
  статус показывает «выключено» (токен сохранён, bot-клиент жив). Offset
  такого батча подтверждён Telegram, поэтому после повторного включения эти
  update второй раз не придут;
- если батч пришёл уже после отмены, он отбрасывается без подтверждения
  offset: после повторного включения бот получит его заново — задача не
  потеряется, но и не выполнится дважды в рамках одного процесса;
- «Удалить токен» — исключение из первого пункта: токен исчезает сразу, и
  рантайм на переходе, который запускает сама ручка, забывает bot-клиента,
  поэтому задача из уже полученной пачки доигрывается, а отправить ответ в
  чат уже не может. Нажимайте «Удалить токен», когда задач в работе нет.

Просмотр файлов в чате ограничен настройкой `maxFileBytes` плагина (по
умолчанию 256 КиБ): это предел **отображения** файла в Telegram, а не
ограничение доступа агента — агент читает файлы воркспейса своими файловыми
инструментами (`read`, `glob`, `grep`), и `maxFileBytes` их не ограничивает.

Входящие сообщения из групп и от другого User ID игнорируются молча, без
раскрытия списка воркспейсов.

Служебная переменная окружения `BALBES_TELEGRAM_API_BASE` задаёт базовый адрес
Bot API и существует только для тестов (указывает на локальный фейковый Bot
API): на сервере она не задаётся — ни в юните, ни в профиле — и менять её не
нужно.

## Smoke без браузера (curl + JWT)

Команды — блок «Smoke without a browser» из итоговой сводки установщика
(`print_admin_summary` в `scripts/install.sh`), здесь — с корректным
извлечением токена из JSON-ответа логина. Логин и пароль подставьте из лога
установки. Ответ `POST /api/auth/login` — JSON
`{"token": ..., "expiresAt": ...}`; для запросов нужен только `token`:

```bash
# 1) Публичный health-чек
curl -fsS -X POST http://127.0.0.1:8080/api/health
# ожидается: {"ok":true,"version":"0.1.0"}

# 2) Логин: получаем JWT
RESP=$(curl -fsS -X POST http://127.0.0.1:8080/api/auth/login \
  -H 'content-type: application/json' \
  -d '{"login":"balbes-1a2b3c4d","password":"ВАШ-ПАРОЛЬ-ИЗ-ЛОГА"}')
# ожидается: {"token":"eyJ...","expiresAt":"..."}
TOKEN=$(printf '%s' "$RESP" | node -pe 'JSON.parse(require("fs").readFileSync(0,"utf8")).token')

# 3) Тестовый промпт с JWT (нужен настроенный ключ DeepSeek)
curl -fsS -X POST http://127.0.0.1:8080/api/prompt \
  -H "authorization: Bearer $TOKEN" \
  -d '{"prompt":"Напиши ok"}'
# ожидается: HTTP 200, JSON вида {"text":"ok","reason":{"kind":"completed"}}
```

```bash
# воркспейсы (bearer; подставьте TOKEN из входа выше)
curl -sS -X POST http://127.0.0.1:8080/api/workspaces/list \
  -H "authorization: Bearer $TOKEN"
curl -sS -X POST http://127.0.0.1:8080/api/workspaces/create \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"name":"my-project"}'
curl -sS -X POST http://127.0.0.1:8080/api/workspaces/delete \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \

#    после задачи агенту через Telegram здесь появляется одна запись вида
#    {"id":"session-…","title":"…","channel":"telegram","createdAt":"2026-…Z"}
#    (порядок — от новых к старым; title:null, если в логе нет заголовка)

выполните задачу через Telegram, а потом проверяйте; если сессий в воркспейсе

# форма документа: version и карта workspaces с ключами home / project:<имя>

  "$DSH_HOME/workspace-sessions.json"

#    в записях только sessionId и channel (заголовки и время — из логов сессий)
```

сервере тот же, что у первого curl ниже:

Полный smoke Telegram-канала — REAL-тест пакета `dsh-balbes-telegram`
(`integration.test.ts`), ниже — то, что можно проверить на живом сервере:

```bash
# статус на свежем сервере (токена ещё нет)
curl -sS -X POST http://127.0.0.1:8080/api/telegram/status \
  -H "authorization: Bearer $TOKEN" -w '\nHTTP %{http_code}\n'
#    ожидается: HTTP 200
#    {"status":{"state":"not-configured","tokenConfigured":false,"enabled":false}}

# включить без токена и User ID: 400, НИЧЕГО не записывается
curl -sS -X POST http://127.0.0.1:8080/api/telegram/save \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"enabled":true}' -w '\nHTTP %{http_code}\n'
#    ожидается: HTTP 400
#    {"error":{"code":"invalid-config","message":"store a bot token and a positive User ID before enabling the bot"}}

# неположительный User ID (0, отрицательный, null) — тоже 400
curl -sS -X POST http://127.0.0.1:8080/api/telegram/save \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"allowedUserId":0}' -w '\nHTTP %{http_code}\n'
#    ожидается: HTTP 400
#    {"error":{"code":"invalid-user-id","message":"allowedUserId must be a positive integer"}}

# тест подключения без сохранённого токена
curl -sS -X POST http://127.0.0.1:8080/api/telegram/test \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{}' -w '\nHTTP %{http_code}\n'
#    ожидается: HTTP 400
#    {"error":{"code":"not-configured","message":"bot token is not configured"}}

# сохраняем токен и User ID, бот пока выключен
curl -sS -X POST http://127.0.0.1:8080/api/telegram/save \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"token":"123456:ВАШ-ТОКЕН","allowedUserId":123456789,"enabled":false}' \
  -w '\nHTTP %{http_code}\n'
#    ожидается: HTTP 200
#    {"status":{"state":"disabled","tokenConfigured":true,"enabled":false,"allowedUserId":123456789}}

# тест подключения с сохранённым токеном (getMe; ничего не сохраняет и не включает)
curl -sS -X POST http://127.0.0.1:8080/api/telegram/test \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{}' -w '\nHTTP %{http_code}\n'
#    ожидается: HTTP 200 {"username":"имя_бота"} (имя без @)
#    неверный токен → HTTP 400 {"error":{"code":"invalid-token",...}}
#    Telegram ответил иначе/недоступен → HTTP 502
#    {"error":{"code":"telegram-error","message":"…"}} (текст ошибки Telegram,
#    токен в нём вырезан; без ответа от Telegram — "getMe failed")

# включаем бота (токен и User ID уже сохранены)
curl -sS -X POST http://127.0.0.1:8080/api/telegram/save \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"enabled":true}' -w '\nHTTP %{http_code}\n'
#    ожидается: HTTP 200; "state" становится "connected", когда цикл опроса
#    действительно поднялся (обычно сразу, иногда через пару секунд), плюс
#    "botUsername" после фонового getMe и "lastPollAt" после первого опроса:
#    {"status":{"state":"connected","tokenConfigured":true,"enabled":true,
#               "allowedUserId":123456789,"botUsername":"имя_бота","lastPollAt":"2026-…"}}

# отключаем бота: токен ОСТАЁТСЯ
curl -sS -X POST http://127.0.0.1:8080/api/telegram/disable \
  -H "authorization: Bearer $TOKEN" -w '\nHTTP %{http_code}\n'
#    ожидается: HTTP 200
#    {"status":{"state":"disabled","tokenConfigured":true,"enabled":false,"allowedUserId":123456789}}
#    (состояние меняется сразу; сам цикл опроса дожидается текущего getUpdates —
#     до ~50 с при живом Telegram, до ~180 с при мёртвой сети)

# удаляем токен: бот выключается, состояние "не настроено"
curl -sS -X POST http://127.0.0.1:8080/api/telegram/clear-token \
  -H "authorization: Bearer $TOKEN" -w '\nHTTP %{http_code}\n'
#    ожидается: HTTP 200
#    {"status":{"state":"not-configured","tokenConfigured":false,"enabled":false,"allowedUserId":123456789}}

# без токена все пять ручек обязаны отвечать 401
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:8080/api/telegram/status
#    ожидается: 401
```

Порядок в блоке соответствует состояниям: `not-configured` → `disabled` →
`connected`. Строка `tokenConfigured` — единственное, что API сообщает о
токене; сам токен не возвращается ни в одном ответе. Поле `botUsername`
заполняется фоновым `getMe`, поэтому появляется не мгновенно и может ещё
присутствовать в ответе на `disable`/`clear-token` (имя сбрасывается вместе с
токеном в фоне) — ориентируйтесь на `state` и `tokenConfigured`.

Если на шаге 2 вместо токена пришла ошибка — проверьте, что в
`-d '{"login":...,"password":...}'` подставлены именно те значения, что
напечатаны в логе установки, и что файл `$DSH_HOME/admin-auth.json`
существует (см. «Битый или удалённый admin-auth.json»).

Требуется настроенный ключ модели: `/api/prompt` гоняет запрос через
реальную модель DeepSeek (ключ — в `$DSH_HOME/.credentials.yaml`). Без ключа
ответ — HTTP 502 с `reason.kind="error"` (см. «Нет ключа модели»).

## Чеклист проверки Telegram (после обновления)

Тот же порядок, что и в «Настройка Telegram через админку» и в
Telegram-блоке «Smoke без браузера»: команды там, здесь — порядок, ожидаемый
результат каждого шага и что делать при расхождении. Выполняйте подряд;
шаги 1-3 проверяются без Telegram-клиента, шаги 4-8 — в личном чате.

**Шаг 0. Обновление дошло до сервера.**

```bash
bash ~/dsh-balbes-server/scripts/install.sh      # Enter на запрос ключа
```
Ожидается: `Profile 'balbes' composes OK.`, строка копирования
`Telegram plugin copied into …/node_modules/dsh-balbes-telegram`,
`Health OK: POST http://127.0.0.1:8080/api/health`. При сбое — «Обновление» и
«Сервис не стартует или падает».

**Шаг 1. Плагин собрался и отвечает.** Статус должен быть пустым, а не 404:
`{"status":{"state":"not-configured","tokenConfigured":false,"enabled":false}}`.
404 на `/api/telegram/status` означает, что профиль не пересинхронизирован —
повторите шаг 0.

**Шаг 2. Валидация до записи.** `save` без токена и User ID → `400
invalid-config`; `save {"allowedUserId":0}` → `400 invalid-user-id`; после
обеих ошибок `status` не изменился (ничего не записалось).

**Шаг 3. Сохранение и проверка токена.** `save` с реальным token + своим
User ID + `"enabled":true` → `200`, в ответе `state:"connected"` (username
появляется фоновым `getMe` — повторите `status`). Затем `test` → `200
{"username":"…"}`; отдельно с испорченным токеном → `400 invalid-token`.

**Шаг 4. Первый контакт в Telegram.** `/start` → карточка `🤖 Агент сервера`
со строками `Воркспейс не выбран`, `Задача: нет активной задачи` и
`Модель: <модель> · <подключение>`; кнопки — «📁 Воркспейсы», «🧠 Модель»,
«🔄 Обновить». Список команд зарегистрирован в Telegram: по «/» у поля ввода
видно `/menu`, `/status`, `/ws`, `/model`, `/reset`, `/stop`, `/help`, рядом с
полем — кнопка «Меню». `/menu` и `/start` присылают эту же карточку,
`/status` — ту же карточку плюс строку `Сессия: активна` или
`Сессия: не создана`, `/help` — справку («/stop — остановить задачу
(контекст сохраняется)», «/reset — сбросить контекст (сессия удаляется)»).
«📁 Воркспейсы» открывает список: `Дом агента` и проекты, под списком —
кнопка «⬅ Меню» (возврат к карточке); выбор строки (`Дом агента` или проект)
→ **новое** сообщение `Выбран: …` с полным набором кнопок («📄 Файлы»,
«🧠 Модель», «📁 Воркспейс», «🔄 Сбросить контекст», «⏹ Стоп», «🔄 Обновить»).
Неизвестная команда (например `/foo`) → «Не знаю такой команды.» и та же
карточка; текст, **начинающийся** с `/`, агенту не уходит — его обрабатывает
бот (путь вроде `/etc/hosts` внутри текста задачи уходит агенту как обычно).

**Шаг 5. Задача.** Текстовое сообщение → живая карточка **«⏳ <воркспейс> ·
время · шаг N»** со списком шагов инструментов (`🔧 read notes.txt ✔`) и
кнопками «⏹ Стоп» / «⬅ Меню»; она обновляется на месте не чаще раза в 3–4
секунды, пока задача идёт, и становится квитанцией **«✅ Готово · время · N
шагов»** (существительное согласуется с числом: «1 шаг», «2 шага», «5
шагов»); финальный ответ приходит отдельным сообщением (длинный — несколькими
сообщениями). Проверьте, что агент действительно работает с выбранным
воркспейсом: попросите прочитать файл внутри проекта — ответ должен содержать
его содержимое.

Пока задача идёт, следующее сообщение получает карточку **«🕓 <воркспейс> ·
в очереди №N»** и стартует после текущей. Отказ приходит квитанцией, а не
успехом: если в очереди уже три задачи (предел), новая не запускается →
**«⚠️ Ошибка · 0:00: очередь заполнена»** и сообщение «В этом воркспейсе уже
3 задачи в очереди — дождитесь завершения»; тот же текст задачи дважды подряд
→ **«⚠️ Ошибка · 0:00: задача уже выполняется»** и «Задача уже выполняется…».

**Шаг 6. Границы канала (паритет с Web-агентом).** Пять проверок:
1. Попросите задачу, требующую оболочки (например: «выполни `whoami` через
   bash»). Ожидается результат команды: набор инструментов у Telegram-задачи
   полный, как у Web-агента, и `bash` ей доступен (см. «Настройка Telegram через
   админку», абзац про поверхность инструментов).
2. Попросите прочитать файл вне воркспейса (например `/etc/hostname` или файл
   другого проекта) — ожидается содержимое файла: отдельного read-guard у
   канала нет, чтение доступно настолько, насколько позволяет ОС.
3. Попросите найти что-то в интернете (например: «найди в интернете, какая
   сейчас погода в Москве»). Ожидается результат поиска — сводка и/или список
   ссылок-источников: инструмент `web_search` у задачи есть. Если вместо
   результата пришла ошибка поиска (в тексте «no API key», код
   `WEB_PROVIDER_CREDENTIAL_MISSING`) — значит ключ `DEEPSEEK_API_KEY` не виден
   поисковому провайдеру; в штатной конфигурации ключ у чата и поиска один, так
   что это признак разведённых ключей (см. `apiKeyEnv` в абзаце про поиск в
   «Настройка Telegram через админку»). Если бы ключа не было **вовсе**, задача
   упала бы раньше — на вызове модели (см. «Нет ключа модели»), а не ошибкой
   поиска.
4. Попросите открыть конкретный URL (например: «открой
   `https://example.com` и покажи текст страницы»). Ожидается содержимое
   страницы: `web_fetch` у задачи есть, как и у Web-агента.
5. Негативный контроль, что границы реальны: попросите записать файл за
   пределами воркспейса (например, в `/etc` или домашний каталог сервиса).
   Ожидается отказ sandbox/approval, а не тихая запись — границы задачи это
   sandbox-политика процесса (`workspace-write` + `ask`).

**Шаг 7. Файлы и сброс контекста.** Кнопка «📄 Файлы» открывает дерево
выбранного воркспейса: каталоги раскрываются, текстовый файл показывается
постранично, бинарный файл и симлинк не открываются. «🔄 Сбросить контекст» →
подтверждение («Да, сбросить» / «Отмена», ниже — «⬅ Меню» для возврата к
карточке) → «Контекст сессии сброшен»: следующая задача начинается с чистого
контекста (агент не помнит прошлую).

Отдельно проверьте три вещи. `/model` → «🧠 Модель сейчас: <модель> ·
<подключение>» → соединение → модель: карточка, в которой вы выбирали,
становится меню и показывает новую модель в строке `Модель:`, селект
«Дефолтная модель» в разделе «Модели» админки показывает ту же модель, а
следующая задача в том же воркспейсе отвечает без сброса контекста (агент
помнит предыдущий вопрос). `/stop` во время длинной задачи («считай от 1 до
1000») → «Остановил. Контекст сохранён — можно ставить новую задачу.» и
квитанция **«⏹ Остановлено владельцем · время»** в карточке самой задачи;
следующая задача **помнит** предыдущий диалог — в отличие от `/reset`, после
которого агент не помнит ничего. Соединение без ключа помечено в пикере «нет
ключа», нажатие отвечает подсказкой «Ключ не задан — добавьте в админке» и
ничего не меняет.

**Шаг 8. Отказы для чужих и групп.** Напишите боту с другого Telegram-аккаунта
и добавьте бота в группу: в обоих случаях бот не должен ответить ни в личку,
ни в группу, и не должен выдать список воркспейсов или содержимое файлов.
При этом в `/api/telegram/status` ошибок быть не должно — такие update просто
игнорируются.

**Шаг 9. Состояние переживает рестарт.**

```bash
sudo systemctl restart dsh-balbes
```
После возврата сервиса: `status` снова `connected`, `Последний успешный опрос`
обновляется; задача в ранее выбранный воркспейс продолжает **ту же** сессию —
агент помнит предыдущую переписку. Проект, удалённый при живом канале,
сбрасывает выбранный воркспейс и просит выбрать заново.

**Шаг 10. Отключение и удаление токена.** «Отключить» (`disable`) → `200`,
`status` сразу `disabled`, токен сохранён; в Telegram новые сообщения больше
не обрабатываются. Остановка не мгновенна: цикл докатывает текущий `getUpdates`
(до ~50 с на живой сети, до ~180 с при недоступном Telegram) — это не
зависание. «Удалить токен» (`clear-token`) → `not-configured`, токена нет в
`$DSH_HOME/.credentials.yaml`, polling выключен.

**Шаг 11. Данные на диске.** `ls -l $DSH_HOME/telegram-state.json` —
существует, права `600`; форма файла та же, что до появления команд и смены
модели: `"version": 1`, `activeWorkspace`, `sessions`, `offset` — и **нет**
токена. Токен — только в `$DSH_HOME/.credentials.yaml`; настройки — секция
`balbes-telegram` в `$DSH_HOME/settings.yaml`. Модель в `telegram-state.json`
не хранится: её место — секция `agent-default-model` того же
`$DSH_HOME/settings.yaml`, и это ровно та настройка, которой управляет раздел
«Модели» админки (см. «Где лежат данные»). Один и тот же токен не должен
встречаться в выводе
`sudo journalctl -u dsh-balbes -n 200`.

**Шаг 12. Глобальный контекст дома.** Проверяется без переустановки:
1. Допишите в `$DSH_HOME/agent/AGENTS.md` строку-маркер (например
   «во всех ответах упоминай кодовое слово БАЛЬБЕС»). Выберите в Telegram
   «Дом агента» и отправьте задачу — маркер учтён; затем выберите проект —
   маркер действует и там: домашнее правило глобально.
2. Измените `$DSH_HOME/agent/self.md` и отправьте задачу — самоописание
   подхватится без рестарта сервиса (файл читается по времени изменения);
   секция не появляется в промпте, если файла нет.
3. Создайте `$DSH_HOME/agent/skills/<имя>/SKILL.md` — скилл доступен и в
   доме, и в проекте. Затем создайте
   `$DSH_HOME/projects/<имя>/.dsh/skills/<имя>/SKILL.md` с другим
   содержимым — в проекте побеждает проектный скилл, в доме — домашний.
4. Уберите маркеры после проверки; на диск при обычном обновлении ничего не
   переносится.

**Если что-то не так.** Пришлите: вывод упавшего шага, ответ
`/api/telegram/status`, `sudo journalctl -u dsh-balbes -n 100 --no-pager` и
(для шагов 4-8) текст сообщений бота. Не пересылайте сам bot token.

## Обновление

Обновление — повторный запуск установщика: он подтянет репозиторий
(`git pull --ff-only`), пересоберёт workspace, пересинхронизирует профиль,
обновит host и SPA на диске. Ключ API при запросе пропускается (Enter).
Пароль администратора при этом **не меняется**: `admin-auth.json` уже
существует, поэтому печатается только `Admin login (unchanged): <login>`;
данные сессий dsh не трогаются.

```bash
curl -fsSL https://raw.githubusercontent.com/mdikarev/dsh-balbes-server/main/scripts/install.sh | bash
curl -fsS -X POST http://127.0.0.1:8080/api/health   # {"ok":true,...}
```

Установщик **перезапускает сервис на каждом запуске** (`systemctl restart`
в шаге 11), поэтому после обновления демон сразу работает на новом коде —
ручной `systemctl restart dsh-balbes` не нужен. Перезапускайте юнит вручную
только если меняли что-то руками (конфигурацию юнита, файлы окружения и т.п.),
см. «Устранение неполадок».

## Сброс пароля

Пароль хранится только в виде scrypt-хэша — восстановить его нельзя, только
сгенерировать новый:

```bash
bash ~/dsh-balbes-server/scripts/install.sh --reset-admin-password
```

Ожидаемый вывод:

```
Password reset for login: balbes-1a2b3c4d
  new password (printed once): <новый пароль>
```

Логин при сбросе сохраняется, а `jwtSecret` ротируется: вместе с новым
паролем (scrypt-хэшем) в файл атомарно записывается новый секрет подписи.
Поэтому старый пароль сразу перестаёт подходить, и **ранее выданные JWT сразу
становятся недействительными** (файл перечитывается при каждой выдаче и
проверке токена и при каждом входе — рестарт не нужен). Команда требует уже
выполненной установки: она читает существующий `$DSH_HOME/admin-auth.json` и
собранный host. После сброса войдите в админку с новым паролем.

## Проверка демона

Юнит `/etc/systemd/system/dsh-balbes.service`: сервис от имени пользователя,
который запускал установку; `ExecStart` — глобальный `dsh --profile balbes`;
переменные `DSH_HOME`, `BALBES_PORT`, `BALBES_UI_DIST`; `Restart=on-failure`;
basic hardening (`NoNewPrivileges`, `PrivateTmp`, `ProtectSystem`,
`ReadWritePaths=$DSH_HOME`); `WantedBy=multi-user.target` с
`After/Wants=network-online.target`.

```bash
systemctl status dsh-balbes        # active (running), enabled
systemctl is-enabled dsh-balbes    # enabled
systemctl is-active dsh-balbes     # active
```

Демон поднимается при загрузке: переживает reboot VPS. После
`sudo reboot` и возврата по SSH:

```bash
systemctl is-active dsh-balbes     # active (может понадобиться пара секунд
                                   # после появления сети: юнит ждёт network-online)
curl -fsS -X POST http://127.0.0.1:8080/api/health   # {"ok":true,...}
```

## Ручная проверка (DoD, спека 9.4)

Список — ровно критерии готовности Этапа 2 (спека 9.4). Раздел самодостаточен:
команды и ожидаемые результаты ниже; выполняется на VPS после установки
(пункты 3–4 и 6–7 используют команды разделов «Доступ»/«Smoke без браузера»/
«Обновление»/«Сброс пароля»).

```bash
# 1. Демон и reboot
systemctl is-enabled dsh-balbes && systemctl is-active dsh-balbes
#    ожидается: enabled, active
sudo reboot   # после возврата:
systemctl is-active dsh-balbes
#    ожидается: active — демон пережил reboot

# 2. Админка и отсутствие штатной морды
curl -fsS -X POST http://127.0.0.1:8080/api/health
#    ожидается: {"ok":true,"version":"0.1.0"}
ps aux | grep -i dsh | grep -v grep
#    ожидается: один процесс сервера (dsh --profile balbes); процессов
#    dsh-web-app / headless нет
dsh --profile balbes --dump-config | grep -E 'dsh-web-app|dsh-headless'
#    ожидается: пусто (grep ничего не нашёл)
```

3. **Вход.** В браузере `http://<IP>:8080`: логин/пароль из лога установки →
   страница с тестовым промптом; неверный пароль → ошибка 401. Либо curl:
   команда (2) из «Smoke без браузера» → `{"token":...}`.
4. **Кнопка / curl.** Кнопка **«Отправить тестовый промпт»** — ответ реальной
   модели над кнопкой; либо curl-команда (3) из «Smoke без браузера» →
   HTTP 200, `{"text":...,"reason":{"kind":"completed"}}`. Перезагрузка
   страницы с токеном не требует повторного входа (`/api/auth/me`).
5. **401 без токена** (проверено curl'ом «из интернета» — с другого хоста по
   `http://<IP>:8080`, если открыт файрвол):

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:8080/api/prompt -H 'content-type: application/json' -d '{"prompt":"x"}'   # 401
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:8080/api/auth/me                                                          # 401
#    health и login при этом открыты (см. п. 2 и 3)
```

6. **Обновление.** Повторный `install.sh` (команда из «Обновления»):
   установщик сам перезапускает сервис; логин и пароль не меняются
   (`Admin login (unchanged): ...`), данные сессий целы.
7. **Сброс пароля.** `bash ~/dsh-balbes-server/scripts/install.sh
   --reset-admin-password` → новый пароль в логе; вход по старому → 401, по
   новому → успех.
8. **Секреты не в git.** В клоне репозитория и в репозитории на GitHub нет
   `admin-auth.json` / `.credentials.yaml`; на сервере они с правами 600:

```bash
cd ~/dsh-balbes-server
git ls-files | grep -E 'admin-auth\.json|\.credentials\.yaml'   # пусто
ls -l "$HOME/.dsh/admin-auth.json" "$HOME/.dsh/.credentials.yaml"   # -rw------- (600)
```

9. **CI зелёный** — GitHub Actions на ветке `main`:
   https://github.com/mdikarev/dsh-balbes-server/actions (job `validate`:
   typecheck, тесты, сборка, композиция профиля без LLM, `bash -n` скриптов).
10. **Контракты.** SPA админки импортирует типы из `dsh-balbes-contracts`, и
    имена полей совпадают с host'ом: `/api/auth/login`
    `{login,password}` → `{token,expiresAt}`, `/api/prompt` `{prompt}` →
    `{text,reason}`, `/api/health` → `{ok:true,...}`. Проверка — typecheck:

```bash
cd ~/dsh-balbes-server && pnpm -r --if-present run typecheck   # exit 0
```

## Устранение неполадок

### Сервис не стартует или падает

Установщик при неудачном health-чеке печатает предупреждение
`health check failed`; первый шаг диагностики — статус и логи юнита:

```bash
systemctl status dsh-balbes
sudo journalctl -u dsh-balbes -n 50
```

Типичные причины: порт занят (см. ниже), `dsh` не найден по `ExecStart`
(переустановите глобально:
`sudo npm i -g "@deepseek-ai/dsh@$(cat "$HOME/dsh-balbes-server/scripts/engine-version.txt")"`
и повторите установщик), неверный `DSH_HOME` (юнит пишется со значениями на момент
установки — при другом `DSH_HOME` повторите установку с
`export DSH_HOME=...` перед запуском). После ручной правки юнита —
`sudo systemctl daemon-reload && sudo systemctl restart dsh-balbes`.

### Предупреждение о рассинхроне версии dsh

Установщик сверяет установленную версию движка (`dsh --version`) с пином из
`scripts/engine-version.txt` и при расхождении печатает в stderr блок вида:

```text
=====================================================================
WARNING: dsh engine version mismatch
  installed: <что стоит на хосте>
  expected:  <версия из scripts/engine-version.txt>
...
  sudo npm i -g "@deepseek-ai/dsh@<версия>"
=====================================================================
```

Это **не** ошибка установки: установщик продолжает работу и не переустанавливает
движок сам (обычный запуск не требует sudo, а сознательно выбранная на хосте
версия не затирается). Но профиль, канон и CI нацелены на ожидаемую версию,
поэтому сервер на другой версии может вести себя иначе. Обновите движок явно и
повторите установщик:

```bash
cd ~/dsh-balbes-server
git pull --ff-only
sudo npm i -g "@deepseek-ai/dsh@$(cat scripts/engine-version.txt)"
dsh --version   # должно совпасть с scripts/engine-version.txt
```

Если версию определить не удалось (`dsh --version` не печатает ничего похожего
на версию), установщик отдельно предупреждает об этом и тоже продолжает
работу — проверьте `command -v dsh` и `dsh --version` вручную.

### Health не отвечает

Сервис активен, но `POST /api/health` не даёт `{"ok":true,...}` — проверьте,
что слушатель на месте и отвечает:

```bash
sudo ss -ltnp | grep 8080        # ожидается: LISTEN на 0.0.0.0:8080 процессом dsh
curl -fsS -X POST http://127.0.0.1:8080/api/health
```

Если `ss` пуст — юнит не поднялся (см. предыдущий пункт). Если порт слушает
другой процесс — см. следующий пункт.

### Порт занят

В логах — `EADDRINUSE`, юнит падает в цикле рестарта. Порт задаётся
переменной `BALBES_PORT` **на момент установки** и фиксируется в юните.
Освободите порт или переустановите на другой:

```bash
export BALBES_PORT=8081
curl -fsSL https://raw.githubusercontent.com/mdikarev/dsh-balbes-server/main/scripts/install.sh | bash
sudo ufw allow 8081/tcp
# админка: http://<IP>:8081; health: POST http://127.0.0.1:8081/api/health
```

### Битый или удалённый `admin-auth.json`

Файл `$DSH_HOME/admin-auth.json` — не валидный JSON, отсутствует или имеет
неверную форму (например, вручную отредактирован без `jwtSecret`). При старте
в логах юнита — предупреждение `balbes-auth: admin auth file ... unusable
(missing, unreadable, or invalid shape); auth unavailable until the file is
valid`; защищённые маршруты (`/api/prompt`, `/api/auth/me`) отвечают 401, вход
по паролю — 401 (сервер «закрывается», но не падает: каждая попытка входа
перечитывает файл и пишет в лог причину).

Восстановление — пересоздать файл установщиком (он сгенерирует новый логин и
пароль и напечатает их один раз):

```bash
curl -fsSL https://raw.githubusercontent.com/mdikarev/dsh-balbes-server/main/scripts/install.sh | bash
```

Свежие логин/пароль — в логе (блок «Admin credentials generated»). Старые
логин/пароль при этом перестают работать (файл целиком пересоздан, `jwtSecret`
новый — и старые JWT тоже недействительны). Файл перечитывается на каждом
входе, поэтому после восстановления отдельный рестарт не обязателен —
установщик всё равно перезапускает сервис (шаг 11).

### Нет ключа модели

Кнопка/curl `/api/prompt` отвечают ошибкой (HTTP 502, `reason.kind="error"`,
или ошибка провайдера в админке) — сервер не может сходить в DeepSeek.
Ключ лежит в `$DSH_HOME/.credentials.yaml` (секция `refs`, имя
`DEEPSEEK_API_KEY`, права `600`) — порядок действий как в Этапе 1 (раздел
«Ключ не принят»). После правки перезапустите сервис:

```bash
sudo systemctl restart dsh-balbes
curl -fsS -X POST http://127.0.0.1:8080/api/prompt -H "authorization: Bearer $TOKEN" -d '{"prompt":"Напиши ok"}'
```

### 401 на защищённых маршрутах

`POST /api/prompt` и `POST /api/auth/me` без валидного JWT обязаны отвечать
401 — это нормальная работа защиты (проверка DoD, п. 5). Если 401 приходит с
валидными кредами на логине — проверьте значения из лога и не упёрлись ли вы
в rate-limit (5 неудач / 30 мин с IP → 429). Если токен перестал подходить
после перезапуска/сброса — просто войдите заново (JWT живёт до 24 ч).

### 500 «workspace sessions registry … is not valid JSON»

`sessions.list` (`POST /api/sessions/list`) отвечает HTTP 500
`{"error":{"code":"internal","message":"workspace sessions registry <путь> is not valid JSON"}}`,
а таб «Сессии» на странице «Проекты» показывает «Не удалось загрузить сессии: …»:
реестр сессий воркспейсов `$DSH_HOME/workspace-sessions.json` повреждён —
файл не разобрался как JSON, либо у него чужая форма (в тексте ошибки тогда
будет `has an unsupported version`, `misses the workspaces map`,
`has an invalid …` или `unreadable`). Путь в сообщении — тот самый файл;
он должен принадлежать пользователю сервиса и иметь права `600`.

Два способа восстановления:

- **починить файл** — привести его к форме
  `{"version":1,"workspaces":{}}` (или с записями вида
  `{"version":1,"workspaces":{"home":[{"sessionId":"session-…","channel":"telegram"}]}}`)
  и выставить права `600`;
- **удалить файл** — витрина пересоберётся из новых сессий, а Telegram при
  следующем старте сервиса зарегистрирует текущие сессии воркспейсов заново
  (их источник — `sessions` в `$DSH_HOME/telegram-state.json`; повторная
  запись того же `sessionId` ничего не дублирует). Без рестарта этого не
  произойдёт: досылка идёт на старте, поэтому после удаления выполните
  `sudo systemctl restart dsh-balbes`, если сессии нужны в списке сразу.

Нюанс кэша: **неудачное** чтение реестра не кэшируется, поэтому исправленный
или удалённый файл подхватывается уже следующим запросом — рестарт ради
починки не нужен. А вот успешно прочитанный реестр процесс держит в памяти:
правки файла «сбоку» (руками или другим процессом) сервис увидит только
после рестарта (`sudo systemctl restart dsh-balbes`).

### 404 на `/api/telegram/status`

Ручки нет в профиле: плагин не попал в `node_modules` профиля или профиль не
пересинхронизирован. Повторите установщик (см. «Обновление») и проверьте
строку `Telegram plugin copied into …` в его выводе, затем
`dsh --profile balbes --dump-config | grep -A2 balbes-telegram`.
Тот же 404 бывает, когда профиль собран без обязательной зависимости канала:
плагину Telegram нужен сервис моделей (`balbes-models`), поэтому в
`--dump-config` рядом с `balbes-telegram` обязана быть и `balbes-models` —
поставляемый профиль `balbes` её содержит, а установщик копирует её в
`node_modules` профиля (строка `Models plugin copied into …`).

### Статус `ошибка` в карточке Telegram

Так помечается либо фатальный ответ Telegram (`401` от Bot API — неверный или
отозванный токен: проверьте его в BotFather и сохраните заново), либо
`enabled` без работающего цикла. Смотрите поле ошибки в `status` и
`sudo journalctl -u dsh-balbes -n 100 --no-pager`. Одиночный сетевой сбой
статус в `ошибка` не переводит — он остаётся `подключено`, а текст последней
ошибки виден в `status`.

### Бот молчит в личном чате

Проверьте по порядку: `status.state` = `подключено`; User ID в настройках —
ровно тот, с которого пишете (чужой отправитель игнорируется молча, это
защита, а не сбой); сообщение отправлено в **личный** чат, а не в группу
(групповые update игнорируются). Если `enabled` включён, а `state` не
`подключено` — см. предыдущий пункт.

### В Telegram нет списка команд и кнопки «Меню»

Регистрация списка команд и нативной кнопки «Меню» (`setMyCommands` +
`setChatMenuButton`) — best-effort: она идёт на каждом успешном старте опроса,
а отказ Telegram только пишет предупреждение в лог. Сам опрос от неё не
зависит: бот отвечает и без списка — команды можно набирать руками.
Проверьте журнал и ответ Telegram (команду выполняйте на сервере, токен в чат
не пересылайте):

```bash
sudo journalctl -u dsh-balbes -n 200 | grep "command registration failed"
curl -sS "https://api.telegram.org/bot<token>/getMyCommands"
# ожидается: {"ok":true,"result":[{"command":"menu",…}, …]} — семь команд
```

Пустой `result` при чистом журнале означает, что опрос ещё ни разу не
стартовал успешно (список пушится только на переходе в «подключено»):
выключите и включите бота в админке.

### Карточка задачи перестала обновляться

Если задача идёт, а карточка «замерла» — это по дизайну, а не поломка: после
трёх подряд неудачных правок сообщения (Telegram троттлит правки или отвечает
«message is not modified») чат перестаёт обновлять эту карточку, чтобы не
долбить API вечно. Успешная правка сбрасывает счётчик, поэтому единичный сбой
обновление не выключает. Сама задача при этом идёт до конца, а финальная
квитанция и ответ приходят как обычно.

### Смена модели не подействовала на текущую задачу

Ожидаемое поведение: выбранная модель применяется со следующего шага, а шаг,
который уже выполняется, доигрывает на прежней — об этом карточка выбора и
пишет («Смена применится со следующего шага; текущий шаг доигрывает на
прежней модели.»). Проверяйте смену на следующей задаче в том же воркспейсе:
контекст при ней не сбрасывается, а строка `Модель:` карточки и селект
«Дефолтная модель» в админке показывают новый выбор сразу после нажатия.

### «Список устарел» на первом нажатии кнопки

Ожидаемое поведение только для старого сообщения со списком: кнопки указывают
на снимок списка, который сервер держит в памяти и теряет при рестарте. Бот
перерисовывает список — нажмите кнопку ещё раз. Если это повторяется на
свежем сообщении, пришлите вывод `status` и логи.

### Задача просит инструмент, которого нет

У Telegram-задачи **полная поверхность инструментов процесса**, та же, что у
Web-агента: `bash`, `web_fetch`, `skill`, субагенты и остальные инструменты ей
доступны. Если агент сообщает об отсутствии такого инструмента, это не
ограничение канала: либо модель назвала несуществующее имя (обычная
галлюцинация инструмента), либо профиль собран не полностью — тогда сверьтесь с
разделами «Обновление» и «Проверка демона».

### `disable` отвечает, а сообщения ещё обрабатываются

Ожидаемое поведение: статус читается из настроек и меняется сразу, а цикл
опроса докатывает уже начатый `getUpdates` — до ~50 с на живой сети и до
~180 с при недоступном Telegram. Новые пачки после остановки не забираются.

## Где лежат данные

Все данные сервера находятся в каталоге `$DSH_HOME` (по умолчанию `~/.dsh`):

- `profiles/balbes/` — профиль: манифест (`package.json` с
  `dsh.profile.bundles`) и `node_modules/` — копии собранных пакетов,
  которыми пользуется демон: `dsh-balbes-host/` (host-бандл),
  `dsh-balbes-workspaces/` (плагин воркспейсов),
  `dsh-balbes-models/` (плагин моделей),
  `dsh-balbes-sessions/` (плагин сессий воркспейсов),
  `dsh-balbes-telegram/` (плагин Telegram) и
  `dsh-balbes-home/` (плагин глобального контекста дома);
- `profiles/node_modules/` — зеркало-симлинки на установку dsh
  (`@deepseek-ai/*`), откуда резолвятся базовые бандлы;
- `admin-auth.json` — учётка администратора: логин, scrypt-хэш пароля,
  `jwtSecret`, `createdAt` (права `600`);
- `.credentials.yaml` — ключи API, включая `DEEPSEEK_API_KEY` (права `600`);
- `agent/` — зарезервированный домашний каталог агента (создаётся
  автоматически при первом обращении к API воркспейсов) и источник
  глобального контекста: `AGENTS.md` — глобальные правила, `self.md` —
  секция системного промпта, `skills/` — глобальные скиллы. При первом старте
  сервер кладёт стартовые файлы `AGENTS.md`, `self.md` и каталог `skills/` с
  `README` (только если их нет — правки владельца не перезаписываются);
- `projects/` — каталог проектов-воркспейсов: один подкаталог на проект,
  создаётся и удаляется только через API воркспейсов; при создании проекта в
  нём идемпотентно создаётся `<project>/.dsh/skills/README` (проектные скиллы,
  см. «Глобальный контекст дома агента»);
- `projects.json` — реестр воркспейсов (права `600`): метаданные строк
  (`createdAt` по имени проекта), не источник истины — строки, чей каталог
  удалён вручную, вычищаются при `list`;
- `workspace-sessions.json` — реестр сессий воркспейсов (права `600`,
  пишется атомарно, только добавление записей): принадлежность
  «воркспейс → `sessionId` + канал», ключ воркспейса — `home` или
  `project:<имя проекта>`. Заголовки и время создания здесь **не** хранятся:
  витрина берёт их из логов сессий `$DSH_HOME/sessions/`, поэтому сессия,
  чей лог уже удалён, в списке не появится. Пишет реестр Telegram-канал
  (первая задача в воркспейсе), он же при старте сервиса досылает в него
  сессии воркспейсов из `telegram-state.json`;
- `telegram-state.json` — состояние Telegram-канала (права `600`, пишется
  атомарно): offset long polling, выбранный в чате воркспейс и id сессий
  агента по воркспейсам. Форма файла (`version: 1`, `activeWorkspace`,
  `sessions`, `offset`) не менялась при добавлении команд и смены модели:
  выбранной в Telegram модели здесь нет — она живёт в секции
  `agent-default-model` файла `settings.yaml`. Токен бота здесь **не
  хранится** — он лежит в `.credentials.yaml`. Повреждённый файл не
  сбрасывается молча: сервер поднимается с пустым состоянием и пишет
  предупреждение в лог юнита, файл остаётся как был до первой успешной записи;
- `balbes/ui/` — собранный SPA админки, который раздаёт сервер;
- `settings.yaml` — настройки dsh, включая секцию `balbes-telegram`
  (`enabled`, `allowedUserId`), которой управляет страница «Telegram»,
  секцию `agent-default-model` (модель по умолчанию — её пишут и раздел
  «Модели» в админке, и выбор модели в Telegram) и сессии агента.

Всё это — секреты и локальное состояние: они не коммитятся в репозиторий и
больше нигде не хранятся. Профиль воспроизводим из репозитория, но
`admin-auth.json` и `.credentials.yaml` при удалении `$DSH_HOME` теряются
безвозвратно: после переустановки сгенерируются новый логин/пароль, а ключ
придётся ввести заново.
